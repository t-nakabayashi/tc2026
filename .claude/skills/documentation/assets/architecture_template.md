# <対象範囲名>

アーキテクチャ設計を新規作成するときの雛形。配置は `docs/` 直下とする。

複数パッケージにまたがる構造と責務分担を示す文書である。パッケージ内部の実装には
踏み込まない。それは詳細設計書の役割である。

## 1. 目的と対象範囲

- この文書が答える問いを書く。対象に含めるパッケージと、含めないものを明示する。
- 前提環境（実機、シミュレーション、必要なハードウェア）を書く。

## 2. 全体構成

- パッケージ一覧と、それぞれが担う責務を書く。
- 構成が複数ある場合（実機、模擬、単体試験）は、構成ごとに何が入れ替わるかを書く。

## 3. データフロー

- topic / service を軸に、入力から出力までの流れを書く。
- 図を使う場合は mermaid とする。図と本文が食い違わないよう、図には要約だけを置く。

## 4. 境界の定義

- パッケージ間で何を約束するかを書く。型、座標系、単位、時刻の基準、失効の扱い。
- 約束が破られたとき（未受信、失効、型不整合）に下流がどう振る舞うかを書く。

## 5. 各パッケージの責務

- 「何をするか」に加えて「**何をしないか**」を書く。責務の重複と抜けはここで防ぐ。

## 6. 設計上の制約と前提

- 現在の構成がその形になっている理由のうち、コードから読み取れないものを書く。
- 「A は〈制約〉により要件を満たさない」は書く。「A を試したが駄目だった」は書かない。

## 7. 未解決事項

- 未確定の仕様、確認待ちの事項を書く。何を確認すれば確定できるかを併記する。
