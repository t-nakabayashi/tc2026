# <package_name> 詳細設計書

パッケージ固有の詳細設計書を新規作成するときの雛形。既存パッケージに詳細設計書が
既にある場合はこの雛形を使わず、既存文書の章立て・用語・粒度に合わせて不足章の追加や
既存章への追記を行う（SKILL.md の「詳細設計書」参照）。

該当しない章は「該当なし」と明記するか、既存文書の粒度に合わせて省略理由を記載する。

**クラス名・関数名を列挙しない。** コードとドキュメントの二重管理になり必ず乖離する。
書くのはコードを読んでも分からないことに限る。

## 章立ての設計意図

10 章は「ROS の構成要素」ではなく「**1 つの設計判断を 1 箇所に置く**」ことを基準に
切っている。同じ事実を複数章へ書くと、片方だけが更新されて矛盾する。次の 3 つは
特に割れやすいため、置き場所を固定する。

| 割れやすいもの | 置く場所 | 他章で繰り返さない |
| --- | --- | --- |
| 設定値の既定値と、その値を選んだ理由 | **7 章**（判定ロジックと閾値） | 4 章は所在だけ。6 章・8 章で値を再掲しない |
| QoS の割り当てと、その QoS を選んだ理由 | **3 章**（外部インタフェース） | 8 章は周期・並行性のみ |
| 異常時の挙動 | **6 章**（処理フローと異常時の挙動） | 入力ごとに正常時と並べて書く |
| 既知の欠陥・制約の説明 | **7 章** | 10 章は参照と選択肢だけを書く |

## 1. 目的・スコープ

- 設計書の目的、対象パッケージ、対象ノードを記載する。
- **README が正とするものと、本書が定めるものを冒頭で切り分ける。** 一覧（topic、型、
  パラメータ、起動コマンド）は README を正とし、本書は再掲しない。
- 責務と非スコープを分けて書く。非スコープは「どのパッケージが担うか」を名指しする。
- 実装済み／未検証を区別する。実機、シミュレーション、GUI、センサ、外部デバイスなど
  前提環境がある場合は明記する。

## 2. 構成とファイル配置

- ノード、コアモジュール、補助ツール、launch、params、msg、srv、データファイルの関係を
  記載する。
- ROS 依存処理と ROS 非依存ロジックの分担を示し、`*_core.py` などへ切り出す範囲を
  明記する。
- 追加・変更する主なファイルと配置理由を表で整理する。
- 生成物、外部モデル、third_party、実機固有ファイルを扱う場合は、管理対象と非管理対象の
  境界を記載する。

## 3. 外部インタフェース仕様

- 一覧は README を正とする。**本章は一覧に現れない取り扱いだけを書く。** 配信・購読の
  条件、フィールドの解釈、配信を止める条件、終了時に出す値などである。
- **QoS はここに置く。** reliability、durability、history、depth と、**その設定を選んだ
  理由**を同じ表に書く。購読が成立しない条件（配信元との非互換）は実害があるため必ず残す。
- 独自 `msg` / `srv` を使う場合は、`.msg` / `.srv` を正とし、本章では解釈だけを書く。
- topic remap や namespace を前提にする場合は、既定名と変更方法を記載する。
- 時刻の扱いを明記する。`header.stamp` を使うのか受信時刻を使うのかは判定の意味が変わる。
- **画面・可視化を持つ場合は本章の節として書く**（`3.x 画面・可視化`）。Marker、RViz、
  GUI、画像出力、HTTP 表示はいずれも出力面であり、独立章にしない。表示専用の情報と
  制御に影響する入力を区別する。画面が大きい場合は別文書へ分け、ここから参照する。

## 4. 設定の所在

- **どのパラメータがどの判定に効くか、どこから設定できるかだけを書く。** 既定値の意味と
  選定理由は 7 章に置き、本章で繰り返さない。
- ROS パラメータとして外から変えられる値と、コード内の初期値で固定され変更に実装修正を
  要する値を**別の表に分ける**。後者は README にもどこにも現れないため、本章が唯一の
  記載場所になる。
- **ノード宣言の既定値と `params/*.yaml` の値が異なる場合は明記する。** `ros2 run` と
  `ros2 launch` で有効値が変わる。
- 読み込むだけで挙動に影響しないパラメータがあれば、その旨を書く。実装するか削るかは
  10 章の未決事項に挙げる。
- launch 引数、YAML、環境依存設定、モデルファイル、地図、経路 CSV などとの対応を記載する。

## 5. データモデル・内部状態

- 内部で保持する状態、dataclass、構造体、キャッシュ、履歴、FSM 状態、GUI snapshot などを
  表で整理する。**初期値・更新契機・クリア条件**の 3 列を必ず持たせる。
- 排他制御（ロックの対象と取得区間）、古いデータの扱いを明記する。
- 座標系、frame_id、時刻、単位、信頼度、ステータス値などの解釈を明記する。
- 「保持しないもの」も書く。入力の鮮度を判定しない、古い値を破棄しないといった性質は
  下流の挙動に影響する。

## 6. 処理フローと異常時の挙動

- 初期化、通常処理、callback、timer、service 処理、終了処理、再起動時復帰の流れを記載する。
- FSM を持つ場合は、状態一覧と遷移表（条件 → 結果）を書く。遷移時に publish する値、
  ログ、エラー復帰を含める。
- **入力ごとに、正常時の扱いと異常時の扱いを並べて書く。** 入力欠落、型不整合、
  ファイル不在、モデル読み込み失敗、外部プロセス失敗、タイムアウトを別章へ分けない。
- 異常時に publish を止めるのか、安全値を出すのか、直前値を保持するのかを明記する。
- 終了時に安全値を出すかを明記する。出さない場合、下流に最後の値が残る。
- `debug` / `info` / `warn` / `error` / `fatal` の使い分け、スロットル、重複抑制、
  運用時に見るべきログを記載する。実際に使っていない重要度があればそう書く。
- ノード間連携が重要な場合は、テキストシーケンスまたは表で publish / subscribe /
  service 呼び出し順を示す。

## 7. 判定ロジックと閾値

- 経路生成、追従、障害物判定、信号認識、画像処理、座標変換、速度制御などの計算手順を
  記載する。入力、出力、前提条件、丸め、フィルタ、デバウンスを明記する。
- **閾値の既定値と、その値である理由をここに 1 箇所だけ書く。** 4 章・6 章・8 章で
  値を再掲しない。
- 境界値と、境界が他の値と一致する場合の帰結を書く。2 つの閾値が従属関係にあるなら
  そう書く。
- **既知の欠陥・制約はここで説明を完結させる。** 10 章へ書くのは参照と選択肢だけとする。
- 判定が前提にしている外部の性質（発行元の配信方式、センサの更新レートなど）を書く。
  前提が崩れると判定が成立しないものは実害があるため必ず残す。
- 実装上の関数・クラス名を示す場合は、公開 API と内部実装を区別する。

## 8. 並行性・周期・起動・依存関係

- timer 周期、publish 周期、入力 timeout の**一覧**を表で示す。値の意味は 7 章にあるため
  ここでは繰り返さない。
- callback group、スレッド、ロック、キュー、GUI スレッド連携など並行性の注意点を記載する。
  単一スレッド executor で動かない構成なら、その前提と破った場合の症状を書く。
- `ros2 launch`、entry point、node name、namespace、remap、parameter file、simulator
  同時起動の扱いを記載する。
- 起動時のパラメータ検証、外部デバイス接続、モデル読み込み、初期 publish の有無を
  明記する。読み込み失敗が起動を止めるかを書く。
- `package.xml`、`setup.py`、`CMakeLists.txt`、`requirements.txt` の依存関係を整理する。
  ビルド時依存と実行時依存を区別する。
- ROS 2 Jazzy、Python、C++、外部ライブラリ、submodule、モデル形式、実機デバイスの前提を
  記載する。

## 9. 確認方法と未確認範囲

- **自動確認・手動確認・未確認範囲の 3 つに分ける。**
- 自動確認は、試験ファイルごとに「何を固定しているか」を書く。試験名の列挙はしない。
  複数箇所の値を照合している試験があれば、何と何を照合しているかを書く。
- 手動確認は観点を列挙する。単体テスト、launch/ビルド確認、異常系、境界値、状態遷移、
  パラメータ差分を含める。
- **確認していない範囲を必ず書く。** 実機、センサ、GUI、Gazebo、外部デバイスが必要で
  自動確認できない項目を明示する。これが無いと読み手に過剰な信頼を与える。
- **設計値と実測値を区別する。** 「本書の値は設計上の判断であり実測値ではない」を
  必要な箇所に書く。
- 確認方法を独立した文書に分けない。設計と一体であり、分けると片方だけが更新される。

## 10. 影響範囲・未決事項

- 既存 topic、service、msg/srv field、パラメータ、launch 引数、ファイル配置への互換性
  影響を記載する。
- downstream / upstream パッケージ、README、上位アーキテクチャ文書への影響を整理する。
  変更時に同時更新すべきものを名指しする。
- 仕様変更時は、旧仕様からの移行方法、暫定対応を記載する。
- **未決事項は 7 章への参照と選択肢だけを書く。** 事象の説明を繰り返さない。
  「7.2 節の件: A にするか B にするか。blocker ではない」の粒度にする。
- 未決事項には、誰が・何を確認すれば確定できるか、実装を止める blocker かどうかを
  可能な範囲で書く。
