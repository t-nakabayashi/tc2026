作成日: <YYYY-MM-DD>
対象コミット: <調査時点の commit hash>
決着期限: <YYYY-MM-DD>

<結論を 3 行以内で書く。読み手が全文を読まずに要否を判断できるようにする。>

---

検討資料を新規作成するときの雛形。配置と命名は `docs/notes/<YYYY-MM-DD>_<主題>.md` とする。
日付をファイル名の先頭に置く。一覧しただけで古さが分かる状態にするためである。

上のヘッダ 4 行は必須とする。以降の構成は主題に応じて自由とする。以下は目安である。

## 背景

- 何を解決しようとしているかを書く。

## 調査・分析

- 観測した事実と、そこから導いた判断を分けて書く。
- 検討の**時系列**ではなく**判断構造**を書く。「最初に A を試したが駄目だったので B に
  した」は経緯であり、書くべきは「B を採る。A は〈理由〉により要件を満たさない」である。

## 提案

- 恒久文書へどう反映するかを書く。反映先の文書名を具体的に挙げる。

## 未確認事項

- 確認していないことを書く。これが無いと読み手に過剰な信頼を与える。

---

## 扱いの規則

1. 恒久文書（規約・アーキテクチャ設計・詳細設計書・運用手順）から `docs/notes/` へ
   リンクしない。参照は検討資料 → 恒久文書の一方向のみとする。
2. 現状追従の義務を負わない。トピック名・パラメータ名・リンクの整合性検査の対象外とする。
3. 決着したら内容を恒久文書へ反映し、**このファイルを削除する。**「状態: 採用」と書いて
   残さない。判断の記録は git 履歴が持つ。
4. 決着期限を延ばす場合は期限行を書き換える。延長した事実が git diff に残る。
