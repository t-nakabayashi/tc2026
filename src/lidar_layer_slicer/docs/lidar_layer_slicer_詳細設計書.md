# lidar_layer_slicer 詳細設計書

## 1. 目的・スコープ

MID-360 の点群と topURG の `/scan` から、床面基準の水平スライス層を作り、層ごとの
観測値と AI 入力用の可視化画像を配信するノードの設計を定める。

topic 名、メッセージ型、パラメータ一覧、起動コマンドは [README](../README.md) を正とし、
本書では再掲しない。本書は取り扱いの理由と判定条件を定める。

責務は、(1) 点群を床上高さで切り出すこと、(2) 層ごとに車体が横へ寄れる量を算出すること、
(3) 層を同一スケールで並べた画像を作ることの 3 つである。層を停止判定に使わない理由を
含む全体の責務分担は[AI助言による障害物回避](../../../docs/AI助言による障害物回避.md)を
正とする。

非スコープを次に示す。

- 前方閉塞の判定（停止判定）は `obstacle_monitor` が `/scan` のみから行う。本ノードは
  `front_blocked` に相当する値を持たない。
- 回避方向と回避量の決定は `route_follower` が行う。本ノードは上限の根拠となる観測値を
  出すだけで、どちらへ避けるかを決めない。
- 障害物の種類の判定は行わない。層の形状から種類を推定する処理を持たない。

実装は pytest による単体確認のみを行っている。実機センサ、Gazebo、実際の取付姿勢での
動作は確認していない（9 章）。

## 2. 構成とファイル配置

| ファイル | 役割 | 配置理由 |
| --- | --- | --- |
| `lidar_layer_slicer/layer_core.py` | 層の切り出し、横移動余裕、観測可能高さの計算 | ROS 非依存。幾何計算は単体で固定したい |
| `lidar_layer_slicer/layer_render_core.py` | 層の描画と横並び合成 | ROS 非依存。画像仕様を単体で固定したい |
| `lidar_layer_slicer/lidar_layer_slicer_node.py` | 購読、TF 変換、累積、配信 | ROS 入出力に限定する |
| `params/default.yaml` | 層定義と判定条件の既定値 | 現地調整で層の高さを変えるため |
| `launch/lidar_layer_slicer.launch.py` | 単体起動 | 実機と模擬で入力 topic を切り替える |

幾何計算と描画を ROS 非依存に保つのは、bag からの再現と模擬環境での評価を、ROS グラフを
立てずに実行できるようにするためである。

## 3. 外部インタフェース仕様

### 3.1 QoS

| 対象 | 設定 | 理由 |
| --- | --- | --- |
| `/scan`、点群入力の購読 | SensorDataQoS | 配信元が外部パッケージであり、購読側が合わせる |
| 層の観測値の配信 | BEST_EFFORT / VOLATILE / depth 1 | `stream` 様式の既定（[トピック通信規約](../../../docs/トピック通信規約.md) 4 章） |
| 可視化画像の配信 | RELIABLE / VOLATILE / depth 1 | `rqt_image_view` などが RELIABLE を要求する。既定からの例外 |

### 3.2 時刻と座標系

`header.stamp` は配信時刻を入れる。累積した点群の各フレームの観測時刻ではないため、
どの時刻の観測かを厳密に扱う用途には使えない。累積の時間幅は `accumulated_span_s` が
持つ。`frame_id` は `base_link` とし、x 前方・y 左・z 上とする。

層の高さは床面基準で指定する。点群は `base_link` 系へ変換してから
`floor_to_base_link_m` を足して床上高さへ直す。パラメータを床面基準にしたのは、
障害物の寸法（縁石、車止め、コーン）が床からの高さで表されるためである。

### 3.3 画面・可視化

可視化画像は AI 入力を主目的とし、人間の目視用の `obstacle_monitor` の `sensor_viewer`
とは別に作る。共通する方針は、実距離に比例した画素配置、下端中心をセンサ位置とする原点、
白背景に赤点である。本ノードが加えるのは次の 4 点である。

- 1 m ごとのグリッド線と距離の数値ラベル。画像から距離を推定させないために置く。
- 車体矩形（車体全幅）と進行方向の矢印。原点と向きを画像単体で判別できるようにする。
- 直進時に車体が占有する帯（車体幅＋左右余裕）の境界線と、評価した前方距離の線。
- 層ごとの見出し（層名、高さ、厚さ、生成元、点数）。

縮小は行わない。層は同一スケール・同一原点で横へ並べ、間に区切り線を入れる。
画像内の文字は OpenCV の既定フォントで描くため ASCII に限る。日本語の説明が必要な値は
画像ではなく構造化テキスト（`layer_context_lines`）で渡す。

## 4. 設定の所在

ROS パラメータは README 5 章の表と `params/default.yaml` を正とする。既定値の選定理由は
7 章に置く。本章は対応関係のみを示す。

| パラメータ | 効く判定 |
| --- | --- |
| `cloud_layer_names` / `cloud_layer_heights_m` / `cloud_layer_thickness_m` | 層の切り出し（7.1） |
| `floor_to_base_link_m` | 床上高さへの変換（7.1） |
| `forward_range_m` / `robot_width_m` / `side_margin_m` / `near_x_m` / `max_offset_m` | 横移動余裕（7.2） |
| `accumulate_frames` / `accumulate_window_sec` | 点群の累積（7.3） |
| `view_range_x_m` / `view_range_y_m` / `view_pixel_pitch` | 画像の範囲と解像度（3.3） |
| `scan_half_fov_deg` | scan 層に残す前方範囲（7.1） |
| `base_frame` / `cloud_message_type` / `publish_rate_hz` | 入出力の構成（8 章） |

コード内で固定し、変更に実装修正を要する値を次に示す。

| 値 | 内容 |
| --- | --- |
| scan 層の厚さ | 0.0 とする。2D scan は単一平面であり厚さの概念を持たない |
| 画像の配色 | 背景白、点赤、グリッド灰、帯と距離線はオレンジ、車体黒 |
| 車体矩形の描画長さ | 前方 0.3 m。車体の実寸ではなく原点を示す目印である |

`scan_layer_height_m` は記録と画像の見出しに使う値であり、`/scan` から点を切り出す
条件には使わない。2D scan は取付高さの平面そのものだからである。

## 5. データモデル・内部状態

| 状態 | 初期値 | 更新契機 | クリア条件 |
| --- | --- | --- | --- |
| 最新 scan | なし | `/scan` 受信 | クリアしない（上書きのみ） |
| 点群フレーム列 | 空 | 点群受信時に `base_link` 系へ変換して追加 | `accumulate_frames` 超過、または配信時に `accumulate_window_sec` を過ぎたフレームを捨てる |
| TF 警告済みフラグ | false | TF 取得失敗時に true、成功時に false | ノード再起動 |

保持しないものを次に示す。

- 入力の鮮度を判定しない。最新 scan は上書きのみで、途絶しても直前値を使い続ける。
  購読側は `header.stamp` と配信レートから鮮度を判断する必要がある。
- 自己運動による累積点の補正を行わない。走行中は累積した点が流れる（7.3）。
- 層ごとの時系列を持たない。層の観測値はフレームごとに独立して算出する。

## 6. 処理フローと異常時の挙動

初期化でパラメータを読み、TF listener と購読・配信を作り、`publish_rate_hz` の timer を
開始する。timer ごとに、scan 層と点群層を作り、観測値と画像を配信する。

入力ごとの扱いを次に示す。

| 入力 | 正常時 | 異常時 |
| --- | --- | --- |
| `/scan` | 前方 `scan_half_fov_deg` の範囲を xy へ変換する | 未受信なら scan 層を点数 0 とする。配信は止めない |
| 点群 | `base_link` へ変換して累積する | 空フレームは捨てる。TF 取得失敗時は累積せず、警告を 1 度だけ出す |
| 点群の型 | `cloud_message_type` に従って購読する | `custom` 指定で livox のメッセージを取り込めない場合、警告して `points` を購読する |
| 層定義 | 名前・高さ・厚さを同じ並び順で読む | 個数が一致しない場合は error を出し、点群層を作らず scan 層のみとする |

異常時も配信は止めない。層を作れない場合は点数 0 の層として配信し、「観測できていない」
ことを購読側が検出できる状態を保つ。配信を止めるとノード停止と区別できなくなる。
終了時に安全値は出さない。本ノードの出力は観測値であり、制御指令ではない。

ログは、起動時の層定義を `info`、TF 取得失敗と入力型の切り替えを `warn`、層定義の
個数不一致を `error` とする。TF 取得失敗の警告は、復旧するまで 1 度だけ出す。
`debug` と `fatal` は使っていない。

## 7. 判定ロジックと閾値

### 7.1 層の切り出し

点群は `base_link` 系へ変換したうえで、各点の床上高さ `z + floor_to_base_link_m` を求め、
層の中心高さとの差が厚さの半分以下なら、その層に含める。

既定の層は床上 0.25 m（topURG）、0.35 m、0.50 m である。この 3 つを選んだ理由は次のとおり。

- MID-360 は床上 0.562 m に前下がり 26.9° で取り付ける。仰角 -7°〜+52° が回転して
  車体基準で -33.9°〜+25.1° になり、距離 d で観測できる床上高さは
  `0.562 - 0.672d` 〜 `0.562 + 0.468d` [m] である。
- 0.35 m の層は 0.32 m 以遠、0.50 m の層は 0.09 m 以遠から観測できる。停止判定が起きる
  0.75 m より手前から観測できるため、近傍の障害物が層に現れる。
- 水平取付（前下がり 0°）では 0.35 m の層は 1.7 m 以遠まで観測できない。層の高さの
  選定は取付角に依存する。取付を変えた場合は層の高さを選び直す必要がある。
- 0.25 m と 0.50 m の間を埋める位置に 0.35 m を置き、車止めの下部・縁石・コーンの底部と、
  コーン本体・草・ポール・ロボットの車体を別の層で見る。
- 人の胴体（床上 1.1〜1.2 m）は 1.4 m 以遠でしか観測できないため、層では扱わない。
  近傍での人とロボットの識別はカメラ画像の役割とする。

厚さの既定 0.10 m は、MID-360 が非回転の疎なスキャンであり、薄い層では単一フレームに
乗る点が少ないことへの対処である。厚くすると点は増えるが、高さ分解能は落ちる。

`/scan` は取付高さの平面そのものであるため、高さによる切り出しを行わず、前方
`scan_half_fov_deg`（既定 90°）の範囲だけを残す。後方の点は回避の判断に使わない。

### 7.2 横移動余裕

車体が横へ `s` [m] 寄ったとき、車体は `[s - w/2 - m, s + w/2 + m]` の帯を占有する
（`w` は車体全幅、`m` は左右余裕）。前方帯（`near_x_m` < x ≦ `forward_range_m`）にある
各点は、その点を含む占有帯を作る `s` の範囲を塞ぐ。塞がれていない `s` の区間を空き区間と
呼び、`±max_offset_m` の範囲で求める。

空き区間から左右それぞれ 2 つの値を出す。

- `required`: 横移動量 0 に最も近い空き区間の、0 に近い側の端。0 が空き区間に含まれる
  場合は 0 となり、現在位置のまま通行できることを表す。空き区間が無い側は inf とする。
- `available`: その空き区間の遠い側の端。回避幅の上限に使う。`required` が inf の側は
  0 とする。

既定値は車体全幅 0.6 m、左右余裕 0.1 m、前方 2.0 m、横移動量の上限 3.0 m、
評価から除外する近距離 0.15 m である。車体全幅は `obstacle_monitor` の `robot_width_m`
と同じ値を既定にしている。左右余裕 0.1 m は車体幅に対する片側の余裕であり、実測から
得た値ではない。前方 2.0 m は `obstacle_monitor` の `max_obstacle_distance_m`（1.5 m）
より長く、回避の横移動が完了するまでの区間を含める意図で選んだ。横移動量の上限 3.0 m は
`obstacle_monitor` の上限と揃えている。

`nearest_x_m` は直進帯で最も近い点の距離であり、`forward_range_m` の上限を適用しない。
回避幅の制限には遠方の点を使わないが、状況説明からは落とさないためである。

全層に共通して使える幅は、点数が 1 点以上ある層の `available` の最小値とする。点数 0 の
層を「空いている」として扱うと、観測できていない高さの障害物へ向かって幅を広げることに
なる。逆に 0 として扱うと、観測距離に達していない層のせいで回避できなくなる。そのため
点数 0 の層は判定から外す。全層が点数 0 の場合は 0 とする。

### 7.3 累積

点群は `accumulate_frames`（既定 3 枚）まで保持し、配信時に `accumulate_window_sec`
（既定 1.0 秒）を過ぎたフレームを捨てる。MID-360 は 10 Hz であり、既定は約 0.3 秒分に
相当する。

自己運動の補正は行わない。停止中に助言を求める運用を前提としているためである。
走行中は累積した点が進行方向へ流れ、層の点が実際より手前・広がった位置に現れる。
`accumulated_frames` と `accumulated_span_s` を配信しているため、購読側はどれだけの
時間幅を束ねた結果かを判断できる。

### 7.4 既知の制約

- 層の点数 0 は未観測であり、障害物が無いことを意味しない。TF 未取得、入力途絶、
  観測範囲外のいずれでも 0 になる。これらを区別する値は持たない。
- 空き区間は点の有無だけで決まる。地面、草、段差、未観測領域を区別しない。地面が層に
  入る高さを選ぶと、全面が塞がれた判定になる。
- 層が水平であることは、ロボットが水平であることを前提とする。坂やピッチングでは
  層の高さが路面に対してずれる。姿勢による補正は行っていない。
- `required` と `available` は点の分布だけから求めた幾何量であり、通行できることを
  保証しない。経路境界、路面の支持、段差は判定に含まれない。

## 8. 並行性・周期・起動・依存関係

| 項目 | 値 |
| --- | --- |
| timer 周期 | `publish_rate_hz`（既定 10.0 Hz） |
| 層観測値・画像の配信周期 | timer と同じ |
| 入力 timeout | 持たない（7.4） |

単一スレッドの executor で動作する。購読 callback は入力の保存と座標変換のみを行い、
層の生成と描画は timer で行う。ロックは持たない。入力レートが timer より高い場合、
配信に使われないフレームが出る。

entry point は `lidar_layer_slicer`、node name は `lidar_layer_slicer` である。
入力 topic は remap で切り替える。起動時にパラメータの検証は行わず、層定義の個数不一致
のみを実行時に検出する。TF の取得失敗は起動を止めない。

依存はビルド時・実行時ともに `rclpy`、`sensor_msgs`、`sensor_msgs_py`、`cv_bridge`、
`tf2_ros`、`tc_perception_msgs`、`tc_diagnostics` である。`numpy` と `opencv` は実行時に
必要であり、`requirements.txt` ではなく apt 由来の `python3-numpy` / `python3-opencv` を
`package.xml` の実行時依存として宣言している。`livox_ros_driver2` は実機構成でのみ
必要であり、取り込めない環境では `PointCloud2` の購読へ切り替わるため依存に含めない。

## 9. 確認方法と未確認範囲

### 自動確認

`tests/test_layer_core.py` は次を固定している。

- 床上高さと厚さによる切り出しが、base_link の z に `floor_to_base_link_m` を足した
  高さで判定されること。
- 点が無い層で `required` が 0、`available` が上限になること、および点数 0 が
  未観測を意味すること。
- 正面の点に対する `required` が車体占有半幅と一致すること。
- 壁がある側だけ `available` が制限され、反対側が影響を受けないこと。
- 通れる幅が無い場合に `required` が inf、`available` が 0 になること。
- `forward_range_m` より遠い点が横移動量を塞がず、`nearest_x_m` には現れること。
- 点数 0 の層が共通の使用可能幅の算出から外れること。
- 取付角と層の高さの関係（26.9° では 0.35 m の層が 0.32 m 以遠、水平取付では 1.7 m
  以遠でしか観測できないこと）。これは幾何計算と 7.1 節の設計値を照合している。

`tests/test_layer_render.py` は、原点が描画領域の下端中心であること、x 前方が上・
y 左が画像左へ距離に比例して写ること、点が実距離の位置へ赤で描かれること、範囲外の点が
描画されないこと、複数層が同一スケールで横へ並ぶことを固定している。

### 手動確認

- `/obstacle/layers` の層ごとの値が、既知の配置（コーン、壁）と整合すること。
- `/obstacle/layer_view` を `rqt_image_view` で見て、層の対応と距離が読めること。
- 入力 topic の remap と `cloud_message_type` の切り替えで起動すること。

### 未確認範囲

- 実機の MID-360 での点の分布、層に乗る点数、累積枚数の妥当性。
- 実際の取付姿勢（roll -0.6°、pitch 26.9°）の TF を使った切り出し結果。
- Gazebo 模擬構成での動作。模擬のロボットモデルは MID-360 を床上 1.005 m の水平取付と
  しており、本ノードが前提とする取付と異なる。
- 走行中の累積点のずれの大きさ。
- 層の高さ 0.35 m / 0.50 m、厚さ 0.10 m、左右余裕 0.1 m が実環境で妥当かどうか。
  いずれも幾何計算と対象物の寸法からの設計値であり、実測値ではない。

## 10. 影響範囲・未決事項

- `tc_perception_msgs` に `ObstacleLayer` / `ObstacleLayers` を追加した。同パッケージの
  README の一覧と合わせて更新する。
- `obstacle_monitor` の挙動は変更していない。前方閉塞判定の分担を変える場合は、
  同パッケージの詳細設計書と本書 1 章を同時に更新する。
- 層の観測値を回避幅の上限に使う側（`route_follower`）は、点数 0 の層の扱いを 7.2 節と
  揃える必要がある。
- 7.1 節の件: 層の高さ 0.35 m / 0.50 m を実機の点群で見直すか、現状の設計値で進めるか。
  実機の bag で層の点数を数えれば確定できる。blocker ではない。
- 7.3 節の件: 走行中も使うなら自己運動補正を入れるか、停止中限定の用途に留めるか。
  現状は停止中限定で足りるため未実装とする。blocker ではない。
