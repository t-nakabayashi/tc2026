# route_survey 詳細設計書

## 1. 目的・スコープ

本書は `route_survey` パッケージの内部設計を定める。手動走行中の共通自己位置
（ICP／GNSS融合）からwaypointを採取し、観測点群から回避幅の候補を保存する。

トピック名、型、パラメータの一覧と起動方法は [README](../README.md) を正とする。
本書は**採取条件、路面観測と幅推定の判定、保存の規則、観測の限界**を定める。

**速度指令は発行しない。** 走行・手動介入はdrive_mode_manager、位置推定はgnss_lio_fusionが
担当する。**採取ボタンは車体停止操作ではない。**

関連文書は次のとおりである。

| 文書 | 内容 |
| --- | --- |
| [局所空間参照サンプル](空き空間参照サンプル.md) | オフライン評価用のサンプル |
| [閾値評価](路面閾値の比較ツール.md) | 路面閾値の比較ツール |

**いずれもオフライン評価用であり、走行時の進路生成には接続されていない。**

記載内容はすべて実装済みである。実機の全センサ・GUI・bag記録との同時稼働、新しい現地
ルートの採取は未確認である（9.3節）。

## 3. 外部インタフェース仕様

一覧は [README](../README.md) を正とする。本章はQoSの選定理由と取り扱いを定める。

### 3.1 QoS

| 対象 | 設定 | 選定理由 |
| --- | --- | --- |
| 位置・odom・状態 | depth 10 | — |
| 点群・Joy・NavSatFix | sensor_data QoS（BEST_EFFORT） | センサ入力の標準プロファイル |

### 3.2 トピック

| トピック | 型 | 用途 |
| --- | --- | --- |
| `/localization/pose_enu` | PoseWithCovarianceStamped | 採取する車軸位置・yaw |
| `/lio/odometry` | Odometry | 水平化済みLIO、点群蓄積・車体姿勢 |
| `/cloud_registered_body` | PointCloud2 | IMU/body座標の点群 |
| `/joy` | Joy | ボタン0/1/2/3で開始・停止属性・信号停止属性・終了 |
| `/route_survey/command` | String | start、finish、line_stop、signal_stop |
| GNSS fix/status、`/fusion/status` | NavSatFix、RtkStatus、String | 比較軌跡と品質 |
| `/route_survey/status` | String | 保存後の状態、点数、幅、保存先・結果・エラー |

GNSSトピックの単体既定値は `/rtk_gps/fix`、`/rtk_gps/rtk_status` である。共通実機起動は
実機のgnss_namespaceに合わせる。

### 3.3 画面・可視化

表示用点群は共通自己位置でmapへ配置し、**15 m以内・0.15 mボクセル・最大10万点**を保持する。
**幅判定用の短時間蓄積とは別データである。**

編集画面では点の選択・追加・削除・移動、方位、左右幅、停止・スキップ属性、undo/redo、
CSV/JSON/PNG保存を行える。**位置等を編集すると要確認に戻る。確認済み操作は利用者による
確認であり、自動検証ではない。**

GNSS／自己位置推定軌跡を切り替え、時刻ごとの品質も参照できる。
**編集結果を走行中の経路へ自動適用せず、停止後にCSVと投影設定を読み直す。**

`build_editor.py --map-points` の入力も同じ投影原点のmap座標である必要がある。

HTMLはオフラインで動作する。**PC内ファイルはiPhone向け共有URLではない。** 遠隔閲覧には
会話内画像・本文または指定された共有先を使用する。

操作画面での採取状態の表示は `robot_console` が `/route_survey/status` を購読して行う。

## 4. 設定の所在

一覧は [README](../README.md) を正とする。

**`output_directory` と `projection_config` は必須である。** 主要な調整項目は
`spacing_m`、`turn_deg`、`surface_window_s`、`surface_margin_m`、
`surface_max_seed_intensity` である。

単独設定の `lidar_height_m=0.6` は水平取付の既定値である。実機では
[hardware.yamlから生成したrecorder.yaml](../../icart_bringup/docs/実機ハードウェア統合.md)を
使う。

採取条件・路面観測・幅判定の閾値のうちパラメータを持たないものがある。値と理由は7章に置く。

## 5. データモデル・内部状態

| 状態 | 寿命・上限 |
| --- | --- |
| 幅判定用の点群蓄積（LIO座標） | 既定6秒、重複点除去は2.5 cmボクセル |
| 表示用点群（map座標） | 15 m以内・0.15 mボクセル・最大10万点 |
| GNSS軌跡・融合軌跡 | 各約5 Hz・最大10万件。上限超過時は古い観測を落とす |
| 採取済みwaypoint | 上限なし |

**蓄積を破棄する契機は、時刻逆行・1秒超の断絶・位置跳躍・水平基準の再確定である。**

軌跡は**採取開始前・終了後を含むノード稼働中の履歴**を持つ。

## 6. 処理フローと異常時の挙動

### 6.1 採取の流れ

1. `/localization/pose_enu` を受けて車軸位置・yawを保持する。
2. `/cloud_registered_body` を取付角・レバーアームで補正し、水平化済みLIOの世界座標へ配置
   する。
3. 採取条件（7.1節）を満たした時点でwaypointを追加する。
4. 路面観測から左右幅の候補を求める（7.2〜7.4節）。
5. 1秒ごとにスナップショットを保存ワーカーへ渡す（7.5節）。
6. 終了操作で最終保存を行う。

### 6.2 操作の受け付け

| 操作 | 条件 |
| --- | --- |
| 開始・停止属性・信号停止属性 | **位置が0.5秒以上古い間は受け付けない** |
| 終了 | **位置途絶中も受け付ける。** 古い位置から終点を作らず保存を完了する |

Joyのボタン0/1/2/3と `/route_survey/command` の文字列の両方で操作できる。

### 6.3 異常時の挙動

| 事象 | 挙動 |
| --- | --- |
| 非有限値・時刻逆行・1秒を超える入力断・位置跳躍 | **拒否する**（7.1節） |
| 入力断からの復帰 | `input_gap`・幅0・要確認として残す |
| 位置分散が閾値超過 | **採取を継続するが、自動幅は0とする** |
| ICP照合不良・状態欠測 | 軌跡の該当点を `uncertain=true` とする |
| 保存失敗 | UIへ通知し、「終了・保存」で再試行できる |
| ノード終了 | 最終保存を待つ |

**終了時の書込み成功まで保存完了と表示しない。**

### 6.4 ログと状態通知

`/route_survey/status` に保存後の状態、点数、幅、保存先・結果・エラーを出す。異常の通知は
主にこのトピックで行う。

## 7. 判定ロジックと閾値

### 7.1 採取条件

waypointを保存する契機は次のとおりである。

| 契機 | 条件 |
| --- | --- |
| 距離 | 通常**5 m**ごと |
| 曲がり角 | **25°以上**の方位変化かつ**1 m以上**の移動 |
| 停止属性操作 | 操作時 |
| 終了 | 終了時 |

移動距離は**0.2 m以上**離れた観測を積算し、**0.3 m以内**の重複位置は統合する。

**停止・信号停止属性は両方保持できる。** 方位は採取時の車体方位で、編集画面から変更できる。

拒否する入力は、非有限値・時刻逆行・**1秒**を超える入力断・**2 m/sに0.1 mの余裕を加えた**
位置跳躍である。

位置分散が**0.25 m²**を超えても採取を継続するが、**自動幅は0とする。**

### 7.2 路面観測の採用条件

**通行幅の蓄積にはGNSSの絶対位置補正を使わない。** LIO座標で蓄積する。

位置・姿勢と点群の時刻差が**0.15秒以内**の場合に採用し、**約5 Hz**で計算する。

### 7.3 基準平面の推定

| 項目 | 範囲・閾値 |
| --- | --- |
| 候補の範囲 | 前後 −0.6〜3 m、左右±0.35 m、高さ −0.4〜0.15 m |
| 反射強度の候補 | 既定**30以下** |
| 必要点数 | **20点以上** |
| 不成立の条件 | 勾配**15°超**、推定粗さ**2.5 cm超**など |

外れ値除去を繰り返す最小二乗平面を使う。**車軸のz=0を地面と仮定しない。**

### 7.4 幅判定

前後±0.6 mを**0.4 mずつ3パッチ**、左右を**0.2 mの帯**に分け、**左右各最大3 m**まで調べる。

| 項目 | 閾値 |
| --- | --- |
| 各パッチの必要点数 | **3点以上** |
| 段差の基準 | **6 cm**（点群の推定ノイズを加味する） |
| 反射強度の拒否閾値 | `max(30, 基準面の強度中央値×2.5)` |

拡張を止める条件は、未観測・段差／下り・粗面／障害物・材質変化・勾配超過である。

**強度は拡張を拒否する補助情報であり、アスファルトや芝生の意味分類ではない。**

連続観測した幅から `surface_margin_m`（既定0.35 m）を引いた値をleft/rightへ保存する。
**左右とも中央の通過範囲を観測できなければ両方0とする。**

**保存値は車体中心が横へ動ける余裕の候補であり、歩道そのものの全幅ではない。** 人・コーン等
が写った観測の影響を除去した恒久的な歩道形状も、現行処理では推定しない。
`review_required` は自動解除しない。

**2D URGはこの幅推定の根拠には使わず、走行時の障害物監視を担当する。** 平坦で反射強度の
近い芝生、濡れ・塗装・遮蔽は幾何と強度だけで識別できない場合がある。

### 7.5 保存の規則

`fixed/waypoints.csv`、`route_config.yaml`、`projection.yaml`、`survey.json` を保存する。

CSVは[route_planner仕様](../../route_planner/README.md)に従い、**LLH正本・高度空欄**と
する。`heading_deg` は真北0°・時計回りで、map回転を反映する。

**各ファイルは一時ファイルから置換するが、複数ファイルをまたぐトランザクションではない。**
出力先は**新規ディレクトリのみ**受け付ける。

1秒ごとにスナップショットを**単一の保存ワーカー**へ渡し、ディスク待ちを受信処理から分離
する。**保存中の再要求は1件にまとめ、次回に最新状態を渡す。**

### 7.6 比較軌跡の構成

`survey.json` の `traces.gnss` / `fused` は**独立した観測履歴**である。`traces.source` は
方式、`fused` 内の各点には `source` と同時刻の状態 `mode` を保存する。

ICPモードは `icp_map_manifest` も記録する。

GNSS品質は保存時に**±0.25秒以内**の最寄りRtkStatusと対応づけ、不一致は不明とする。

**GNSS軌跡はアンテナの生位置で、自己位置推定との位置差には取付位置・時刻差も含まれる。**
履歴がないJSONを読み込んでも観測を補完しない。

## 8. 並行性・周期・起動・依存関係

### 8.1 周期

| 項目 | 値 |
| --- | --- |
| 幅推定の計算 | 約5 Hz |
| 軌跡の記録 | 各約5 Hz |
| 保存スナップショットの受け渡し | 1秒 |

### 8.2 並行性

保存は**単一の保存ワーカー**で行い、ディスク待ちを受信処理から分離する（7.5節）。
受信処理が保存で塞がらないようにするためである。

### 8.3 起動

[README](../README.md)の単独 `record.launch` は起動済みセンサと位置推定を購読する。

`icart_bringup` の `survey.launch` はsessionで選択された自己位置推定・手動操縦・UIを含めて
起動し、**自律復帰を無効にする**（`drive_mode_manager` の `allow_auto_resume=false`）。

実機domainは0、模擬は86とする。**Joyの二重配信を避ける。**

### 8.4 依存関係

採取ノードはROSに依存し、4つのcoreモジュールは標準ライブラリとNumPyで動く。
編集画面はオフラインのHTMLである。

## 9. 確認方法と未確認範囲

### 9.1 自動確認

`tests/` では次を確認する。

| 対象 | 確認する内容 |
| --- | --- |
| 採取条件 | 距離・曲がり角・属性・欠落復帰・時刻・保存 |
| 路面観測 | 段差・粗面・材質・未観測 |
| ICP入力 | ICP入力だけでの採取、GNSS比較軌跡との分離 |
| 取付変換 | 取付変換を一度だけ適用した点群の姿勢・高さ |
| 品質記録 | 照合不良時の品質記録 |
| 保存 | 保存遅延中の受信継続、保存完了・エラー・再試行 |

### 9.2 実施済みの負荷確認

通常版のインストール済みノードを、ネットワーク・デバイスを分離したdomain 193で確認した。

1,000ウェイポイント、表示点群10万点、GNSS／ICP各18,000点の履歴を保持してメディアへ保存し、
別ROSプロセスから10 Hzで送信した位置120点をすべて受信、棄却0点、終了時の保存成功を確認した。
受信遅延は平均11.2 ms、95%点66.8 ms、最大105.4 ms。

**試験時間は約16秒で、1時間走行を実時間再生した試験ではなく、長時間分のデータ量による保存
負荷試験である。** 通常GUIのICP／GNSS選択と起動引数、生成sessionの地図原点一致も確認して
いる。原本は測定時のメディア上の `verification.json` である。

`tools/evaluate_gnss_loss.py` は融合と採取へ模擬GNSS/LIOを入力する結合確認に使う。

### 9.3 未確認範囲

- **実機の全センサ・GUI・bag記録との同時稼働、新しい現地ルートの採取は未確認である。**
- **模擬入力の成立と、実機での検出精度・長時間ドリフトは区別する。**
- **地面の観測だけで前方の歩道通行性を保証しない。** 保存経路・幅・停止属性は現地確認する。
- 幅推定の閾値（7.3節、7.4節）が実路面の材質分布に対して適切かを確認していない。
- 平坦で反射強度の近い芝生、濡れ・塗装・遮蔽の識別は幾何と強度だけでは成立しない場合が
  ある（7.4節）。
- 1時間規模の連続走行での軌跡上限（5章）到達時の挙動を実走で確認していない。

## 10. 影響範囲・未決事項

### 10.1 影響範囲

出力するCSVの列仕様は `route_planner` のparserに従う。列を変える場合は `route_planner` と
`obstacle_route_sim` のwaypoint生成を併せて更新する。

`projection.yaml` の投影原点は `geo_pose_converter` の設定と一致している必要がある。
**採取時と走行時の原点が異なると、保存した経路が別の場所を指す。**

`/route_survey/status` のJSONの形は `robot_console` のルート記録タブが前提にする。

`survey.json` の `traces` 構造は編集画面と評価ツールが読む。

### 10.2 未決事項

| 件 | 選択肢 | blocker |
| --- | --- | --- |
| 7.5節: 複数ファイルをまたぐトランザクションでない | 全ファイルの一括置換を実装する／現状を維持し保存完了の判定を終了時に限る（現状） | ではない |
| 7.4節: 幅の保存値が通行幅の保証ではない | 恒久的な歩道形状の推定を実装する／候補として扱い現地確認を前提とする（現状） | ではない |
| 5章: 採取済みwaypointに上限がない | 上限を設ける／現状を維持する | ではない |
| 1章: 評価ツールが走行時の進路生成へ接続されていない | 接続する／オフライン評価に留める（現状） | ではない |
