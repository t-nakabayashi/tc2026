# 経路採取・編集の設計と確認方法

## 1. 役割と構成

手動走行中の共通自己位置（ICP／GNSS融合）からwaypointを採取し、観測点群から回避幅の候補を保存する。
速度指令は発行しない。走行・手動介入はdrive_mode_manager、位置推定はgnss_lio_fusionが担当する。

| 実装 | 責務 |
| --- | --- |
| survey_core.py | 採取間隔、曲がり角、停止属性、位置の妥当性 |
| surface_core.py | LIO座標での短時間蓄積、局所平面・材質による幅推定 |
| storage_core.py | CSV・JSON・投影設定の保存 |
| recorder_node.py | ROS入出力、取付補正、点群処理、比較軌跡 |
| web/editor.html、tools/build_editor.py | オフライン編集画面と埋込みデータ生成 |

## 2. 入出力

| トピック | 型 | 用途 |
| --- | --- | --- |
| `/localization/pose_enu` | PoseWithCovarianceStamped | 採取する車軸位置・yaw |
| `/lio/odometry` | Odometry | 水平化済みLIO、点群蓄積・車体姿勢 |
| `/cloud_registered_body` | PointCloud2 | IMU/body座標の点群 |
| `/joy` | Joy | ボタン0/1/2/3で開始・停止属性・信号停止属性・終了 |
| `/route_survey/command` | String | start、finish、line_stop、signal_stop |
| GNSS fix/status、`/fusion/status` | NavSatFix、RtkStatus、String | 比較軌跡と品質 |
| `/route_survey/status` | String | 保存後の状態、点数、幅、保存先・結果・エラー |

位置・odom・状態はdepth 10、点群・Joy・NavSatFixはsensor_data QoSを使う。
GNSSトピックの単体既定値は `/rtk_gps/fix`、`/rtk_gps/rtk_status`。
共通実機起動は実機のgnss_namespaceに合わせる。

## 3. 採取条件

通常5 mごと、25°以上の方位変化かつ1 m以上の移動、停止属性操作、終了時に点を保存する。
移動距離は0.2 m以上離れた観測を積算し、0.3 m以内の重複位置は統合する。
停止・信号停止属性は両方保持できる。方位は採取時の車体方位で、編集画面から変更できる。

非有限値・時刻逆行・1秒を超える入力断・2 m/sに0.1 mの余裕を加えた位置跳躍を拒否する。
入力断からの復帰はinput_gap・幅0・要確認として残す。
位置分散が0.25 m²を超えても採取を継続するが、自動幅は0とする。
位置が0.5秒以上古い間は開始・属性操作を受け付けない。
終了だけは位置途絶中も受け付け、古い位置から終点を作らず保存を完了する。

## 4. 路面観測と幅推定

取付角・レバーアームを適用し、body点群を水平化済みLIOの世界座標へ配置する。
通行幅の蓄積にはGNSSの絶対位置補正を使わない。
位置・姿勢と点群の時刻差が0.15秒以内の場合に採用し、約5 Hzで計算する。
既定の保持時間は6秒、重複点除去は2.5 cmボクセル。
時刻逆行・1秒超の断絶・位置跳躍・水平基準の再確定で蓄積を破棄する。

基準平面は前後 −0.6〜3 m、左右±0.35 m、高さ −0.4〜0.15 mの候補から求める。
反射強度がある場合は既定30以下を候補とし、20点以上を要求する。
外れ値除去を繰り返す最小二乗平面を使い、勾配15°超・推定粗さ2.5 cm超などでは基準を不成立とする。
車軸のz=0を地面と仮定しない。

幅判定は前後±0.6 mを0.4 mずつ3パッチ、左右を0.2 mの帯に分け、左右各最大3 mまで調べる。
各パッチ3点以上を要求し、未観測・段差／下り・粗面／障害物・材質変化・勾配超過で拡張を止める。
段差の基準は6 cmで、点群の推定ノイズを加味する。
反射強度の拒否閾値は `max(30, 基準面の強度中央値×2.5)`。
強度は拡張を拒否する補助情報であり、アスファルトや芝生の意味分類ではない。

連続観測した幅から `surface_margin_m=0.35` mを引いた値をleft/rightへ保存する。
左右とも中央の通過範囲を観測できなければ両方0とする。
保存値は**車体中心が横へ動ける余裕の候補**であり、歩道そのものの全幅ではない。
人・コーン等が写った観測の影響を除去した恒久的な歩道形状も、現行処理では推定しない。
`review_required` は自動解除しない。

2D URGはこの幅推定の根拠には使わず、走行時の障害物監視を担当する。
平坦で反射強度の近い芝生、濡れ・塗装・遮蔽は幾何と強度だけで識別できない場合がある。

## 5. 保存と比較軌跡

fixed/waypoints.csv、route_config.yaml、projection.yaml、survey.jsonを保存する。
CSVは[route_planner仕様](../../route_planner/README.md)に従い、LLH正本・高度空欄とする。
heading_degは真北0°・時計回りで、map回転を反映する。
各ファイルは一時ファイルから置換するが、複数ファイルをまたぐトランザクションではない。
出力先は新規ディレクトリのみ受け付ける。
1秒ごとにスナップショットを単一の保存ワーカーへ渡し、ディスク待ちを受信処理から分離する。
保存中の再要求は1件にまとめ、次回に最新状態を渡す。終了時の書込み成功まで保存完了と表示しない。
保存失敗はUIへ通知し、「終了・保存」で再試行できる。ノード終了時は最終保存を待つ。

survey.jsonのtraces.gnss/fusedは独立した観測履歴で、各約5 Hz・最大10万件。
`traces.source` は方式、`fused` 内の各点には `source` と同時刻の状態 `mode` を保存する。
ICPモードは `icp_map_manifest` も記録し、照合不良・状態欠測時は `uncertain=true` とする。
採取開始前・終了後を含むノード稼働中の履歴を持ち、上限超過時は古い観測を落とす。
GNSS品質は保存時に±0.25秒以内の最寄りRtkStatusと対応づけ、不一致は不明とする。
GNSS軌跡はアンテナの生位置で、自己位置推定との位置差には取付位置・時刻差も含まれる。
履歴がないJSONを読み込んでも観測を補完しない。

## 6. 表示用地図と編集

表示用点群は共通自己位置でmapへ配置し、15 m以内・0.15 mボクセル・最大10万点を保持する。
幅判定用の短時間蓄積とは別データである。
`build_editor.py --map-points` の入力も同じ投影原点のmap座標である必要がある。

編集画面では点の選択・追加・削除・移動、方位、左右幅、停止・スキップ属性、undo/redo、
CSV/JSON/PNG保存を行える。位置等を編集すると要確認に戻る。
確認済み操作は利用者による確認であり、自動検証ではない。
GNSS／自己位置推定軌跡を切り替え、時刻ごとの品質も参照できる。
編集結果を走行中の経路へ自動適用せず、停止後にCSVと投影設定を読み直す。

HTMLはオフラインで動作する。PC内ファイルはiPhone向け共有URLではない。
遠隔閲覧には会話内画像・本文または指定された共有先を使用する。

## 7. 起動と設定

[README](../README.md)の単独record.launchは起動済みセンサと位置推定を購読する。
icart_bringupのsurvey.launchはsessionで選択された自己位置推定・手動操縦・UIを含めて起動し、自律復帰を無効にする。
実機domainは0、模擬は86。Joyの二重配信を避ける。
採取ボタンは車体停止操作ではない。

単独設定の `lidar_height_m=0.6` は水平取付の既定値。
実機では[hardware.yamlから生成したrecorder.yaml](../../icart_bringup/docs/実機ハードウェア統合.md)を使う。
主要調整項目はspacing_m、turn_deg、surface_window_s、surface_margin_m、surface_max_seed_intensity。
output_directoryとprojection_configは必須である。

## 8. 確認方法と限界

`tests/` では距離・曲がり角・属性・欠落復帰・時刻・保存、段差・粗面・材質・未観測を確認する。
ICP入力だけでの採取、GNSS比較軌跡との分離、取付変換を一度だけ適用した点群の姿勢・高さ、
照合不良時の品質記録、保存遅延中の受信継続、保存完了・エラー・再試行も確認対象とする。

通常版のインストール済みノードを、ネットワーク・デバイスを分離したdomain 193で確認した。
1,000ウェイポイント、表示点群10万点、GNSS／ICP各18,000点の履歴を保持してメディアへ保存し、
別ROSプロセスから10 Hzで送信した位置120点をすべて受信、棄却0点、終了時の保存成功を確認した。
受信遅延は平均11.2 ms、95%点66.8 ms、最大105.4 ms。
試験時間は約16秒で、1時間走行を実時間再生した試験ではなく、長時間分のデータ量による保存負荷試験である。
通常GUIのICP／GNSS選択と起動引数、生成sessionの地図原点一致も確認している。
原本は `/media/nkb/TEST/icp_route_survey_20261009/verification.json`。
実機の全センサ・GUI・bag記録との同時稼働、新しい現地ルートの採取は未確認。
`tools/evaluate_gnss_loss.py` は融合と採取へ模擬GNSS/LIOを入力する結合確認に使う。
模擬入力の成立と、実機での検出精度・長時間ドリフトは区別する。
地面の観測だけで前方の歩道通行性を保証せず、保存経路・幅・停止属性は現地確認する。

[局所空間参照サンプル](free_space_sample.md)と[閾値評価](threshold_and_jev_evaluation.md)は
オフライン評価用であり、走行時の進路生成には接続されていない。
