# robot_console 画面・機能詳細設計書

## 1. 文書目的・対象範囲

本書は `robot_console` の画面構成、表示内容、操作、業務フローを定める。表示元の構造は
[アーキテクチャ詳細設計書](robot_console_gui_architecture_design.md)、起動手順と公開範囲は
[README](../README.md) を正とする。

**本書の章番号はコード内のコメントから参照される。** 章の追加・削除・移動を行う場合は、
`grep -rn 'screen_function_design' src/robot_console` で参照箇所を確認して併せて更新する。

記載内容はすべて実装済みである。運用判断に使えない値を 11.3 節に明示する。

## 2. 基本方針

通常の運行監視と操作をダッシュボードへ集約し、詳細情報は対応するタブで確認する。
**画面は ROS 観測の写しであり、走行可否の判定機構を持たない。表示値だけで走行の許可を
判断しない。**

### 2.1 画面サイズ・スケーリング方針

`ScaledCanvas` でウィンドウ全体を拡縮する。レイアウトは固定の論理サイズで組み、
ウィンドウサイズに応じて一様に拡大・縮小する。画面解像度ごとにレイアウトを分けない。

実機の時刻同期警告は全タブの上部へ表示する（11.2 節）。

## 3. 業務フロー

### 3.1 業務分類

業務モードは「環境 × 走行モード」の組で表し、起動プリセットと対応させる。

| 環境 | 走行モード | 主な起動内容 |
| --- | --- | --- |
| 実機（ICP） | 手動走行 | 共通実機 launch（`localization_mode=icp`） |
| 実機（ICP） | 自律走行 | 共通実機 launch（ICP 記録ルート） |
| 実機（融合） | 手動走行 | 共通実機 launch（`localization_mode=gnss`） |
| 実機（融合） | 自律走行 | 共通実機 launch（記録ルート） |
| 実機 | 手動走行 / 自律走行 | 上記の既定選択 |
| デジタルツイン | 自律走行 | 融合スタック（`environment=simulation`） |
| シミュレーション | 手動走行 | 障害物シミュレーション + 走行制御 |
| シミュレーション | 自律走行 | 上記 + 経路スタック + 障害物監視 + navigator |
| 机上確認 | 手動走行 | 走行制御のみ（Joy は simulator） |
| 机上確認 | 自律走行 | 経路スタック + 走行制御（Joy は simulator） |

### 3.2 共通業務フロー

1. 起動・設定タブで環境と走行モードを選び、プリセットを適用する。
2. 設定ファイルと launch 引数を確認する。
3. 重複する起動構成を停止する。
4. ダッシュボードで一斉起動する。
5. 自己位置と運行系トピックの受信を待つ。
6. 操作を行う。
7. 停止する。

**環境の選択だけでは稼働中プロセスの環境を切り替えない。** 全停止後に設定して再起動する。

### 3.3 実機手動走行フロー

1. 起動・設定で「実機／手動走行」を選び、プリセットを適用する。
2. 場所・RTK 局・保存先と ICP 地図を確認し、重複する起動構成を停止する。
   **既定地図はつくばの FIX 拘束地図である。**
3. ダッシュボードで一斉起動し、ICP の初期化と自己位置の受信を待つ。初期値は良好 FIX と
   方位、または手動設定を使う。
4. ルート記録タブで開始し、L1 を保持して操縦する。停止属性はコントローラから記録する。
5. 車体を停止して終了・保存を行い、保存完了を確認する。

「実機（融合）／手動走行」または自己位置設定 `gnss` を選ぶと、GNSS 融合による記録になる。

### 3.4 実機自律走行フロー

1. 採取構成を停止する。
2. 「実機（ICP）／自律走行」または GNSS 系の「実機／自律走行」で保存ルートを選ぶ。
3. 経路・原点・設定・幅未確認点を確認して起動する。
4. 始点付近で `manual_start` を送る。

**採取中・2 点未満・必要ファイル欠落の経路は自律起動に使わない。**

### 3.5 シミュレーション自律走行フロー

1. 「シミュレーション／自律走行」または「デジタルツイン／自律走行」を選ぶ。
2. 一斉起動し、経路の受信と自己位置を確認する。
3. `manual_start` を送る。

デジタルツインは実機と同じ融合・経路・画面を使う。

### 3.6 机上確認フロー

実機もシミュレータも使わず、Joy simulator と経路スタックだけで画面と操作の接続を確認
する。走行指令は車体へ届かない。

## 4. 起動・設定タブ

| 領域 | 内容 |
| --- | --- |
| 環境・運転モード | 業務モードの選択（3.1 節） |
| プリセット | 選択した業務モードの起動プリセットを適用 |
| 起動候補ツリー | profile をカテゴリ別に一覧（[アーキテクチャ](robot_console_gui_architecture_design.md) 9.2 節） |
| 起動予定ノード一覧 | 順・profile・カテゴリ・Config・Override・状態・Health |
| 設定編集 | 設定ファイルの選択と launch 引数の編集 |
| 記録ルート選択 | 自律走行で使う保存済みルート |

**プリセットの引数変更も `ConsoleCore` へ通知する。** 表示中の方式と実際の起動引数を
一致させるためである。

RTK 補正局は、地域の既定局・地域内の個別局・NTRIP なし・独自局から選ぶ。
**場所を変更した場合、別地域の局は地域の既定局へ戻す。** 独自局は認証情報を含む接続設定
YAML を「独自局の設定ファイル」で指定する。**編集は起動中の接続を変更しない。** 切替時は
現在の GNSS または共通構成を停止して再起動する。

## 5. コンソールログタブ

profile ごとのプロセス状態、標準出力・標準エラー、保存ログを表示する。

| 表示 | 内容 |
| --- | --- |
| プロセス状態 | profile ごとの起動状態と終了コード |
| 出力 | 標準出力・標準エラーの逐次表示 |
| 保存ログ | ログファイルの場所 |

配色は 10.3 節に従う。

## 6. ダッシュボードタブ

### 6.1 役割

走行前の確認と走行中の監視を 1 画面で行う。起動操作と手動入力もここに置く。

### 6.2 レイアウト

上段に運行フェーズ領域、中段に 4 カード（Route/Follower、Drive/CmdVel、GPS/Pose、
Event）、下段に Node Health、Manual Ops、起動操作、bag 保存を置く。

### 6.3 運行フェーズ領域

運行フェーズは単独の ROS topic では表現されず、起動管理状態・route / follower 状態・
drive mode・`manual_start` の組み合わせから判定する。

| フェーズ | 判定条件 |
| --- | --- |
| `異常` | profile 起動失敗、follower ERROR、route error |
| `終了処理中` | profile 停止処理中、route completed、follower FINISHED |
| `未起動` | 起動中／起動済み profile が無く、運行系 topic も未受信 |
| `起動確認中` | profile が STARTING、または起動済みだが運行系 topic が未受信 |
| `一時停止` | 走行開始後に停止要因あり |
| `走行中` | 走行開始後かつ follower / route が走行状態 |
| `走行準備完了` | 上記以外（運行系 topic 受信済みで走行開始待ち） |

**判定は「最も重い状態を優先する」方式とし、上の順に評価する。**

`robot_console` 自身がノードを起動しない使い方（HTML 遠隔観測 UI の単独起動など）では
全 profile が STOPPED のままになる。そのため**起動管理状態だけでフェーズを決めず、
運行系 topic（`route_state` / `follower_state`）の受信有無を併用する。**

停止理由は、操作者が次に取るべき判断に近い順で最初に成立したものを 1 つ表示する。

| 順 | 停止要因 | 表示 |
| --- | --- | --- |
| 1 | follower が `WAITING_STOP` | 停止 waypoint で待機中（信号/停止線） |
| 2 | follower が `WAITING_REROUTE` | 再経路待ち（route_manager の応答待ち） |
| 3 | follower が `STAGNATION_DETECTED` | 滞留検知（回避判断中） |
| 4 | follower が `WAITING_OBSTACLE` | 移動障害の通過待ち（人・ロボット） |
| 5 | route が `holding` | route_manager holding: 理由 |
| 6 | drive mode が `manual` | 手動介入中（drive_mode=manual） |
| 7 | 自律復帰待ち | 自律復帰待ち（auto resume pending） |

走行モードは**実際に走行制御が選択しているモード（`drive_mode_status`）を正**とし、
未受信の間だけ起動・設定タブの選択値で代替する。

current / next waypoint は `route_state` の現在 index と label を使う。label が無い場合は
index 表記（`#3`）へ落とす。最終 index では next を `goal` とする。**`route_state` と
`active_route` のいずれも未受信の間は `-` を表示する。** index 表記（`#0`）を出すと
受信済みと誤認させるためである。

**フォロワの走行状態を新鮮に受信していれば、開始操作を観測し損ねても走行中として表示
する。** 開始指令を推測して再送しない。

### 6.4 Route / Follower カード

route_version、現在 index と総数、進捗率、follower の状態、滞留理由、回避試行回数、
再計画の判断を表示する。

### 6.5 Drive / CmdVel カード

走行モード、出力元（ZERO / AUTONOMOUS_CMD / MANUAL_CMD）、最終速度指令、自律指令、
車輪 odom の実測速度、復帰待ちの残り秒を表示する。

**モードと出力元は別の値である。** 自律モードでも出力元はゼロになり得る。

### 6.6 GPS / Pose カード

RTK 状態、衛星数、HDOP、補正データ年齢、方位と標準偏差、自己位置を表示する。

色ルールは次のとおりである。

| 条件 | 色 |
| --- | --- |
| 鮮度が OK でない | 鮮度の色（STALE は黄、LOST は赤、UNKNOWN は灰） |
| RTK_FIX | 緑 |
| RTK_FLOAT | 黄 |
| それ以外 | 赤または灰 |

**鮮度が OK でない場合、RTK 状態より鮮度の色を優先する。** 古い FIX 表示を正常色に
しないためである。未受信の数値は「—」とする。

GNSS 単独方位は北基準の時計回り、融合 yaw は map 基準の反時計回りとして明示する。
標準偏差は推定品質であり実測誤差ではない。

### 6.7 Event カード

注意すべき事象を優先順位の高い順に並べる。**Qt と HTML が同じ並びで表示する。**

| 順 | 種別 |
| --- | --- |
| 1 | profile error |
| 2 | topic lost |
| 3 | road_blocked |
| 4 | front_blocked |
| 5 | signal STOP / WAITING_STOP |
| 6 | manual_start 待ち |
| 7 | signal GO |
| 8 | route update |

未知の種別は最下位に置く。優先順位の定義は UI 非依存の層に置き、PyQt5 と HTML が共有
する。

### 6.8 Node Health カード

profile ごとに状態（RUNNING / STARTING / STOPPED / ERROR）と健全性（OK / STALE / LOST /
UNKNOWN）を表示する。合成規則は
[アーキテクチャ](robot_console_gui_architecture_design.md) 13.3 節を参照する。

外部起動（GUI が起動していないが topic が届いている）は RUNNING として表示し、外部起動で
あることを区別して示す。

**プロセスの RUN 数は起動グループ数であり、すべてのセンサが正常なことを表さない。**

### 6.9 Manual Ops カード

5 つのタブで手動入力を送る。

| タブ | 送る内容 |
| --- | --- |
| manual_start | 開始・停止点からの再開（true）、入力解除（false） |
| 信号認識 | `sig_recog` の値 |
| 道路封鎖 | `road_blocked` の真偽 |
| 固定障害物ヒント | `obstacle_avoidance_hint` の固定値 |
| 静止画像入力 | `/frame_image_path` のパス |

**`manual_start=false` は入力解除であり、走行停止ではない。** 実際の手動介入は
`drive_mode_manager` の L1 + PS を使う。

**固定障害物ヒントは停止操作で解除し、通常の `obstacle_monitor` へ戻す。**

QWidget は ROS の publisher を持たず、`ConsoleCore` を経由して配信する。

## 7. 自己位置・センサ情報タブ

### 7.1 役割

経路・自己位置・目標の地図と、センサ画像・カメラ認識結果を表示する。

### 7.2 レイアウト

左に地図、右に画像列を置く。**Qt の地図と画像列の横比は 3:2** とする。HTML はカード幅に
上限を設けて中央に置く。

### 7.3 地図表示

`active_route` の LLH を表示する。

| 要素 | 色 |
| --- | --- |
| 未走行の経路 | 緑 |
| 走行済みの経路 | 灰 |
| 現在位置 | 水色 |
| 目標 | 黄 |

**緯度経度を持つ waypoint だけを描く。** 現在 index を境に走行済みと未走行を色分けする。

初回受信と形状変更では全体表示にし、進捗更新では手動の拡大率を維持する。「ルート全体」
ボタンで表示範囲を戻せる。最大 zoom は 22 で、19 を超える範囲は背景タイルを拡大表示する。

Qt 側は `QWebEngineView` に地図 HTML を埋め込み、**HTML 遠隔観測 UI と同じ Leaflet 1.9.4
と OSM タイルで描画する。** 同じ実装を共有することで両 UI の表示内容を揃える。

### 7.4 画像列の構成

上からフロントカメラ、Sensor Viewer の順に縦積みとし、**Qt と HTML で順序を揃える。**
画像列内のカメラと Sensor Viewer の行高比は 3:2 とする。

実機カメラは usb_cam の `/usb_cam/image_raw` である。

### 7.5 センサ・画像パネル

パネル 1 枚は画像と表示名、元 topic 名、受信時刻を持つ。画像は
[アーキテクチャ](robot_console_gui_architecture_design.md) 8.2 節の `ImageStore` から
取得する。

初期の候補パネルはフロントカメラと Sensor Viewer である（地図は別領域）。

### 7.6 カメラ認識の重畳

**道路封鎖・信号の認識ノードは画像を配信しない。** `/perception/*/overlay` の検出矩形と
判定を `ConsoleCore` が同じカメラ画像へ重畳する。

| 枠 | 描画 |
| --- | --- |
| 採用した検出 | 太線 |
| 採用外の検出 | 細線・灰色 |
| フレームとの時刻差が大きい検出 | 破線 |

直近の認識枠は保持期限内であれば後続フレームにも描画する。

### 7.7 判定チップ

GO / STOP、封鎖状態、`status_note` を画像の直下に表示する。**未受信でも枠を残す。**

**画像表示の有無だけで、認識結果やセンサ較正の有効性を判断しない。**

## 8. HTML 遠隔観測 UI

### 8.1 役割

別端末のブラウザから走行状態を観測する。Snapshot による読取専用表示である。

### 8.2 表示内容

Qt と同じ Snapshot を使う。GNSS は**測位状態・衛星数・基地局受信状態の 3 項目のみ常時
表示**し、詳細は標準の `details` 要素へまとめて初期状態で閉じる。**開閉状態は定期更新でも
維持し、ページ再読み込み時は閉じる。** スマートフォン幅では接続先を折り返す。

### 8.3 禁止事項

- 走行指令を送らない。
- 起動・停止を行わない。
- bag 操作を提供しない。
- 経路採取の操作を提供しない。
- **起動時の上書き入力（`override_inputs`）をペイロードに含めない。** NTRIP の
  パスワードなど任意の値が入り得るためである。
- 認証ユーザー名・パスワード・サーバ応答本文を診断 JSON に含めない。

HTTP サーバは loopback で待ち受け、認証機能を持たない。別端末への公開範囲と手順は
[README](../README.md) に従う。**PC 内の URL は遠隔端末から直接開ける共有 URL ではない。**

## 9. GNSS・基地局タブ

ダッシュボードには基地局 / RTCM 状態とマウントポイントを表示する。本タブには次を表示
する。

| 区分 | 内容 |
| --- | --- |
| 基地局 | 地域、局名、ホスト:ポート、マウントポイント |
| RTCM | CRC 確認済み RTCM の受信速度・累積量・最終受信からの秒数、再接続回数、通信エラー種別 |
| GNSS | RTK 状態、衛星数、HDOP、補正データ年齢、方位・標準偏差、アンテナ間距離、主アンテナの緯度・経度・高度 |

方位はアンテナ間の北基準時計回りであり、融合の車体 yaw とは区別する。

診断（`std_msgs/String` の JSON）を 1 Hz で購読する。実機・模擬とも
`/rtk_gps/rtk_status` と `/rtk_gps/ntrip_status` に配信する。単独起動・GUI の一斉起動・
共通起動・HTML 観測 UI は同じ公開名を使う。別の配信元を使う場合は Qt launch の
`rtk_status_topic` / `ntrip_status_topic`、HTML の `--ros-args -r` で指定する。

鮮度の判定は次のとおりである。

| 条件 | 判定 |
| --- | --- |
| CRC 有効 RTCM が 5 秒以上届かない | 補正途絶 |
| 診断 topic を 2.5 秒超受信しない | 更新遅延 |
| 診断 topic を 5 秒超受信しない | 情報途絶 |
| GNSS 自体 | 1 秒 / 3 秒の既定閾値 |

**接続成功と補正受信を区別する。** NTRIP を使わない設定は「無効」と表示する。
**外部補正入力の有無を NTRIP 無効から推定しない。** シミュレーションは NTRIP を持たず
`DISABLED` を配信する。**無配信による診断途絶とは区別する。**

**本タブは観測画面であり、走行中の接続先変更機能は設けていない。**

## 10. 入力・表示の共通設計

### 10.1 入力の種別

| 種別 | 例 |
| --- | --- |
| ROS へ配信する入力 | Manual Ops（6.9 節）、経路採取の開始・終了 |
| プロセスを操作する入力 | 起動・停止、bag 記録、地図作成ジョブ |
| 表示のみを変える入力 | 地図の拡大率、「ルート全体」、details の開閉 |

### 10.2 入力の無効化条件

| 入力 | 無効化する条件 |
| --- | --- |
| 一斉起動 | 同じドライバ・走行スタックが稼働中 |
| 環境の切り替え | プロセス稼働中 |
| 経路採取の操作 | 採取状態が 3 秒届かない（未接続へ戻す） |
| bag の保存先変更・開始 | 記録中 |
| 自律起動のルート選択 | 採取中・2 点未満・必要ファイル欠落 |

### 10.3 ログ表示の配色

コンソールログと地図作成のログは Ubuntu 端末風の配色を使う。背景を暗色、通常出力を
淡色、警告を黄、エラーを赤とする。

### 10.4 フォント

ログと数値は等幅フォントを使う。桁が揃わないと値の変化を読み取りにくいためである。
見出しと説明文は標準フォントを使う。

## 11. 警告と表示上の制約

### 11.1 警告の色

| 事象 | 色 |
| --- | --- |
| R1 による GNSS 途絶模擬（`/fusion/gnss_dropout_active`） | 赤 |
| 通知の期限切れ | 黄 |
| GNSS / NTRIP の未受信・期限切れの数値 | **正常色で表示しない** |

### 11.2 時刻同期警告

実機の時刻同期は未成立・喪失を**全タブで警告する。** 復旧後は共通構成を再起動する。

`core/clock_sync_status.py` が `/run/icart-clock/status.json` を読み、同じ boot ID・
3 秒以内・`clock_source=ntp`・`ready` の条件を確認する。**ROS 起動前にも表示でき、実機
モードの全タブで 1 秒周期に更新する。** 停止の実行は `icart_bringup` の同期ゲートが
担当する。

### 11.3 運用判断に使えない値

画面モデルに存在しても、次の値は運用判断の根拠にしない。

| 値 | 状況 |
| --- | --- |
| `signal_stop_active` / `line_stop_active` | 停止属性からの導出が未実装で、既定値のままである |
| `within_arrival_threshold` | 到達閾値を受信して算出する機能がない |
| Node Health の `last_log_level` | 実際の警告判定を網羅しない |
| Node Health の `required_but_not_selected` | 同上 |

停止理由は経路属性・follower 状態・ログを併せて確認する。

## 12. 互換性・移行・影響範囲

### 12.1 影響範囲

本書の章番号はコードから参照される（1 章）。購読する topic と型の変更は
[アーキテクチャ](robot_console_gui_architecture_design.md) 17 章の範囲である。

### 12.2 入力元の区別

`manual_start`、`sig_recog`、`road_blocked` は GUI と GUI 以外の双方が配信する。

## 13. ROSBAG 保存

### 13.1 操作

ダッシュボードの「ROSBAG 保存」で保存先を選び、記録開始を押す。終了時は停止・保存を
押し、保存完了になるまで待つ。記録状態、経過時間、保存容量、保存先と出力フォルダ名を
表示する。空き容量は状態欄、出力先の完全なパスはフォルダ名のツールチップで確認できる。

**HTML 遠隔観測 UI には操作も状態表示も置かない。**

### 13.2 保存先

既定は PC の `~/rosbags` である。環境変数 `ROBOT_CONSOLE_BAG_DIR` で初期値を変更でき、
UI の保存先欄または「変更…」でも変更できる。

**記録中は保存先変更と二重開始を無効にする。** 同じ保存先を使う別 UI との同時記録も
ロックで防ぐ。日時とランダム ID のフォルダを毎回作り、**既存 bag を上書きしない。**

### 13.3 記録の構成

`ros2 run robot_console record_bag_with_map` を起動する。内部の rosbag は
`--all-topics --storage sqlite3 --max-bag-size 1073741824` を使い、除外正規表現
`^/(Laser_map|sensor_viewer)$` で記録用 relay に置き換える元トピックを除外する。
通常トピックは開始後に出現するものも探索する。

| 元トピック | bag へ記録するトピック | 記録周期 |
| --- | --- | --- |
| `/Laser_map` | `/Laser_map_record` | 10 秒 |
| `/sensor_viewer` | `/sensor_viewer_record` | 1 秒 |

各周期に受信済みの最新 1 件を記録し、元の時刻・frame_id・点群／画像データを保持する。
Sensor Viewer は非圧縮画像のまま頻度だけを下げる。**カメラ画像はこの間引きの対象外で
ある。**

GUI は元の `/sensor_viewer` を購読し、通常の配信頻度で表示する。地図の表示更新・蓄積
密度、障害物判定と走行用ヒントも通常どおり動作する。

**新しい入力がない周期は古いデータを再配信しない。** 最初の記録用地図は開始約 10 秒後、
記録用 Sensor Viewer は約 1 秒後のため、それより短い記録には含まれない場合がある。
relay は記録開始時に起動し、停止時に終了する。

再生側で元トピック名が必要なら次を使う。

```bash
ros2 bag play <bag> --remap /Laser_map_record:=/Laser_map /sensor_viewer_record:=/sensor_viewer
```

**隠しトピックとサービスは対象外である。** `ROS_DOMAIN_ID` 等は UI の実行環境を
引き継ぐ。

センサ・点群・画像を含むため、実機で必要な受信レートと保存媒体の速度を確認する。
bag は約 1 GiB ごとの db3 ファイルと `metadata.yaml` で構成される。親フォルダに同名の
`.log` も残す。

### 13.4 停止と保存完了の判定

停止は SIGINT を送り、**プロセスの正常終了と `metadata.yaml` の存在を確認して保存完了と
する。** UI の通常終了・SIGINT / SIGTERM 終了時にも停止処理を行う。

| 事象 | 扱い |
| --- | --- |
| 20 秒以上終了しない | SIGTERM を送り、**正常保存とは扱わない** |
| 強制電源断・SIGKILL | **最終保存を保証できない** |
| 開始時に空き 1 GiB 未満 | 開始しない |
| 記録中に空き 512 MiB 未満 | 停止する |
| 停止・エラー | 保存済みファイルを**自動削除しない** |

実装は `core/bag_recorder.py`、Qt 表示は `ui_qt/widgets/bag_card.py` に置く。

## 14. ルート記録タブ

ICP / GNSS 融合による採取状態、開始・終了、点数、左右幅の候補と理由、保存中・完了・
エラーを表示する。

| 状況 | 挙動 |
| --- | --- |
| ICP 照合が不良 | LIO 予測を**要確認**として記録し、自動幅を 0 にする |
| LIO が途絶 | 新しい点を追加しない |
| 保存 | 別ワーカーで行い、**終了時の書き込み成功まで保存完了と表示しない** |
| 保存エラー | 終了・保存で再試行する |
| 採取状態が 3 秒届かない | 未接続へ戻し、操作を無効にする |

**記録の開始・終了は速度指令を出さない。** 終了は位置途絶中でも可能で、**保存失敗を
完了と表示しない。**

[ROSBAG 保存](#13-rosbag-保存)は PC の記録操作、[経路採取](../../route_survey/README.md)は
共通自己位置（ICP / GNSS 融合）と経路属性の保存であり、出力形式と用途が異なる。

## 15. 地図作成タブ

bag の選択、FIX・ICP グラフの生成、進捗・中止・結果の再表示、俯瞰確認、次回 ICP 走行・
ルート記録への地図設定を行う。

`icart_mapping` で入力を検査し、`QProcess` で専用ジョブを起動する。**ジョブは
bubblewrap 隔離内でのみ処理し、ネットワークと実機デバイスに接続しない。**

段階状態は `status.json`、詳細は `build.log` へ保存する。Qt は状態とログを非同期に読み、
**処理中も中止できる。** GUI 終了時はジョブを終了する。

**完成状態と地図ハッシュを確認できた結果だけ、利用者の操作で起動・設定タブへ渡せる。**
この操作は次回の ICP 走行・ルート記録の地図引数を更新し、`ConsoleCore` の同じ override
更新経路へ通知する。**走行指令・稼働中ノード・現在の経路は変更しない。**

## 16. 確認方法と未確認範囲

`tools/tests/` と `tools/check_qt_entry.py` で Snapshot・各画面・実 ROS 受信を確認する。
試験の分離方針は
[アーキテクチャ](robot_console_gui_architecture_design.md) 16 章を参照する。

| 対象 | 確認する観点 |
| --- | --- |
| 運行フェーズ（6.3 節） | 列挙値ごとの判定条件と、停止理由の優先順位 |
| Event カード（6.7 節） | 表示対象と優先順位 |
| GNSS・基地局（9 章） | 不正 JSON、未受信、期限切れ、機密フィールドの除外、Qt / HTML 表示 |
| ROSBAG 保存（13 章） | 二重開始、別 UI との競合、空き容量不足、起動失敗、停止・保存状態 |
| 記録用 relay | 地図の 10 秒周期、Sensor Viewer の 1 秒周期、画像データと元時刻の保持、元画像の高頻度配信、入力停止後の重複抑止 |

ネットワークとデバイスを隔離した ROS 結合試験で上記の relay 動作を確認する。記録後は
`metadata.yaml` と必要トピックのメッセージを確認する。

未確認範囲は次のとおりである。

- **画面表示の試験は実機運動の検証を代替しない。**
- 模擬 NTRIP 診断の表示と、実 GNSS の測位品質・補正受信は区別する。
- 実機センサ一式の帯域・保存媒体性能・長時間保存は実構成で検証する。
- 11.3 節の値は導出が未実装であり、表示の正しさを確認できない。
