# avoidance_advisor 詳細設計書

## 1. 目的・スコープ

停止中の回避について、AI エージェントへ助言を求める action server の設計を定める。
topic 名、型、パラメータ一覧、起動コマンドは [README](../README.md) を正とし、本書では
再掲しない。

責務は、(1) 観測値と画像から要求文を組み立てること、(2) 外部 CLI を起動し上限時間内に
終了させること、(3) 応答を検証し採用可能な範囲へクランプすることの 3 つである。

パッケージ間の責務分担、安全境界、障害物の種類別の方針は
[AI助言による障害物回避](../../../docs/AI助言による障害物回避.md)を正とする。

非スコープを次に示す。

- いつ助言を求めるかの判断は `route_follower` が持つ。本ノードは要求されたときだけ動く。
- 呼び出し回数の制限、クールダウン、助言の再利用も `route_follower` が持つ。本ノードは
  同時実行を 1 件に制限するだけである。
- 助言を採用して回避目標を作る処理は `route_follower` が行う。本ノードは目標を作らない。
- 層の観測値と可視化画像の生成は `lidar_layer_slicer` が行う。

実装は pytest による単体確認のみを行っている。実際の AI エージェントを使った判断の
妥当性、応答時間、機上 PC での計算資源の競合は確認していない（9 章）。

## 2. 構成とファイル配置

| ファイル | 役割 | 配置理由 |
| --- | --- | --- |
| `avoidance_advisor/advice_core.py` | 要求文の組み立て、JSON の取り出し、検証とクランプ | ROS 非依存。採用条件を単体で固定したい |
| `avoidance_advisor/cli_core.py` | 外部プロセスの起動、タイムアウト、取り消し | ROS 非依存。代替スクリプトで挙動を確認できる |
| `avoidance_advisor/avoidance_advisor_node.py` | 購読、action、画像の符号化、配信 | ROS 入出力に限定する |
| `params/default.yaml` | CLI のコマンド列と採用条件の既定値 | 実行環境ごとに CLI が異なる |

助言の採用条件を ROS 非依存に保つのは、AI の応答を入力とする検査を、ROS グラフも CLI も
使わずに固定するためである。

## 3. 外部インタフェース仕様

### 3.1 QoS

| 対象 | 設定 | 理由 |
| --- | --- | --- |
| 層画像・カメラ画像・層観測値の購読 | BEST_EFFORT / VOLATILE / depth 1 | `stream` の購読規則。最新の 1 枚だけを使う |
| 助言の配信 | RELIABLE / VOLATILE / depth 10 | `event` 様式の既定。取りこぼすと記録が欠ける |

助言の配信は記録と表示のためであり、制御は action の result を使う。topic を取りこぼしても
制御には影響しない。

### 3.2 action の契約

goal には、waypoint の左右開放幅、前方余裕距離、obstacle_monitor のオフセット中央値、
採用可能な最小・最大オフセットを入れる。入力画像は server 側が購読済みの最新値から作る。
要求ごとに画像を goal へ載せないのは、画像が大きく、要求側が画像を保持する必要も
ないためである。

result は助言、採否、不採用の理由である。採否は server が決め、client は
`advice_valid=false` を従来の回避へ退避する合図として扱う。

client が goal を cancel したとき、server は起動中の CLI をプロセスグループごと終了させ、
`canceled` で終える。待機の上限は client が持つ。server 側にも `cli_timeout_sec` がある
が、これは CLI が応答しない場合の保険であり、client の待機上限とは独立である。

同時に 2 件の goal は受け付けない。実行中の要求がある間、新しい goal は reject する。

### 3.3 時刻の扱い

画像の鮮度は `header.stamp` と現在時刻の差で判定する。`image_max_age_sec` を超えた画像は
要求文へ含めない。古い画像を渡すと、現在と異なる場面を根拠に判断させることになる。
`stamp` が 0 の画像は鮮度を判定できないため、新しいものとして扱う。

### 3.4 記録

要求ごとに作業ディレクトリを作り、要求文、入力画像、CLI の標準出力と標準エラーを残す。
ディレクトリ名は `request_id` であり、`/avoidance_advice` と action の result にも同じ値が
入る。走行後に、どの場面でどの助言が返り、採用されたかを対応付けられるようにするためで
ある。削除は行わない。運用側で periodic に消す前提とする。

## 4. 設定の所在

ROS パラメータは README 5 章の表と `params/default.yaml` を正とする。既定値の意味と
選定理由は 7 章に置く。

| パラメータ | 効く判定 |
| --- | --- |
| `enabled` | goal の受理（6 章） |
| `cli_command` / `cli_timeout_sec` | CLI の起動と打ち切り（7.2） |
| `workspace_root` / `keep_workspace` | 作業ディレクトリの場所（7.3） |
| `min_confidence` | 助言の採否（7.1） |
| `default_wait_sec` / `max_wait_sec` | 待機時間の決定（7.1） |
| `image_max_age_sec` | 画像を要求文へ含めるか（3.3） |

コード内で固定し、変更に実装修正を要する値を次に示す。

| 値 | 内容 |
| --- | --- |
| 要求文の本文 | 判断の方針と出力形式。`advice_core` のみが持つ |
| 画像の符号化形式 | PNG。文字と細い点を保つため非可逆圧縮にしない |
| `obstacle_class` と `rationale` の長さ上限 | 64 文字と 512 文字。長大な応答を記録へ流し込まない |
| 完了待ちの刻み | 0.2 秒。取り消し要求の検出と feedback の配信に使う |

## 5. データモデル・内部状態

| 状態 | 初期値 | 更新契機 | クリア条件 |
| --- | --- | --- | --- |
| 最新の層画像・カメラ画像 | なし | 各 topic の受信 | クリアしない（上書きのみ） |
| 最新の層観測値 | なし | `obstacle/layers` の受信 | クリアしない（上書きのみ） |
| 実行中の呼び出し | なし | goal 受理時に生成 | 次の goal 受理時に置き換え |

保持しないものを次に示す。

- 過去の助言を保持しない。再利用とキャッシュは要求側の責務である。
- 呼び出し回数と課金の累計を保持しない。予算管理は要求側が持つ。
- 入力の鮮度は画像についてのみ判定し、層観測値については判定しない。層が古い場合も
  そのまま要求文へ入れる。層が未受信の場合は `layers=unavailable` と明記する。

## 6. 処理フローと異常時の挙動

goal を受けると、観測値と画像から要求文を作り、作業ディレクトリへ画像と要求文を書き、
CLI を起動する。0.2 秒ごとに完了と取り消しを確認し、完了したら出力を検証して result を
返す。

入力・事象ごとの扱いを次に示す。

| 事象 | 正常時 | 異常時 |
| --- | --- | --- |
| goal 受理 | 実行中でなければ受理する | `enabled=false` または実行中なら reject する |
| 層観測値 | 要求文の観測値として入れる | 未受信なら `layers=unavailable` を入れて続行する |
| 画像 | PNG へ符号化して渡す | 未受信・古い・変換失敗のいずれでも、その画像を省いて続行する |
| CLI の起動 | 子プロセスとして起動する | 実行ファイルが無い場合は失敗として返す（ノードは落ちない） |
| CLI の応答 | 標準出力を検証する | 上限時間超過はプロセスグループごと終了し `timeout` を返す |
| CLI の終了コード | 0 なら検証へ進む | 0 以外は `cli_failed` を返し、出力を採用しない |
| 応答の内容 | JSON を取り出して検証する | 空・JSON 無し・スキーマ違反・確信度不足・余裕不足は理由を付けて不採用 |
| 取り消し | — | CLI を終了させ `canceled` で終える |

いずれの異常でも goal は成功として終え、`advice_valid=false` と理由を返す。action を
abort しないのは、要求側から見て「助言が得られなかった」という 1 つの結果だからである。
助言は常に topic へも配信する。不採用の場合は `action=ACTION_UNKNOWN` の助言を配信し、
要求があった事実と `request_id` を記録に残す。

ログは、起動と各要求の終了（識別子・状態・所要時間）を `info`、要求の拒否・画像の欠落・
CLI の異常終了・助言の不採用を `warn` とする。`debug`、`error`、`fatal` は使っていない。
CLI の標準エラーはログへ 200 文字まで出し、全文は作業ディレクトリへ残す。

## 7. 判定ロジックと閾値

### 7.1 助言の検証とクランプ

出力から最初に現れる対応の取れた JSON オブジェクトを取り出す。囲み文や前後の説明が
付いていても取り出せるようにしているのは、出力形式の指示に従わない応答でも、値が
取り出せるなら使えるためである。壊れた JSON の後に正しい JSON がある場合は後者を採る。

次の順で検査する。いずれかで外れた場合は不採用とし、理由を返す。

1. 行動種別が `avoid` または `wait` であること。
2. 確信度が数値であり、`min_confidence`（既定 0.5）以上であること。確信度が無い応答は
   スキーマ違反として扱う。既定値で補って採用すると、判断できていない応答を採用する
   ことになるためである。
3. `avoid` の場合、方向が `left` / `right` / `none` のいずれかで、オフセットが数値であること。

採用する場合、オフセットを次の範囲へ収める。

- 上限は、要求側が渡した waypoint の開放幅と大域上限の小さい方である。助言が上限を
  超える場合は上限で打ち切る。
- 下限は要求側が渡した最小オフセットである。これを下回る助言は下限まで引き上げる。
- 上限が最小オフセットに満たない側は採用しない。その幅では回避が成立しないため、
  丸めて採用せず `no_feasible_offset` として不採用にする。
- 符号付きの値が来た場合は絶対値を採り、方向は `side` を正とする。

待機時間は `max_wait_sec`（既定 30.0 秒）で打ち切る。30 秒は `route_follower` の
再経路待機と同じ上限に揃えた値であり、待ち時間の上界を走行システム全体で一貫させる
ためである。待機時間が得られない場合は `default_wait_sec`（既定 10.0 秒）を使う。
人が横切る、対向するロボットがすれ違う、といった状況が解消する程度の時間として
選んだ設計値であり、実走の計測値ではない。

`min_confidence` の既定 0.5 は、半々より確からしい判断だけを採る、という意味で選んだ
設計値である。実際の応答分布から決めた値ではない。

`obstacle_class` と `rationale` は検査せず、長さだけを制限して記録へ残す。制御の分岐に
使わないため、値の妥当性を検査する必要がない。

### 7.2 CLI の起動と打ち切り

コマンド列の `{prompt}` を要求文へ置換して起動する。要求文を引数で渡すのは、標準入力を
使う CLI と使わない CLI の差を吸収しないためである。標準入力は閉じて起動する。

上限時間は `cli_timeout_sec`（既定 20.0 秒）である。上限で打ち切るとき、プロセス本体だけ
でなくプロセスグループごと終了させる。グループを使わないと、CLI 本体が消えても推論を
続ける子プロセスが機上 PC に残り、他のノードと計算資源を争い続ける。終了は SIGTERM を
送り、2 秒待って残る場合に SIGKILL を送る。

同時実行は 1 件に制限する。機上 PC では FAST-LIO や YOLO と計算資源を共有しており、
複数の推論を並行させると制御周期へ影響するためである。

### 7.3 作業ディレクトリ

要求ごとに `workspace_root/<request_id>/` を作り、そこを CLI の作業ディレクトリにする。
`workspace_root` の既定はシステムの一時ディレクトリ配下である。リポジトリ内で CLI を
起動すると、リポジトリの設定ファイルや指示をエージェントが読み込み、回避の判断と無関係な
指示が助言へ混入する。これを避けるため、既定をリポジトリ外にしている。

画像は作業ディレクトリへ置き、要求文にはファイル名だけを書く。CLI には読み取りの権限を
与える前提であり、既定のコマンド列では読み取りのツールのみを許可している。

### 7.4 要求文

要求文には、入力画像のファイル名、層ごとの観測値、採用可能なオフセットの範囲、判断の
方針、出力形式を書く。寸法は本文の数値で渡し、画像から距離を読ませない。制御に使う値が
画像の読み取り精度に依存しないようにするためである。

判断の方針として、静止した障害物は回避し、動く障害物は待機し、同じ方向へ進むロボットは
追い越さないことを示す。追い越さないのは、回避を発動しなければ `robot_navigator` が
前方余裕距離に応じて減速・停止し、前車が動けば自然に追従するためである。追従のための
制御は持たない。

### 7.5 既知の制約

- 助言の内容が正しいかどうかを検査する手段はない。検査しているのは形式と値域だけで
  ある。確信度も AI の自己申告であり、較正されていない。
- 画像の鮮度は判定するが、層観測値の鮮度は判定しない。
- `request_id` は実行ごとに生成する識別子であり、同じ障害物に対する複数回の要求を
  束ねる仕組みはない。
- 作業ディレクトリは削除しない。長時間の運用では容量が増える。

## 8. 並行性・周期・起動・依存関係

| 項目 | 値 |
| --- | --- |
| 周期処理 | 持たない（要求されたときだけ動く） |
| 完了待ちの刻み | 0.2 秒 |
| CLI の上限時間 | `cli_timeout_sec`（既定 20.0 秒） |

`MultiThreadedExecutor` と `ReentrantCallbackGroup` で動かす。goal の実行が数秒から
十数秒かかるため、単一スレッドの executor では実行中に購読が止まり、入力画像が更新
されない。CLI の実行自体は専用スレッドで行い、action の実行 callback は完了を
短い刻みで確認する。

entry point は `avoidance_advisor`、node name は `avoidance_advisor` である。
起動時に CLI の存在確認は行わない。確認しても、実行時に失敗する可能性は変わらず、
起動を止めると他のノードの立ち上げまで巻き込むためである。

依存はビルド時・実行時ともに `rclpy`、`sensor_msgs`、`cv_bridge`、`tc_route_msgs`、
`tc_perception_msgs`、`tc_diagnostics` である。AI の CLI 自体は ROS の依存関係では
表現せず、実行環境に導入されている前提とする。

## 9. 確認方法と未確認範囲

### 自動確認

`tests/test_advice_core.py` は、形式どおりの助言が採用されること、待機時間が上限と
既定値で決まること、オフセットが左右それぞれの上限と最小値で丸められること、上限が
最小オフセットに満たない側が不採用になること、確信度不足・スキーマ違反・JSON 無し・
空出力が不採用になること、囲み文や前後の説明が付いた出力からも JSON を取り出せること、
要求文に採用可能な範囲と出力形式の指示が入ることを固定している。

`tests/test_cli_core.py` は実際に子プロセスを起動し、標準出力の取得、要求文の置換、
作業ディレクトリへの保存、上限時間での終了、**CLI が起こした子プロセスまで終了する
こと**、取り消しでの終了、同時実行の拒否、実行ファイルが無い場合と異常終了の扱いを
固定している。AI の CLI は使わず、同じ振る舞いをする短いコマンドへ置き換えている。

### 手動確認

- JSON を返す代替スクリプトを `cli_command` に指定し、action の result が返ること。
- 助言が waypoint の開放幅でクランプされること。
- 作業ディレクトリに要求文・画像・出力が残り、`request_id` で対応付けられること。
- `enabled:=false` で要求が reject されること。

### 未確認範囲

- 実際の AI エージェントの応答時間、応答形式の安定性、判断の妥当性。
- 機上 PC で CLI を起動したときの CPU・メモリ競合が、他ノードの制御周期へ与える影響。
- 画像の解像度・層の並べ方が AI の判断精度に与える影響。
- ネットワーク不良時の失敗の出方。
- 7.1 節の閾値（確信度 0.5、待機 10 秒・上限 30 秒）は設計値であり、実測値ではない。

## 10. 影響範囲・未決事項

- `tc_route_msgs` に `AvoidanceAdvice` と `RequestAvoidanceAdvice` を追加した。
  同パッケージの README と合わせて更新する。
- `route_follower` は本ノードの client になる。要求の発火条件、呼び出し回数の制限、
  助言の採用は同パッケージ側の設計で定める。
- 新しい topic `/avoidance_advice` を記録へ含める場合は、`robot_console` の記録設定を
  更新する。
- 7.1 節の件: 確信度の下限 0.5 を実際の応答分布から見直すか、現状の設計値で進めるか。
  記録した `request_id` ごとの応答を集計すれば確定できる。blocker ではない。
- 7.3 節の件: 作業ディレクトリの削除を本ノードで行うか、運用側へ委ねるか。
  現状は委ねている。blocker ではない。
