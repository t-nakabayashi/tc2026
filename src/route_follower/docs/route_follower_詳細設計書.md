# route_follower 詳細設計書

## 1. 目的・スコープ

本書は `route_follower` パッケージの内部設計を定める。対象ノードは経路追従本体の
`route_follower` と、可視化補助の `active_target_marker` である。

トピック名、型、QoS、パラメータの一覧と起動方法は [README](../README.md) を正とする。
本書はそれを再掲せず、**README とコードだけでは判断できない内部状態、判定式、閾値の由来、
境界挙動と制約**を定める。上位の接続関係は
[システム構成](../../../docs/システム構成.md)、走行系全体の制約は
[走行システムの機能と制約](../../../docs/走行システムの機能と制約.md)を参照する。

経路に沿って 1 点ずつの目標姿勢を下流へ与える役務を負う。速度指令の生成は行わず、
`robot_navigator` が担う。責務は次の 4 点である。

- 経路上の現在追従点を管理し、到達判定で前進させる。
- 停止属性を持つ点で待機し、再開入力で解除する。
- 進行が止まった状態（滞留）を検出する。
- 滞留に対し、局所回避を試みるか、`route_manager` へ再計画を要求する。

非スコープは、速度・加速度の生成、障害物の観測（`obstacle_monitor` が担う）、信号の画像
認識（`traffic_signal_recognizer` が担う）、経路の生成と差し替え（`route_manager`、
`route_planner` が担う）である。

記載内容はすべて実装済みである。実機走行による追従精度・停止距離の検証は行っていない
（9.3 節）。

## 2. 構成とファイル配置

2 層に分ける。

| 層 | 実装 | 責務 |
| --- | --- | --- |
| ROS 層 | `route_follower_node.py` | 購読・配信・タイマー・サービス呼び出し、ROS メッセージと内部構造体の相互変換 |
| ロジック層 | `follower_core.py` | 状態保持、到達判定、滞留判定、回避目標生成、復帰点決定 |

ロジック層は ROS に依存しない純 Python であり、`rclpy` を初期化せずに単体試験できる。
ロジック層は時刻取得に `time.time()`（システム時刻）を使い、ROS 時計を参照しない。
`use_sim_time` を有効にしてもロジック層の時間判定は壁時計で進む。

`active_target_marker` は `/active_target` を購読して ARROW Marker を
`/active_target/marker` へ中継するだけの独立ノードであり、追従判断には関与しない。

| パス | 用途 |
| --- | --- |
| `route_follower/route_follower_node.py` | ROS 層 |
| `route_follower/follower_core.py` | ロジック層 |
| `route_follower/active_target_marker_node.py` | 可視化ノード |
| `launch/route_follower.launch.py` | 追従ノードの起動。トピック名・サービス名を launch 引数で差し替える |
| `launch/active_target_marker.launch.py` | 可視化ノードの起動 |
| `params/default.yaml` | 既定パラメータ |
| `tests/test_follower_boundary.py` | ロジック層の境界挙動の固定 |

ロジック層は `route_follower.follower_core` としても、`sys.path` 追加後の
`follower_core` としても import される。ROS 層は後者で参照し、試験は前者で参照する。
いずれの経路でも同一ファイルを指す。

## 3. 外部インタフェース仕様

一覧は [README](../README.md) を正とする。本章は一覧に現れない取り扱いと、QoS の選定
理由を定める。

### 3.1 QoS

| 種別 | 設定 | 適用先と選定理由 |
| --- | --- | --- |
| TRANSIENT_LOCAL | RELIABLE / KEEP_LAST / depth 1 | `/active_route` の購読。起動順に依らず最新経路を受けるため |
| VOLATILE | RELIABLE / KEEP_LAST / depth 10 | 位置、`manual_start`、`sig_recog`、`road_blocked` の購読、`/active_target`・`/follower_state`・`/recog_flag` の配信 |
| BEST_EFFORT | BEST_EFFORT / KEEP_LAST / depth 5 | `/obstacle_avoidance_hint` の購読。統計で扱うため欠落を許容する |

`/road_blocked` を VOLATILE で購読するのは、**発行元が既定 QoS（VOLATILE）で運用されて
おり、TRANSIENT_LOCAL を要求すると QoS 不整合で購読が成立しない**ためである。ラッチ相当の
保持はロジック層が行う（7.5 節）。

### 3.2 `/active_route`（購読）

`tc_route_msgs/Route` の `version`、`waypoints`、`start_index`、`start_waypoint_label` を
使う。`waypoints` が空のメッセージは警告を出して破棄し、保持中の経路を置き換えない。

`start_index` は `[0, len(waypoints)-1]` にクランプする。`start_waypoint_label` は
内部構造体に保持するが、追従判断には使わない。

Waypoint のうち本ノードが解釈するのは `label`、`pose`、`line_stop`、`signal_stop`、
`left_open`、`right_open` である。各フィールドの意味は
[Waypoint.msg](../../tc_route_msgs/msg/Waypoint.msg) を正とする。

`pose.orientation` は受信時に yaw へ変換して判断に使う一方、四元数の 4 成分もそのまま
保持し、`/active_target` の配信時に復元する。経路点の姿勢は yaw 以外の成分を失わない。
回避サブゴールは yaw のみから生成するため、配信時に四元数へ再構成される。

### 3.3 `/active_target`（配信）

目標が `None` の周期は配信しない。したがって `FINISHED`、`ERROR`、経路未適用の
`IDLE` では配信が止まる。

配信判定は次のとおりである。

- 目標の同一性 `(route_version, waypoint index, waypoint label)` が変化した、または
  位置が 1e-6 m 超動いたときは新規指示として即時配信し、`header.stamp` を現在時刻にする。
- いずれも変化がない場合は `resend_interval_sec` 周期で再送し、**`header.stamp` を
  前回配信時の値のまま据え置く**。再送を新しい指示と区別できるようにするためである。

### 3.4 `/recog_flag`（配信）

信号停止点で待機している間だけ 1、それ以外は 0 とする。値が変化した時のみ配信する。
例外として、起動直後と `IDLE` から `RUNNING` へ移った時点では 0 を強制的に再送する。

### 3.5 `/follower_state`（配信）

毎制御周期で配信する。`state` フィールドはロジック層の状態名を文字列で入れる。
各フィールドの意味は
[FollowerState.msg](../../tc_route_msgs/msg/FollowerState.msg) を正とする。

`front_blocked`、`left_offset_m`、`right_offset_m` はヒント統計の結果（7.4 節）であり、
`front_clearance_m` は統計を取らない最新受信値である。

### 3.6 `/report_stuck`（サービスクライアント）

`tc_route_msgs/srv/ReportStuck` を非同期で呼ぶ。要求と応答の各フィールドは
[ReportStuck.srv](../../tc_route_msgs/srv/ReportStuck.srv) を正とする。

`reason_detail` には滞留理由ラベル（7.6 節）を小文字で入れる。`reason_code` は同ラベルを
列挙値へ写像し、未知のラベルは `REASON_UNKNOWN` とする。`road_blocked` で始まるラベルは
`road_blocked` に正規化する。

`current_pose` には最後に受信した `/localization/pose_enu` の header と姿勢を複製して入れる。
未受信の場合はロジック層が保持する位置から `target_frame` と現在時刻で生成する。

**応答のうち本ノードが挙動へ反映するのは `DECISION_FAILED` のみである。** それ以外の
`decision_code` と `offset_hint` は内容をログへ出すだけで、追従判断には使わない。再開は
`route_manager` が新しい経路を配信することで成立する（6.4 節）。

### 3.7 画面・可視化

`active_target_marker` が `/active_target` を ARROW Marker へ変換して
`/active_target/marker` へ配信する。RViz での目標位置の確認に使う表示専用の経路であり、
追従判断には影響しない。

操作画面での状態表示は `robot_console` が `/follower_state` を購読して行う。本パッケージは
GUI を持たない。

## 4. 設定の所在

パラメータの一覧と既定値は [README](../README.md) を正とする。本章は、どの設定がどの判定に
効くかと、外から変えられない設定の範囲を定める。閾値の値と選定理由は 7 章に置く。

### 4.1 ROS から設定できる値

ROS パラメータは 7 個である。うちロジック層へ渡るのは次の 5 個である。

| パラメータ | 効く判定 |
| --- | --- |
| `arrival_threshold` | 到達判定（7.2 節）。回避サブゴールの到達判定にも同じ値を使う |
| `control_rate_hz` | `tick()` を呼ぶタイマー周期の逆数（8.1 節）。0 以下なら既定値へ補正 |
| `resend_interval_sec` | 目標の再送（3.3 節、8.1 節）。0 以下なら既定値へ補正。ロジック層にも逆数が渡るが、再送判定は ROS 層が行う |
| `avoid_back_offset_m` | 回避起点の後方シフト（7.7 節）。負なら 0.0 へ補正 |
| `road_blocked_confirmation_sec` | 封鎖継続の確認（7.5 節）。負なら 0.0 へ補正 |

`target_frame` は配信する `/active_target` の `frame_id` に使う。`start_immediately` は
開始条件（6.2 節）に使う。

**ノード宣言の既定値と `params/default.yaml` の値は一致しない。** `start_immediately` は
宣言が `true`、YAML が `false` である。`avoid_back_offset_m` は宣言が 0.5、YAML が 0.75
である。launch は既定で YAML を読み込むため、`ros2 launch` 経由では YAML 側が有効になる。
`ros2 run` でパラメータを与えない場合は宣言側が有効になる。

### 4.2 ROS から設定できない値

`FollowerCore.__init__` の初期値で固定され、ROS パラメータも launch 引数も持たない閾値が
13 個ある。変更には実装の修正が必要である。**値と選定理由は 7.1 節の表を正とする。**

対象は、滞留判定の観測窓・移動距離・平均速度・継続時間・グレース期間、回避の横オフセット
下限と上限・前進距離・試行回数の飽和値、再計画待ちの期限、ヒント統計の観測窓・多数決比率・
最小サンプル数である。

## 5. データモデル・内部状態

### 5.1 内部構造体

ロジック層は ROS メッセージを使わず、`Pose`、`Waypoint`、`Route`、`HintSample` の
dataclass で状態を持つ。`Pose` は xy と yaw に加えて四元数 4 成分を任意で保持する
（3.2 節）。`Waypoint` の `left_open` / `right_open` は既定 0.0 である。

### 5.2 保持する状態

| 状態 | 初期値 | 更新契機 | クリア条件 |
| --- | --- | --- | --- |
| 状態（FSM） | `IDLE` | `tick()` のみ | なし（`ERROR`、`FINISHED` は自己復帰しない） |
| 経路と追従 index | なし / 0 | 経路適用、到達、回避復帰 | 経路適用で `start_index` へ |
| 経路有効フラグ | false | 経路適用で true | 再計画待ちへの遷移と再計画失敗で false |
| 現在位置 | なし | 位置受信 | なし（古い位置を破棄しない） |
| 位置履歴 | 空 | 位置受信ごとに追記 | 経路適用でクリア。観測窓の 3 倍または 10 秒の大きい方より古い要素を削除 |
| 回避サブゴールのキュー | 空 | 回避開始で 2 点を積む | 到達ごとに先頭を除去。経路適用、到達、停止解除でクリア |
| 回避試行回数 | 0 | 回避開始で +1（上限で飽和） | 経路適用、到達、停止解除で 0 |
| 直近滞留理由 | 空文字 | 滞留判定の分岐で設定 | 経路適用、滞留解消でクリア |
| 最終目標キャッシュ | なし | 目標決定ごと | なし |

**位置履歴以外に、入力の鮮度を判定する仕組みを持たない。** 位置の受信が途絶しても、
最後に受けた位置を現在位置として使い続け、到達判定と滞留判定を続ける。入力途絶による
停止は `robot_navigator` 側の監視が担う。

### 5.3 排他制御

状態を変更するのは `tick()` だけである。購読コールバックは受け渡し箱（mailbox）へ
最新値を上書きするだけで、状態へ触れない。ロックは 3 個に分ける。

| ロック | 保護対象 | 取得区間 |
| --- | --- | --- |
| 受け渡し箱 | 経路・位置の最新値 1 件ずつ | コールバックの書き込みと `tick()` 冒頭の取り出し |
| ヒント | ヒント観測窓と統計結果 | ヒント受信時の統計更新と `tick()` のスナップショット取得 |
| 制御入力 | `manual_start`、`sig_recog`、`road_blocked` の保持値 | 受信時の書き込みと `tick()` のスナップショット取得 |

経路と位置は最新 1 件のみ保持し、同一周期内に複数届いた場合は最後の 1 件だけが適用される。

## 6. 処理フローと異常時の挙動

### 6.1 周期処理

`control_rate_hz` のタイマーで次を実行する。

1. 受け渡し箱から経路と位置を取り出してクリアする。
2. 経路があれば適用する（状態初期化と滞留グレース期間の設定）。
3. 位置があれば適用する（現在位置の更新と履歴への追記）。
4. ヒント統計と制御入力のスナップショットを取る。
5. 状態遷移と目標決定を行う。
6. 目標を配信判定に通し、状態を配信し、`/recog_flag` を更新する。
7. 前周期の `/report_stuck` 応答を反映する。
8. 再計画待ちであれば `/report_stuck` を呼ぶ。

経路を位置より先に適用する。同じ周期で両方が届いた場合、新しい経路に対して新しい位置で
判定するためである。

### 6.2 状態遷移

| 状態 | 離脱条件 | 遷移先 |
| --- | --- | --- |
| `IDLE` | 経路が有効かつ（`start_immediately` または `manual_start`） | `RUNNING` |
| `RUNNING` | 到達かつ停止属性あり | `WAITING_STOP` |
| `RUNNING` | 到達かつ停止属性なしかつ後続点あり | `RUNNING`（index 前進） |
| `RUNNING` | 到達かつ最終点 | `FINISHED` |
| `RUNNING` | 滞留検出 | `STAGNATION_DETECTED` を経て 6.3 節の分岐 |
| `WAITING_STOP` | 再開入力かつ後続点あり | `RUNNING`（index 前進） |
| `WAITING_STOP` | 再開入力かつ最終点 | `FINISHED` |
| `AVOIDING` | サブゴールを消化 | `RUNNING`（復帰点へ） |
| `AVOIDING` | 回避中に再滞留 | `WAITING_REROUTE` |
| `WAITING_REROUTE` | 新しい経路の適用 | `RUNNING` |
| `WAITING_REROUTE` | 期限超過、または再計画失敗の通知 | `ERROR` |
| `FINISHED`、`ERROR` | なし | — |

`WAITING_STOP` の再開条件は、停止属性が `line_stop` の場合は `manual_start` のみ、
`signal_stop` の場合は `manual_start` または `sig_recog == 1` である。`sig_recog` が 2
（NOGO）以上やその他の値は再開条件にならない。

`manual_start` と `sig_recog` の保持値は、開始時・停止待機への遷移時・停止解除時に
消費済みとしてクリアする。**停止点へ到達する前に届いた `manual_start` は、
`WAITING_STOP` への遷移時に破棄される。** 到達前の先行入力で停止を飛ばさないためである。

**`STAGNATION_DETECTED` は同一周期内で必ず別の状態へ移るため、`/follower_state` に
現れない。** 状態名としては存在するが、外部から観測できる状態ではない。

### 6.3 滞留検出後の分岐

滞留を検出すると、次の順に判定して 1 つを選ぶ。

1. 封鎖が継続していれば、理由 `road_blocked` で再計画待ちへ移る。
2. 現在点の左右許容幅がいずれも 0 以下なら、回避も再計画要求も行わず `RUNNING` を続ける。
   横移動の余地がない区間で回避を試みないためである。この場合、滞留理由はクリアする。
3. ヒント統計が成立していなければ、理由 `no_hint` で再計画待ちへ移る。
4. 前方閉塞の多数決が成立していなければ、理由をクリアして `RUNNING` を続ける。
5. 回避サブゴールを生成できれば、理由 `front_blocked` で `AVOIDING` へ移る。
6. 生成できなければ、理由 `no_space` で再計画待ちへ移る。

2 の分岐は `RUNNING` を続けるため、**左右幅が 0 の区間で前方が塞がれた場合、本ノードは
滞留を検出し続けるだけで何も起こさない。** 停止の継続は下流の障害物制動が担う。

### 6.4 再計画待ち

`WAITING_REROUTE` へ入る時点で経路有効フラグを false にし、待機開始時刻と期限を記録する。
ROS 層は毎周期 `/report_stuck` の呼び出しを試み、応答待ちの重複呼び出しを 1 件に抑える。

経路有効フラグは新しい経路の適用で true になる。したがって、`/report_stuck` の応答内容に
依らず、`route_manager` が経路を配信した時点で `RUNNING` へ復帰する。応答が
`DECISION_FAILED` の場合のみ `ERROR` へ移り、以後は自己復帰しない。

### 6.5 入力別の異常時の挙動

| 入力・事象 | 正常時 | 異常時 |
| --- | --- | --- |
| `/active_route` | 経路を適用し、状態を初期化する | 空の経路は警告を出して破棄。保持中の経路は変えない |
| 位置 | 現在位置を更新し、履歴へ積む | 未受信の間は最終目標キャッシュを配信し続ける。状態遷移は行わない。途絶の検出は行わない（5.2 節） |
| ヒント | 統計を更新する | 観測窓内のサンプルが不足なら統計不成立。滞留時は理由 `no_hint` で再計画要求 |
| `/report_stuck` | 応答を次周期に反映する | 未接続なら警告を出して次周期に再試行。呼び出し失敗・応答なしは例外内容を error で出し、`DECISION_FAILED` 扱いにはしない |
| 経路の保持 | — | 経路が未適用のまま `RUNNING` 以降の状態にあると `ERROR` へ移る |
| 再計画待ち | 新しい経路で復帰 | 期限を超過すると `ERROR` へ移る |

### 6.6 終了処理

`SIGINT` でノードを破棄し、ROS をシャットダウンする。**終了時に安全値を配信しない。**
`/active_target` の最後の値が下流に残るため、下流の指令失効はこのノードでは保証しない
（10 章）。

### 6.7 ログ

`info` を主に使う。状態遷移、経路適用、回避開始、サブゴール到達、停止解除、
`/report_stuck` の結果を `info` で出す。`/follower_state` の内容は 1 秒に 1 回へ間引く。
パラメータの範囲外補正と空経路、サービス未接続は `warn`、サービス呼び出しの例外は
`error` を使う。`debug` と `fatal` は使わない。

ロジック層はロガーを注入され、未指定の場合は `print` へ出す。ROS 層は `get_logger()` の
`info` を渡すため、**ロジック層の出力はすべて `info` になる。** ロジック層に重要度の
区別はない。

## 7. 判定ロジックと閾値

### 7.1 閾値一覧

ROS から設定できない閾値（4.2 節）の値と理由を本節に集約する。他章では値を再掲しない。

| 閾値 | 値 | 用途と理由 |
| --- | --- | --- |
| `window_sec` | 2.0 s | 滞留判定の観測窓 |
| `progress_epsilon_m` | 0.10 m | 窓内の移動距離の下限 |
| `min_speed_mps` | 0.05 m/s | 窓内の平均速度の下限。**`progress_epsilon_m` ÷ `window_sec` と一致する**（7.3 節） |
| `stagnation_duration_sec` | 15.0 s | 滞留条件の継続時間 |
| `stagnation_grace_sec` | 2.0 s | 経路適用直後に滞留判定を止める時間。目標が切り替わって動き出すまでを誤認しないため |
| `avoid_min_offset_m` | 0.35 m | 回避の横オフセット下限。**上限として働かないため許容幅を超え得る**（7.7 節） |
| `avoid_max_offset_m` | 5.0 m | 回避の横オフセット上限 |
| `avoid_forward_clearance_m` | 2.0 m | 横シフト後に前進する距離 |
| `max_avoidance_attempts_per_wp` | 2 | 回避試行回数カウンタの飽和値。**回避の開始を抑止しない**（7.7 節） |
| `reroute_timeout_sec` | 30.0 s | 再計画待ちの期限 |
| `hint_cache_window_sec` | 5.0 s | ヒント統計の観測窓 |
| `hint_majority_true_ratio` | 0.8 | 前方閉塞と判定する多数決比率 |
| `hint_min_samples` | 5 | 統計を成立させる最小サンプル数 |

停止解除の直後は 1.0 秒の猶予で滞留判定を止める。経路適用直後の猶予とは別の値である。

### 7.2 到達判定

現在位置と目標の xy ユークリッド距離が `arrival_threshold`（既定 0.6 m）未満で到達と
する。yaw は判定に使わない。z は使わない。

**到達判定は `robot_navigator` の位置許容（既定 0.5 m）と一致しない。** 本ノードが
0.6 m で到達と判断した時点でも navigator は未到達と見なす。停止属性のある点では、
本ノードが `WAITING_STOP` へ移った後も目標を配信し続けるため、navigator は残距離
0.5〜0.6 m を詰める指令を出し得る。

### 7.3 滞留判定

観測窓の位置履歴から、窓内で最も新しい点と最も古い点の距離を取る。距離が
`progress_epsilon_m` 未満かつ、距離を窓長で割った速度が `min_speed_mps` 未満の状態が
`stagnation_duration_sec` 継続したときに滞留とする。条件が崩れると継続時間の計測をやり直す。
窓内のサンプルが 2 点未満の場合は判定しない。

速度は実測の時間差ではなく窓長で割って求める。**この定義では速度条件が距離条件に
従属する。** 0.10 m ÷ 2.0 s = 0.05 m/s であり、2 つの閾値の境界が一致するため、距離条件
が成立すれば速度条件も必ず成立する。独立した 2 条件として機能していない。

停止属性のある点では、到達判定が成立した後（`WAITING_STOP` へ移る周期）は滞留判定を
除外する。停止待機を滞留として扱わないためである。到達前は判定する。

### 7.4 ヒント統計

`/obstacle_avoidance_hint` を受信ごとに観測窓のキャッシュへ積み、窓外を捨てる。

- サンプル数が `hint_min_samples` 未満の場合、統計は不成立とし、閉塞を false、左右
  オフセットを 0.0 とする。
- 以上の場合、`front_blocked` が真の比率が `hint_majority_true_ratio` 以上で前方閉塞と
  判定する。
- 左右オフセットは、`front_blocked` が真のサンプルのみから中央値を取る。真のサンプルが
  ない場合は 0.0 とする。
- `front_clearance_m` は統計を取らず、最新受信値をそのまま保持する。

統計はロジック層が受信時に逐次更新する。外部から統計値を直接与える口も持つが、ROS 層は
使わない。

### 7.5 封鎖継続の判定

`/road_blocked` を受信すると、値と受信時刻を保持する。封鎖継続の判定は
「保持値が true かつ、**最終受信時刻からの経過時間** が `road_blocked_confirmation_sec`
（既定 5.0 秒）以上」である。

**この判定は、発行元が状態変化時のみ配信する前提に依存する。** 受信ごとに最終受信時刻を
更新するため、`true` を周期的に再送する発行元に対しては経過時間が閾値へ達せず、継続は
永久に成立しない。`road_blockage_detector` は状態変化時のみ配信するため、現構成では
`true` の立ち上がりから既定 5 秒後に継続が成立する。

保持値は、新しい経路の適用時と再計画失敗時に明示的に破棄する。再計画の判断に使った
封鎖情報を次の経路へ持ち越さないためである。

### 7.6 滞留理由ラベル

`road_blocked`、`no_hint`、`front_blocked`、`no_space`、`avoidance_failed` の 5 種を
`/follower_state.last_stagnation_reason` と `/report_stuck` へ渡す。`avoidance_failed` は
回避中の再滞留で設定する。

### 7.7 L 字回避サブゴールの生成

左右それぞれについて採用オフセットを決める。

```
side_max = min(waypoint の許容幅, avoid_max_offset_m)
hint_open = ヒント統計の中央値
採用値 = 0                                                  (hint_open <= 0 または side_max <= 0)
採用値 = max(avoid_min_offset_m, min(hint_open, side_max))   (上記以外)
```

左右とも 0 なら生成失敗とする。両方が正なら**小さい方**を選び、同値なら左を選ぶ。
横移動量を最小に抑えるためである。

**`avoid_min_offset_m` が下限として優先されるため、採用値は許容幅を超え得る。** 許容幅が
0.35 m 未満の正の値である場合、0.35 m の横移動を生成する。狭所では経路境界の逸脱に
なる。この実装を通行境界の厳密な制限として扱わない。

サブゴールは現在姿勢の yaw を基準に 2 点を生成する。

1. 現在位置から進行方向の**後方** `avoid_back_offset_m` だけ下げた点を起点とする。
   起点から横方向へ採用値だけずらした点を横シフト点とする。
2. 横シフト点から進行方向へ `avoid_back_offset_m + avoid_forward_clearance_m` 進んだ点を
   前進点とする。

各点の yaw は直前の点からの方向で与える。起点を後方へ下げるのは、横シフト点までの
距離を確保して旋回余裕を作るためである。**後退指令は出さない。** 横シフト点が現在位置の
後方に置かれる結果として、下流が後退する場合がある。

回避試行回数は回避開始ごとに +1 し、`max_avoidance_attempts_per_wp` で飽和させる。
**この値は回避の開始を抑止しない。** カウンタの上限として機能するだけで、3 回目以降の
回避も同じ条件で開始される。

**車体占有領域の検査は行わない。** 生成する 2 点は位置のみであり、横シフト中・前進中に
車体が経路境界や障害物に干渉しないことを検証していない。

### 7.8 回避完了後の復帰点決定

サブゴールを消化すると、現在位置から復帰する経路点の index を決める。

1. 現在の index から終端までの区間のうち、長さが 0 でない最初の区間の単位方向ベクトルを
   経路の進行方向とする。求まらない場合は現在姿勢の yaw を使う。
2. 現在の index から終端までの各区間に現在位置を射影し、区間内へクランプする。
3. 射影点が進行方向に対して 0.1 m 以上後方にある区間を除外する。戻る方向へ復帰しない
   ためである。
4. 残った区間のうち射影距離が最小の区間を選び、その終点側の index を候補とする。該当が
   なければ現在の index を候補とする。
5. 現在の index から候補までの間に停止属性を持つ点があれば、**最初に見つかった点**を
   復帰点とする。

5 の処理により、回避で前進した結果として停止点を飛び越した場合でも、停止点へ戻って
停止待機する。回避が停止属性のスキップを引き起こさないためである。

## 8. 並行性・周期・起動・依存関係

### 8.1 周期

| 項目 | 値 |
| --- | --- |
| `tick()` と状態配信 | `control_rate_hz`（既定 20 Hz） |
| 目標の再送 | `resend_interval_sec`（既定 1.0 秒） |
| 状態ログの出力 | 1.0 秒（固定） |
| 滞留判定・ヒント統計の観測窓 | 7.1 節 |

### 8.2 並行性

5.3 節の受け渡し箱方式で扱う。コールバックとタイマーは既定の callback group に属するため、
単一の executor スレッドで直列に実行される。ロックは、サービス応答コールバックが別
スレッドから結果を書き込む場合に備えて保持する。

サービス応答は専用のフラグ付き変数へ格納し、次の `tick()` で読み出す。応答処理を
周期処理の中へ集めて、状態変更の契機を `tick()` に限るためである。

### 8.3 起動

entry point は `route_follower` と `active_target_marker` である。launch の引数は
[README](../README.md) を正とする。

launch は、トピック名 7 個とサービス名 1 個を引数で remap できる。ノードは全て相対名で
宣言するため、namespace の付与でも一括して変更できる。ログ用に remap 適用後の名前を
解決して保持する。

起動時のパラメータ検証は 4.1 節の範囲外補正のみである。外部デバイス接続やファイル
読み込みは行わない。起動直後に `/recog_flag` へ 0 を 1 回配信する。

`DiagnosticReporter` へ生存報告を登録する。報告の継続はタイマーが回ることで表される。
監視側の扱いは [ノード健全性監視設計](../../../docs/ノード健全性監視設計.md)を参照する。

### 8.4 依存関係

`ament_python` でビルドする。依存は `rclpy`、`tc_diagnostics`、`geometry_msgs`、
`std_msgs`、`visualization_msgs`、`tc_route_msgs` である。試験は `python3-pytest` と
`ament_copyright` / `ament_flake8` / `ament_pep257` に依存する。

ロジック層は標準ライブラリのみで動く。`numpy` を含む外部ライブラリに依存しない。

## 9. 確認方法と未確認範囲

### 9.1 自動確認

`tests/test_follower_boundary.py` がロジック層の境界挙動を固定する。ROS グラフも車体も
使わない。

| 試験 | 固定する内容 |
| --- | --- |
| 停止点の到達判定 | `line_stop` 到達で `WAITING_STOP` へ移り、かつ目標を配信し続ける。残距離 0.55 m が navigator の位置許容 0.5 m より外側であることを、navigator の `params/default.yaml` を読んで照合する |
| 最終点の終了 | 停止属性のない最終点に到達すると `FINISHED` になり、目標を返さない |
| 回避オフセットの逸脱 | 許容幅 0.1 m に対して `avoid_min_offset_m` 分の横移動を生成する（7.7 節の制約） |

試験は navigator のパラメータファイルを直接読む。両者の値が片方だけ変更された場合に
検出するためである。

### 9.2 手動で確認する範囲

結合確認では、`route_manager` を起動して `/active_route` と `/report_stuck` を成立させ、
次を確認する。状態だけでなく `/active_target` と下流の `/cmd_vel` を併せて見る。

- 初回開始（`start_immediately` の true / false 両方）
- 停止点と信号停止点での待機、`manual_start` と `sig_recog` による解除
- 到達前に送った `manual_start` が破棄されること
- 前方閉塞の継続による回避の開始と、復帰点の決定
- 左右幅 0、最小オフセット未満、境界値での回避の挙動
- 回避不能、ヒント不足、封鎖継続のそれぞれで再計画要求が出ること
- 経路世代の更新による再計画待ちからの復帰
- `/report_stuck` の未接続・失敗・期限切れ

### 9.3 未確認範囲

- **実機走行による追従精度、停止位置、回避軌跡を確認していない。** 本書の到達半径・
  オフセット・制動の記述は設計値であり、実測値ではない。
- 車体占有領域を含む回避の安全性を確認していない（7.7 節）。
- 滞留判定の継続時間が、実際の歩行者・障害物の滞留に対して適切かを確認していない。
- 封鎖継続判定が周期配信する発行元で成立しない点（7.5 節）を実機で確認していない。
  現構成の発行元が状態変化時のみ配信することをコード上で確認しただけである。
- ヒント統計の観測窓と多数決比率が、実センサのばらつきに対して適切かを確認していない。
- 長時間連続走行での位置履歴・ヒントキャッシュのメモリ使用を確認していない。

## 10. 影響範囲・未決事項

### 10.1 影響範囲

`tc_route_msgs` の `Route`、`Waypoint`、`FollowerState`、`ObstacleAvoidanceHint`、
`ReportStuck` に依存する。これらのフィールドを変更する場合は本パッケージの変換処理と
`route_manager` を併せて更新する。

`/active_target` の消費者は `robot_navigator` である。配信を止める条件（3.3 節）と、
下流が目標を保持し続ける性質（6.6 節）は両パッケージにまたがる制約であり、
[走行システムの機能と制約](../../../docs/走行システムの機能と制約.md)に集約する。

`/follower_state` の消費者は `robot_console` と `route_manager` である。状態名を文字列で
渡すため、状態の追加・改名は購読側の表示と判定に影響する。

### 10.2 未決事項

| 件 | 選択肢 | blocker |
| --- | --- | --- |
| 7.3 節: 速度条件が距離条件に従属する | 実時間差で速度を求める／片方の閾値を削る | ではない。閾値を個別に調整できると誤解しやすい |
| 7.5 節: 封鎖継続が発行元の配信方式に依存する | `true` を最初に受けた時刻を基準にする（解除の扱いを併せて決める必要がある）／現状を前提として発行元側に制約を課す | ではない |
| 7.7 節: 回避試行回数の上限が機能していない | 上限到達で再計画要求へ移す／カウンタを表示専用と割り切る | ではない |
| 6.3 節: 左右幅 0 の区間で滞留が放置される | 再計画要求へ移す／停止状態として通知する | ではない |
