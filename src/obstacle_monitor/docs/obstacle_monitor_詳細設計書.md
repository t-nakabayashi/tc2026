# obstacle_monitor 詳細設計書

## 1. 目的・スコープ

本書は `obstacle_monitor` パッケージの内部設計を定める。対象ノードは障害物監視の
`obstacle_monitor` と、動作確認用の `laser_scan_simulator` である。

トピック名、型、パラメータの一覧と起動方法は [README](../README.md) を正とする。
本書はそれを再掲せず、**点群の抽出条件、回避オフセットと前方閉塞の判定式、閾値の由来、
観測の品質に関する制約**を定める。

`/scan`（LiDAR）から前方の閉塞状況と左右の回避余裕を求め、
`tc_route_msgs/ObstacleAvoidanceHint` として配信する。あわせて判定の根拠を
`/sensor_viewer` に可視化する。

**本ノードは観測から回避ヒントを導くところまでを担い、指令を出さない。** 回避経路の生成は
`route_follower`、速度の決定は `robot_navigator` の責務である。購読側の使い分けは、
`robot_navigator` が距離（`front_clearance_m`）、`route_follower` が閉塞
（`front_blocked`）と左右幅を参照する。

単一の 2D LiDAR が `base_link` に前向きで固定搭載されていることを前提とし、**TF 変換を
行わない。** 取付位置や姿勢の補正は持たない。

記載内容はすべて実装済みである。実 LiDAR の反射特性と低い段差は確認していない（9.3 節）。

呼べる（9.1 節）。

## 3. 外部インタフェース仕様

一覧は [README](../README.md) を正とする。本章は一覧に現れない取り扱いと、QoS の選定
理由を定める。

### 3.1 QoS

| 対象 | 設定 | 選定理由 |
| --- | --- | --- |
| `/scan` の購読 | `qos_profile_sensor_data`（BEST_EFFORT / VOLATILE / depth 5） | センサ入力の標準プロファイル |
| `/obstacle_avoidance_hint` の配信 | BEST_EFFORT / VOLATILE / depth 1 | 最新の観測のみを扱う |
| `/sensor_viewer` の配信 | **RELIABLE** / VOLATILE / depth 1 | `rqt_image_view` などの可視化ツールが RELIABLE を要求するため。他の配信と異なる |
| `/localization/pose_enu`、`/active_target` の購読 | RELIABLE / VOLATILE / depth 10 | 可視化にのみ使う |

購読側が RELIABLE で `/obstacle_avoidance_hint` を購読すると QoS 非互換となり、受信が
成立しない。`route_follower` と `robot_console` は BEST_EFFORT で購読する。

### 3.2 `/obstacle_avoidance_hint`（配信）

`/scan` を受信するごとに 1 件配信する。周期は LiDAR の配信レートに従う。フィールドの
意味は
[ObstacleAvoidanceHint.msg](../../tc_route_msgs/msg/ObstacleAvoidanceHint.msg) を正とする。

**観測の品質を表すフラグを持たない。** 点数が不足する場合も「閉塞なし・距離 inf」を
配信する（7.5 節）。

### 3.3 `/localization/pose_enu`、`/active_target`（購読）

**可視化のためだけに使う。** 判定には一切使わない。未受信でも閉塞判定と回避オフセットの
算出は通常どおり行われる。

### 3.4 画面・可視化

`/sensor_viewer` に bgr8 の画像を配信する。描画範囲は `viewer_map_range_m` から
x: 0〜範囲、y: ±範囲/2 として決め、`viewer_pixel_pitch`（pix/m）で画素数を決める。
配信前に `viewer_resize_px` の正方形へリサイズする。

| 描画要素 | 色 |
| --- | --- |
| 車幅帯の境界線 | 黒 |
| `hint_range_m` の位置 | 橙 |
| 前方距離（`front_clearance_m`） | 赤紫 |
| 点群 | 赤 |
| 左右の回避オフセット | 青 |
| 目標への線と目標点 | 橙 |

目標は自己位置と yaw からローカル座標へ変換して描く。

**これは観測結果の可視化であり、旋回中の車体外周・後方・低い段差の通行性を保証するもの
ではない。** 画像が表示されていることをもって、認識やセンサ較正が有効であるとは判断
しない。

`viewer_window` パラメータはウィンドウ名として読み込むが、**OpenCV のウィンドウ表示は
無効化してある。** 画像は topic としてのみ出る。

## 4. 設定の所在

一覧と既定値は [README](../README.md) と
[params/default.yaml](../params/default.yaml) を正とする。本章はどの設定がどの判定に効くか
と、宣言と YAML の差を定める。閾値の値と理由は 7 章に置く。

| パラメータ | 効く判定 |
| --- | --- |
| `max_obstacle_distance_m` | 点群の抽出上限（7.1 節） |
| `front_block_ignore_dist_m` | 点群の抽出下限（7.1 節） |
| `robot_width_m` | 回避オフセットの閾値（7.2 節）と前方閉塞の帯幅（7.3 節） |
| `avoid_offset_min_m` | 回避オフセットの下限（7.2 節） |
| `stop_dist_m` | 前方閉塞の判定距離（7.3 節） |
| `front_clearance_percentile` | 前方距離の分位点（7.3 節） |
| `front_clearance_min_points` | 判定に必要な最小点数（7.3 節） |
| `hint_range_m` | 通知する距離の上限（7.4 節） |
| `viewer_*` | 可視化のみ（3.4 節） |

### 4.1 宣言と YAML で異なる既定値

**ノード宣言の既定値と `params/default.yaml` の値は 3 件で一致しない。**

| パラメータ | ノード宣言 | YAML |
| --- | --- | --- |
| `stop_dist_m` | 1.0 | **0.75** |
| `robot_width_m` | 0.8 | **0.6** |
| `hint_range_m` | `max_obstacle_distance_m` と同値 | **5.0** |

launch は既定で YAML を読み込むため、`ros2 launch` 経由では YAML 側が有効になる。
`ros2 run` でパラメータを与えない場合は宣言側が有効になる。

### 4.2 挙動に影響しないパラメータ

| パラメータ | 状況 |
| --- | --- |
| `front_cone_half_deg` | **読み込まれていない。** 宣言と YAML に存在するが、判定では一切参照しない |

**前方閉塞の判定は角度のくさびではなく、車幅の帯で行う**（7.3 節）。`front_cone_half_deg`
を変えても判定は変わらない。

`viewer_window` は読み込むが表示には使わない（3.4 節）。

## 5. データモデル・内部状態

| 状態 | 初期値 | 更新契機 | クリア条件 |
| --- | --- | --- | --- |
| 最新の点群（可視化用） | なし | `/scan` 受信ごと。点が 0 件なら None | なし |
| 最新の前方距離 | inf | `/scan` 受信ごと | なし |
| 実効の通知距離上限 | `max_obstacle_distance_m` | `/scan` 受信ごとに再計算（7.4 節） | なし |
| 通知距離の警告済み値 | なし | 補正の警告を出した時 | なし |
| 最新の自己位置（x, y, yaw） | なし | `/localization/pose_enu` 受信 | なし |
| 最新の目標（x, y） | なし | `/active_target` 受信 | なし |

**判定に使う状態を持たない。** 各 `/scan` の処理は、その回の点群とパラメータだけで完結
する。前のスキャンの結果を引き継がないため、時間方向の平滑化やヒステリシスはない。

**入力の鮮度を判定する仕組みを持たない。** `/scan` が途絶すると配信も止まる。自己位置と
目標は最後の値を保持し続け、古くなっても可視化に使う。

## 6. 処理フローと異常時の挙動

### 6.1 `/scan` 受信時の処理

1. `LaserScan` の `ranges` を順に見て、XY 座標へ変換する。変換時に点を除外する（7.1 節）。
2. 可視化用に点群を複製して保持する。
3. 抽出範囲で絞り込み、`y` の符号で左右に分割し、`|y|` の昇順へ並べ替える。
4. 左右それぞれの回避オフセットを算出する（7.2 節）。
5. 前方閉塞と前方距離を判定する（7.3 節）。
6. 前方距離を通知範囲で丸める（7.4 節）。
7. ヒントを配信する。
8. 可視化画像を配信する。

### 6.2 異常時の挙動

| 入力・事象 | 正常時 | 異常時 |
| --- | --- | --- |
| `/scan` の各点 | XY へ変換して使う | NaN、Inf、近すぎる点、後方の点は除外する（7.1 節） |
| `/scan` 全体 | ヒントと画像を配信 | **未受信・途絶の間は何も配信しない。** 途絶の検出は行わない |
| 抽出後の点数 | 判定を行う | 最小点数未満なら「閉塞なし・距離 inf」（7.5 節） |
| 車幅帯に点が無い | — | 同上 |
| `hint_range_m` < `max_obstacle_distance_m` | — | warn を出し、内部で `max_obstacle_distance_m` へ補正する（7.4 節） |
| `/localization/pose_enu`、`/active_target` の未受信 | 目標を描画する | 目標の描画のみ省く。判定は通常どおり |

### 6.3 終了処理

ノードを破棄して ROS をシャットダウンする。終了時に安全値を配信しない。**最後に配信した
ヒントが下流に残る。** 下流（`route_follower`）は観測窓で統計を取るため、配信が止まれば
窓が空いて統計が不成立になる。

### 6.4 ログ

**`/scan` を受信するごとに `info` で判定結果を出す。** 停止距離、閉塞判定、前方距離、
左右オフセットを 1 行で出力する。間引きを行わないため、LiDAR のレートと同じ頻度で
ログが出る。

`hint_range_m` の補正は `warn` で出し、同じ値に対しては繰り返さない。`error` と
`fatal`、`debug` は使わない。

`DiagnosticReporter` へ生存報告を登録する。報告の継続はタイマーが回ることで表される。
監視側の扱いは [ノード健全性監視設計](../../../docs/ノード健全性監視設計.md)を参照する。

## 7. 判定ロジックと閾値

### 7.1 点群の抽出

`LaserScan` から XY への変換時に次を除外する。

| 条件 | 閾値 | 理由 |
| --- | --- | --- |
| 距離が NaN または Inf | — | 無効値 |
| 距離が近すぎる | **0.2 m（実装内の固定値）** | 自機の構造物を拾わないため。パラメータを持たない |
| 角度が前方 ±90° の外 | 90 deg（固定） | 後方は判定に使わない |

変換後、さらに `x` 座標で絞り込む。

| 条件 | 閾値 |
| --- | --- |
| `x` が下限未満 | `front_block_ignore_dist_m`（既定 0.15 m） |
| `x` が上限超過 | `max_obstacle_distance_m`（既定 1.5 m） |

**近距離の除外が 2 段ある。** 変換時の 0.2 m は距離（斜距離）に対する固定値、抽出時の
`front_block_ignore_dist_m` は前方距離（`x`）に対するパラメータである。前者はパラメータ
で変えられない。

### 7.2 左右の回避オフセット

左右それぞれについて、`|y|` 昇順に並べた点列を走査する。ギャップの閾値は
`robot_width_m + robot_width_m / 2`（既定 YAML で 0.6 + 0.3 = 0.9 m）とする。

1. 直前の点との `|y|` 差がギャップ閾値を超える位置を探す。
2. 見つかれば、オフセットを「直前の点の `|y|` + `robot_width_m`」とする。
   - **直進経路上（直前の `|y|` が 0）に点が無い場合は回避不要**としてオフセット 0 で
     打ち切る。
   - オフセットが 3.0 m 未満であれば採用して打ち切る。**3.0 m は実装内の固定値**であり、
     パラメータを持たない。
3. ギャップが見つからず最外点まで来た場合、オフセットを「最外点の `|y|` +
   ギャップ閾値 / 2」とする。3.0 m 未満であれば採用する。
4. 得たオフセットが正であれば `avoid_offset_min_m`（既定 0.75 m）を下限として丸める。
   0 以下であれば 0 のままとする。

**下限が上限として働かないため、採用値は車体が通れる幅を保証しない。** 下流の
`route_follower` も独自の最小オフセットを持つため、二重に下限が適用される。

### 7.3 前方閉塞

**判定は角度のくさびではなく、車幅の帯で行う。**

1. 抽出済みの点のうち、`x > 0` かつ `|y| <= robot_width_m / 2` の点を取る。
2. 点数が `front_clearance_min_points`（既定 5）未満なら「閉塞なし・距離 inf」。
3. 帯内に点が無ければ「閉塞なし・距離 inf」。
4. 帯内の `x` の `front_clearance_percentile`（既定 5 %）分位点を前方距離とする。
5. 前方距離が `stop_dist_m`（YAML 既定 0.75 m）以下なら閉塞とする。

分位点を使うのは、単一の最近点ではノイズ 1 点で閉塞と判定されるためである。下位 5 % を
とることで、少数の外れ値に左右されない距離を得る。

**`front_cone_half_deg` はこの判定に関与しない**（4.2 節）。コード中のコメントと
README の旧記述にある「くさび判定」は実装と一致しない。

### 7.4 通知距離の上限

`hint_range_m` は通知する距離の上限である。**`max_obstacle_distance_m` 未満の値が
与えられた場合、warn を出して `max_obstacle_distance_m` へ補正する。**

前方距離が有限かつ通知上限以下であればその値を、そうでなければ inf を通知する。

**`hint_range_m` を大きくしても検知範囲は広がらない。** 点の抽出上限は
`max_obstacle_distance_m` であり、それより遠い点は判定に入らない。遠方を見るには
`max_obstacle_distance_m` を変える必要がある。

### 7.5 未観測と空き領域の区別

**点数が不足する場合も「閉塞なし・距離 inf」を返す。** 未観測と空き領域を区別する品質
フラグを持たない。

したがって購読側は、**新鮮なメッセージを受け取っていることをもって有効な障害物観測が
成立しているとは判断できない。** 入力途絶の検出は購読側で別に行う必要がある。
`robot_navigator` は非有限な距離を「距離制約なし」として扱う（
[robot_navigator 詳細設計書](../../robot_navigator/docs/robot_navigator_詳細設計書.md)）。

## 8. 並行性・周期・起動・依存関係

### 8.1 周期

| 項目 | 値 |
| --- | --- |
| ヒントと画像の配信 | `/scan` の受信ごと（LiDAR のレートに従う） |
| ログ出力 | 同上（間引きなし） |

タイマーを持たない。処理はすべて `/scan` のコールバック内で完結する。

### 8.2 並行性

callback group を指定しないため、既定の group で単一スレッドの executor が直列に処理
する。ロックを持たない。

**点群の XY 変換を Python のループで行う。** `numpy` のベクトル演算を使わないため、
点数に比例した処理時間がコールバック内で消費される。処理が LiDAR のレートに追いつかない
場合、BEST_EFFORT / depth 1 の購読により古いスキャンは破棄される。

### 8.3 起動

entry point は `obstacle_monitor` と `laser_scan_simulator` である。launch の引数は
[README](../README.md) を正とする。

launch はトピック名を引数で remap できる。ノードは相対名で宣言するため、namespace の
付与でも変更できる。

起動時にパラメータを読み、通知距離の上限を検査する（7.4 節）。外部デバイスへの接続や
ファイル読み込みは行わない。

### 8.4 依存関係

`ament_python` でビルドする。依存は `rclpy`、`tc_diagnostics`、`sensor_msgs`、
`geometry_msgs`、`builtin_interfaces`、`tc_route_msgs`、`cv_bridge` である。

`numpy` と `opencv-python` を使う。**`cv_bridge` と OpenCV が無い環境では起動できない。**
判定ロジックのみを単体試験する場合も `numpy` が必要である。

## 9. 確認方法と未確認範囲

### 9.1 自動確認

`tests/test_front_blocked.py` が前方閉塞判定の境界挙動を固定する。ROS グラフも LiDAR も
使わない。判定メソッドは `self` を参照しないため、非束縛メソッドとして呼ぶ。

| 試験 | 固定する内容 |
| --- | --- |
| 点が 0 件 | 未観測ではなく空き領域として報告される（7.5 節） |
| 全点が無効 | 同上 |
| 最小点数未満 | 同上 |
| 車幅帯の内外 | 帯の外の点は判定に入らない |

**回避オフセットの算出（7.2 節）には自動試験が無い。** ギャップ検出の分岐、3.0 m の
打ち切り、下限の適用はいずれも未固定である。

### 9.2 手動で確認する範囲

結合確認では `laser_scan_simulator` で `/scan` を供給し、次を確認する。

- `front_blocked` と `left_offset_m` / `right_offset_m` が障害物に応じて変化すること
- 点数不足・空観測で閉塞なし・距離 inf になること
- `hint_range_m` を小さく与えたときに warn が出て補正されること
- `/sensor_viewer` に点群・車幅帯・距離線・回避幅・目標が描画されること
- 宣言と YAML で異なる既定値（4.1 節）が、`ros2 run` と `ros2 launch` で切り替わること

**ヒントの値だけでなく、下流の最終速度まで併せて確認する。**

### 9.3 未確認範囲

- **実 LiDAR の反射特性を確認していない。** 模擬入力では再現しない。
- **低い段差、旋回中の車体外周、後方の障害物を検知しない。** 前方 ±90° の 2D スキャンのみ
  を使い、TF 変換も行わない。
- 点群の XY 変換が Python ループである影響（8.2 節）を実機のレートで測定していない。
- 回避オフセットの算出が実際の通行可能幅と一致するかを確認していない。幾何的な計算であり
  測量値ではない。
- 分位点 5 % が実センサのノイズに対して適切かを確認していない。

## 10. 影響範囲・未決事項

### 10.1 影響範囲

`tc_route_msgs/ObstacleAvoidanceHint` のフィールドを変更する場合、`route_follower` と
`robot_navigator`、`robot_console` の購読処理を併せて更新する。

`/obstacle_avoidance_hint` を BEST_EFFORT で配信する前提は購読側に伝播する（3.1 節）。
RELIABLE へ変えると既存の購読側と非互換になる。

`/sensor_viewer` は `robot_console` が表示し、bag 記録では 1 秒周期へ間引かれる（
[robot_console 画面・機能詳細設計書](../../robot_console/docs/robot_console_gui_screen_function_design.md)
13.3 節）。画像サイズを変える場合は記録帯域に影響する。

点数不足時の扱い（7.5 節）は走行系全体の制約であり、
[走行システムの機能と制約](../../../docs/走行システムの機能と制約.md)に集約する。

### 10.2 未決事項

| 件 | 選択肢 | blocker |
| --- | --- | --- |
| 4.2 節: `front_cone_half_deg` が読み込まれていない | 角度くさびの判定を実装する／パラメータを削って帯判定のみとする | ではない。YAML と README にあるため、調整しても効かない点が運用上の問題 |
| 7.5 節: 未観測と空き領域を区別できない | ヒントへ品質フラグを追加する／購読側が入力途絶を監視する（現状） | ではない |
| 7.1 節、7.2 節: 実装内の固定値がある | 0.2 m と 3.0 m をパラメータへ出す／固定のまま文書で明示する（現状） | ではない |
| 9.1 節: 回避オフセットに自動試験が無い | 前方閉塞判定と同じ方針で境界試験を追加する | ではない |
| 6.4 節: ログを間引いていない | スキャンごとの `info` を間引く／`debug` へ落とす | ではない。実機のレートでログ量が増える |
