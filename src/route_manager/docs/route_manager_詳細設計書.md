# route_manager 詳細設計書

## 1. 目的・スコープ

本書は `route_manager` パッケージの内部設計を定める。対象ノードは経路管理本体の
`route_manager` と、経路の可視化を行う `active_route_marker` である。

トピック名、型、QoS、パラメータの一覧と起動方法は [README](../README.md) を正とする。
本書はそれを再掲せず、**版管理の規則、再計画の判断順序、FSM と公開状態の対応、
並行性の前提と制約**を定める。経路の生成規則は
[route_planner 詳細設計書](../../route_planner/docs/route_planner_詳細設計書.md)、
追従側の挙動は
[route_follower 詳細設計書](../../route_follower/docs/route_follower_詳細設計書.md)を参照する。

`route_planner` から経路を取得して配信し、走行中に滞留が報告された場合の経路の作り直しを
統括する。責務は次の 4 点である。

- 起動時に初期経路を取得し、`/active_route` として配信する。
- 追従側の進捗を取り込み、現在の追従点と完走を把握する。
- 滞留報告を受け、経路の作り直しを 4 段階で試みて結果を返す。
- 経路の版を管理し、どの版に対する報告かを照合する。

非スコープは、経路そのものの探索（`route_planner` が担う）、追従と到達判定
（`route_follower` が担う）、走行開始の指示である。**走行開始の制御は
`route_follower` の `start_immediately` と `/manual_start` に統一しており、本ノードは
起動直後に無条件で初期経路を要求する。**

記載内容はすべて実装済みである。実機走行による再計画の有効性は検証していない（9.3 節）。

## 2. 構成とファイル配置

3 層に分ける。

| 層 | 実装 | 責務 |
| --- | --- | --- |
| ROS 層 | `route_manager_node.py` | 購読・配信・サービス、ROS メッセージと内部モデルの相互変換 |
| ロジック層 | `manager_core.py` | 経路モデルの保持、版管理、再計画の判断、公開情報の生成 |
| 状態機械 | `manager_fsm.py` | 非同期イベントの直列化、状態遷移、コールバックのタイムアウト |

ロジック層と状態機械は ROS に依存しない。ロジック層は ROS メッセージ型を知らず、
`route_planner` への非同期呼び出しと 3 種の配信を**コールバックとして注入される**。

ロジック層は専用の asyncio イベントループを持ち、デーモンスレッドで動かす。ROS 層は
`run_coroutine_threadsafe` でそのループへコルーチンを投入する。ROS のタイマー・
コールバックとイベントループを分離し、ループの二重生成を避けるためである。

`active_route_marker` は `/active_route` を購読して経路を Marker へ変換する独立ノードで
あり、経路管理の判断には関与しない。

| パス | 用途 |
| --- | --- |
| `route_manager/route_manager_node.py` | ROS 層 |
| `route_manager/manager_core.py` | ロジック層 |
| `route_manager/manager_fsm.py` | 状態機械 |
| `route_manager/route_markers_node.py` | 可視化ノード |
| `launch/route_manager.launch.py` | 経路管理ノードの起動 |
| `launch/active_route_marker.launch.py` | 可視化ノードの起動 |
| `params/default.yaml` | 既定パラメータ |
| `params/tsukuba*.yaml`、`params/inagi.yaml`、`params/obstacle_route_*.yaml` | 現地・シミュレーション別の start / goal / checkpoint 指定 |

`params/` の環境別ファイルは、同名の経路定義を持つ `route_planner/routes/` の各
ディレクトリと対応する。経路データ本体は `route_planner` 側が持ち、本パッケージは
ラベル指定だけを持つ。

## 3. 外部インタフェース仕様

一覧は [README](../README.md) を正とする。本章は一覧に現れない取り扱いと、QoS の選定
理由を定める。

### 3.1 QoS

| 種別 | 設定 | 適用先と選定理由 |
| --- | --- | --- |
| TRANSIENT_LOCAL | RELIABLE / KEEP_LAST / depth 1 | `/active_route`、`/mission_info` の配信。追従側の起動順に依らず最新経路を受け取れるようにするため |
| VOLATILE | RELIABLE / KEEP_LAST / depth 10 | `/route_state`、`/manager_status` の配信、`/follower_state` の購読 |

### 3.2 経路の受理と検証

`/get_route` の応答を受理する際、次をすべて満たさない経路は拒否する。

| 条件 | 拒否時の扱い |
| --- | --- |
| `header.frame_id` が `map` である | 不正としてログを出し、初期要求を失敗させる |
| 版が 1 以上である | 同上 |
| waypoint が 1 点以上ある | 同上 |
| `route_image` が有効（縦横が正かつデータが空でない） | 同上 |

**この検証は `/get_route` の応答にのみ適用する。** `/update_route` の応答は、成功フラグと
経路の存在のみを確認して受理する。再計画で受け取る部分経路に対しては画像も frame_id も
検証しない。

### 3.3 経路の付帯情報の保持

`route_id`、`map_frame_id`、`earth_frame_id`、`projection`、`route_image` は内部モデルへ
複製して保持し、ローカル更新（再配信・shift・skip）でも引き継ぐ。各 waypoint の
`geo_pose`、`has_geo_pose`、`geo_pose_source`、`has_pose_enu`、`not_skip`、
`segment_is_fixed` も同様に引き継ぐ。LLH 系の付帯情報が経路の作り直しで失われないよう
にするためである。フィールドの意味は
[Route.msg](../../tc_route_msgs/msg/Route.msg) と
[Waypoint.msg](../../tc_route_msgs/msg/Waypoint.msg) を正とする。

位置は xy と四元数のみを扱う。**z は扱わない。** ローカル更新で生成する waypoint の z は
0 になる。

### 3.4 `/follower_state`（購読）

`route_version`、`state`、`active_waypoint_index`、`active_waypoint_label` を使う。
現在の追従点を内部モデルへ反映し、`/route_state` を更新する。

版が自分の保持する版と一致しない場合は**ログを出すだけで、反映は行う**。別世代の進捗
通知でも現在 index を更新する。

`state` が `FINISHED` の場合のみ状態機械へ完了イベントを送る。それ以外の状態名は
進捗の反映にのみ使う。**完了判定は追従側の状態通知に基づく位置の判定であり、車輪速度
ゼロを認定する処理ではない。**

### 3.5 `/report_stuck`（サービスサーバ）

要求と応答の各フィールドは
[ReportStuck.srv](../../tc_route_msgs/srv/ReportStuck.srv) を正とする。

滞留理由は、`reason_detail` が空でなければその文字列を、空であれば `reason_code` を
列挙値へ変換した名前を使う。**`reason_detail` が `reason_code` に優先する。** 両者が
矛盾する場合は文字列側が有効になる。

応答は再計画の結果から組み立てる。

| 再計画の結果 | `decision_code` | `offset_hint` | `waiting_deadline` |
| --- | --- | --- | --- |
| skip が成立 | `DECISION_SKIP` | 0.0 | 0.2 秒 |
| それ以外の成功 | `DECISION_REPLAN` | shift の横ずれ量（左は負） | 0.2 秒 |
| 失敗 | `DECISION_FAILED` | 0.0 | 0 |

**`offset_hint` と `waiting_deadline` は追従側の挙動に影響しない。** 追従側は
`DECISION_FAILED` 以外を記録するだけである（
[route_follower 詳細設計書](../../route_follower/docs/route_follower_詳細設計書.md)
3.6 節）。

### 3.6 `/mission_info`（配信）

起動時に 1 回だけ配信する。TRANSIENT_LOCAL で保持するため、後から起動した購読側も
受け取れる。パラメータが変わらない限り再配信しない。

### 3.7 画面・可視化

`active_route_marker` が `/active_route` を Marker へ変換する。経路点、停止属性、
左右開放幅の表示に使う。表示専用であり、経路管理の判断には影響しない。

操作画面での経路・状態表示は `robot_console` が `/active_route`、`/route_state`、
`/manager_status` を購読して行う。本パッケージは GUI を持たない。

## 4. 設定の所在

一覧と既定値は [README](../README.md) を正とする。本章は、どの設定がどの処理に効くかと、
外から変えられない設定の範囲を定める。

| パラメータ | 効く処理 |
| --- | --- |
| `start_label`、`goal_label`、`checkpoint_labels` | 初期経路要求と `/mission_info` |
| `planner_connect_timeout_sec` | 起動直後の `/get_route` 接続待ちの打ち切り（6.1 節） |
| `planner_timeout_sec` | `/update_route` の接続待ち |
| `offset_step_max_m` | shift の横ずれ量の上限（7.2 節） |

**次の 3 個は読み込むだけで、挙動に影響しない。**

| パラメータ | 状況 |
| --- | --- |
| `planner_retry_count` | 値を保持するが、再試行処理を持たない。サービス失敗は 1 回で失敗として扱う |
| `report_stuck_timeout_sec` | 値を保持するが、滞留報告の処理に時間制限を適用していない |
| `image_encoding_check` | 値を保持するが、画像の符号化を検査していない |

`state_publish_rate_hz` はタイマー周期の計算に使うが、そのタイマーのコールバックは
何もしない。**状態の再送は 1 Hz で固定されており、このパラメータでは変わらない**
（8.1 節）。

`checkpoint_labels` は文字列配列として宣言するが、YAML で文字列として与えられた場合も
カンマまたは空白区切りとして解釈する。未初期化の場合は空配列として扱う。

**状態機械の 3 種のタイムアウトは ROS パラメータを持たない。** 値と帰結は 7.5 節に置く。

ロジック層の `offset_step_max_m` の既定値は、ROS 層が渡すパラメータ値とは別に持つ。
ノード経由では常にパラメータ値が有効になる。

## 5. データモデル・内部状態

### 5.1 版管理

経路の版は `major` と `minor` の 2 段で持ち、公開値を次の式で整数化する。

```
公開値 = (major % 100) * 100 + (minor % 100)
```

| 発生源 | 版の扱い |
| --- | --- |
| `route_planner` から取得した経路 | 応答の版を `major` とし、`minor` を 0 にする |
| ローカル更新（再配信・shift・skip） | `major` を保ち、`minor` を +1 する |

`route_planner` へ渡すのは `major` のみである。プランナは `minor` を知らない。
初期の `major` が 1 なら公開値は 100 になる。

**`major` と `minor` はいずれも 100 で剰余を取るため、`minor` が 100 回進むと公開値が
別の `major` の値と衝突する。** 1 回の走行で 100 回のローカル更新に達することは想定して
いないが、上限の検査は行っていない。

### 5.2 保持する状態

| 状態 | 初期値 | 更新契機 | クリア条件 |
| --- | --- | --- | --- |
| 経路モデル | なし | 経路の受理 | なし |
| 現在 index / label | -1 / 空 | 進捗通知、滞留報告、経路の受理 | なし |
| 公開状態文字列 | `IDLE` | 状態の設定、`/route_state` の生成 | なし |
| 現在区間の固定フラグ | false | 経路の受理、進捗の反映 | なし |
| skip 履歴（index:label → 回数） | 空 | skip の成立 | プランナ由来の経路の受理 |
| skip 済み index の集合 | 空 | skip の成立 | プランナ由来の経路の受理 |
| skip 許可フラグ | true | skip の成立で false | プランナ由来の経路の受理で true |
| shift 方向の記憶（index:label → 右/左） | 空 | 初回 shift の方向決定 | プランナ由来の経路の受理、同じ点の skip |
| 直近の滞留報告 | なし | 滞留報告の受信 | なし |
| 直近の横ずれ量 | 0.0 | 再計画の各段階 | 再計画の開始時に 0.0 |

**ローカル更新では skip と shift の履歴を保持し、プランナ由来の経路を受理した時点で
すべて破棄する。** 新しい経路に対して過去の局所調整の履歴を適用しないためである。

### 5.3 状態機械の状態

`IDLE`、`REQUESTING`、`ACTIVE`、`WAITING_REROUTE`、`UPDATING`、`COMPLETED`、`ERROR` の
7 状態を持つ。状態ごとに受け付けるイベントを制限する。

| イベント | 受け付ける状態 |
| --- | --- |
| 初期経路要求 | `IDLE`、`ERROR` |
| 滞留報告 | `ACTIVE`、`WAITING_REROUTE` |
| 明示的な部分更新 | `ACTIVE`、`UPDATING` |
| 進捗通知、強制エラー | すべて |

**受け付けない状態でイベントが来た場合は拒否して失敗を返す。** 状態は変わらない。

## 6. 処理フローと異常時の挙動

### 6.1 起動から初期経路の配信まで

1. パラメータを読み、`/mission_info` を 1 回配信する。
2. 初期要求用タイマー（8.1 節）で 1 回だけ、`/get_route` の接続を待つ。
   `planner_connect_timeout_sec` を超えると error を出して**初期要求を行わずに終了する**。
   この場合、状態機械は `IDLE` のままで `ERROR` にもならない。
3. 接続後、状態機械へ初期経路要求を投げ、`REQUESTING` へ遷移する。
4. `/get_route` を呼び、応答を検証して受理する（3.2 節）。
5. 成功なら `ACTIVE` へ遷移し、公開状態を `running` にする。失敗なら `ERROR` へ遷移する。

接続待ちと初期要求は ROS のタイマーコールバック内で同期的に完了を待つ。

### 6.2 走行中の進捗反映

`/follower_state` を受けるごとに現在 index と label を反映し、`/route_state` を更新する。
`FINISHED` を受けると公開状態を `completed` にし、状態機械を `COMPLETED` へ遷移させる。

### 6.3 滞留報告の処理

サービスコールバックで次を行う。

1. 要求を内部構造体へ変換し、現在 index・label・位置を反映する。版の不一致はログのみ。
2. ロジック層のイベントループへ再計画を投入し、**同期的に完了を待つ**。
3. 状態機械は `WAITING_REROUTE` へ遷移し、再計画を実行する（判断順序は 7.1 節）。
4. 成功なら `ACTIVE` へ、失敗なら `ERROR` へ遷移する。
5. 結果を応答へ整形して返す（3.5 節）。

### 6.4 状態機械と公開状態の対応

`/manager_status.state` と `/route_state.status` は**状態機械の状態名ではなく、
ロジック層が設定する公開状態文字列から作る**。両者は一致しない。

| 公開状態文字列 | 設定する契機 | `/route_state.status` |
| --- | --- | --- |
| `idle` | 初期値 | `STATUS_IDLE` |
| `running` | 経路の受理、shift・skip・再配信の成立 | `STATUS_RUNNING` |
| `holding` | 再計画の全段階が失敗 | `STATUS_HOLDING` |
| `completed` | 追従側の完了通知 | `STATUS_COMPLETED` |

状態機械の状態名はログにのみ現れる。`/route_state.status` への変換表は状態機械の状態名
（`requesting`、`updating`、`waiting_reroute`、`error`）も受け付けるが、**実際に渡される
のは上表の 4 種のみである。**

**再計画が失敗すると、状態機械は `ERROR` へ遷移する一方、公開状態は `holding` になる。**
`/manager_status` と `/route_state` は保留中に見えるが、状態機械はエラー状態にある。
この状態では滞留報告イベントを受け付けないため（5.3 節）、**以降の `/report_stuck` は
拒否され、失敗応答を返し続ける。** 復帰には初期経路要求のやり直しが必要である。

### 6.5 異常時の挙動

| 事象 | 挙動 |
| --- | --- |
| `/get_route` が接続できない | error を出して初期要求を行わない。状態機械は `IDLE` のまま |
| `/get_route` が失敗・不正な経路 | `ERROR` へ遷移。初期経路要求のやり直しのみ受け付ける |
| `/update_route` が接続できない | 失敗として扱い、次の段階（shift・skip）へ進む |
| サービス呼び出しの例外 | 内容をログへ出し、失敗として扱う |
| 状態機械のタイムアウト | `ERROR` へ遷移（7.5 節） |
| 再計画中の予期しない例外 | 状態機械が捕捉して `ERROR` へ遷移 |
| 受け付けない状態でのイベント | 拒否して失敗を返す。状態は変えない |
| 版の不一致（進捗通知・滞留報告） | ログを出し、処理は続ける |

### 6.6 終了処理

ノードを破棄して ROS をシャットダウンする。ロジック層のイベントループはデーモン
スレッドで動くため、明示的に停止しない。**終了時に安全値を配信しない。**
`/active_route` は TRANSIENT_LOCAL のため、ノード停止後も購読側の保持値は残る。

### 6.7 ログ

ほぼすべて `info` である。ロジック層と状態機械は注入されたロガーへ出力し、ROS 層が
`info` を渡すため、**ロジック層と状態機械に重要度の区別はない。** `error` を使うのは
`/get_route` の接続失敗と、非同期処理の完了時に捕捉した例外の 2 箇所である。
`warn`、`debug`、`fatal` は使わない。

状態機械の遷移フックで発生した例外は無視する。フックの失敗を状態機械の健全性へ
波及させないためである。

## 7. 判定ロジックと閾値

### 7.1 再計画の判断順序

滞留理由と現在区間の種別で分岐する。

| 滞留理由 | 区間 | 判断 |
| --- | --- | --- |
| `road_blocked` | 固定 | 現在経路を複製し `minor` を進めて再配信する。成功として返す |
| `road_blocked` | 可変 | プランナ更新のみを試す。失敗なら shift・skip を行わず失敗を返す |
| `road_blocked` | 経路未保持 | 失敗を返す |
| その他 | 固定 | プランナ更新を省略し、shift → skip の順に試す |
| その他 | 可変 | プランナ更新 → shift → skip の順に試す |

shift を試すのは、滞留理由が `front_blocked`、`avoidance_failed`、または理由を列挙値へ
変換できない場合に限る。`no_hint` と `no_space` では shift を飛ばして skip へ進む。

すべて失敗した場合、公開状態を `holding` とし、原因に滞留理由を入れて失敗を返す。

**固定区間での `road_blocked` に対する再配信は、その道路が通れることの検証ではない。**
追従側の経路有効フラグを立て直して追従を再開させるだけであり、封鎖の解消を確認しない。

### 7.2 プランナへの部分更新要求と shift

現在 index と、その 1 つ前の index・label を渡す。**現在 index が 0 の場合は前の点が
存在しないため、要求を出さずに失敗とする。** 経路の先頭で滞留した場合、プランナ更新は
必ず失敗し、shift または skip へ進む。

渡す版は `major` のみである。直近の滞留報告に含まれる位置があれば、要求へ複製して入れる。

shift は現在点を、直前の有効点から現在点へ向かう線分の法線方向へずらす。

1. 現在点の左右開放幅がいずれも 0 以下なら失敗とする。
2. 直前の有効点を探す。skip 済みの index は飛ばす。見つからなければ shift を行わない。
3. 方向を決める。
   - 同じ点で過去に方向を決めていれば、その方向を再利用する。往復を避けるためである。
   - 初回は、滞留報告の位置が線分のどちら側にあるかを外積の符号で判定し、**車体が実際に
     いる側**へずらす。外積が 0 に近い（線分上にいる）場合は判定しない。
   - 判定できない場合は開放幅の広い側（同値なら右）を選ぶ。
4. ずらす量は、選んだ側の開放幅を `[0, offset_step_max_m]` にクランプした値とする。
   0 以下なら失敗とする。
5. 現在点の位置のみを更新する。停止属性、`not_skip`、`geo_pose` などは維持する。
6. ずらした側の開放幅から移動量を引き、反対側へ同量を加える。
7. `minor` を進めた経路として受理・配信する。

**開放幅の付け替えは幾何的な再計測ではなく帳尻合わせである。** 実際の通行可能幅を
再観測した結果ではない。

**ずらすのは現在点 1 点のみである。** 前後の点は動かさないため、経路は折れ線として
その点でとがる。

### 7.3 skip（点の飛ばし）

1 回の再計画シーケンスで 1 回まで、同じ点については経路の受理から 1 回までとする。

次のいずれかに当たる場合は失敗とする。

- skip 許可フラグが false（この経路で既に 1 回 skip した）
- 現在 index が範囲外
- 現在点の `not_skip` が真
- 同じ index:label を既に 1 回 skip している
- 次の index が終端を超える

成立すると、現在 index を次へ進めた経路として `minor` を進めて配信する。**waypoint の
配列は変えない。** 飛ばした点は配列に残り、現在 index が先へ進むだけである。飛ばした
index は集合に記録し、以降の shift で直前の有効点を探す際に除外する。

### 7.4 固定区間の判定

現在 index の waypoint の `segment_is_fixed` を見る。経路の受理時と進捗の反映時に
更新する。**区間ではなく点の属性で判定する。** 区間の両端で属性が異なる場合、どちらの
点が現在 index かで判断が変わる。

### 7.5 状態機械のタイムアウト

初期経路取得、明示的な部分更新、滞留報告の再計画の 3 種にそれぞれタイムアウトを持ち、
**いずれも 5.0 秒で固定する。** ROS パラメータを持たない。超過すると `ERROR` へ遷移する。

**再計画のタイムアウト 5.0 秒は、`/update_route` の接続待ち `planner_timeout_sec`
（既定 5.0 秒）と同値である。** プランナが応答せず接続待ちで 5 秒を使い切った場合、
再計画全体のタイムアウトが同時に成立し、`ERROR` へ遷移し得る。

## 8. 並行性・周期・起動・依存関係

### 8.1 周期

| 項目 | 値 |
| --- | --- |
| 初期要求用タイマー | 0.1 秒（1 回だけ実行して以降は何もしない） |
| 状態スナップショットの確認 | 0.2 秒 |
| 状態の再送 | 1.0 秒（固定） |
| 状態ログの出力 | 1.0 秒（固定） |
| `state_publish_rate_hz` のタイマー | パラメータ依存。コールバックは何もしない |

`/route_state` と `/manager_status` は、ロジック層が値を更新した時点で即時配信し、
加えて最新値を 1 秒周期で再送する。再送はログ出力と配信回数を揃えるために行う。

### 8.2 並行性

**`MultiThreadedExecutor` を前提とする。** サービスサーバとサービスクライアントを
別々の相互排他コールバックグループへ分け、サービスコールバック内でクライアント呼び出しの
完了を待つ構造を取る。

- 滞留報告のサービスコールバックは、ロジック層のイベントループへ処理を投げて
  **同期的に結果を待つ**。
- その処理の中で `/update_route` を呼び、ROS のクライアントコールバックが別グループで
  処理される必要がある。

**単一スレッドの executor で動かすと、滞留報告の処理中にプランナ応答を受け取れず
デッドロックする。** 同じコールバックグループに置いた場合も同様である。

ロジック層のイベントループはイベントを 1 つずつ直列化する。滞留報告と進捗通知が同時に
届いても、状態の更新は順序どおりに行われる。

プランナ呼び出しの完了待ちは 10 ms 間隔のポーリングである。ROS の Future を asyncio の
待機対象へ変換せず、ループを回して完了を見る。

### 8.3 起動

entry point は `route_manager` と `active_route_marker` である。launch の引数は
[README](../README.md) を正とする。

launch はトピック名 4 個、サービス名 3 個を引数で remap できる。ノードは全て相対名で
宣言するため、namespace の付与でも一括して変更できる。

起動時の外部依存は `/get_route` の接続のみである。地図やモデルの読み込みは行わない。

`DiagnosticReporter` へ生存報告を登録する。監視側の扱いは
[ノード健全性監視設計](../../../docs/ノード健全性監視設計.md)を参照する。

### 8.4 依存関係

`ament_python` でビルドする。依存は `rclpy`、`tc_diagnostics`、`geometry_msgs`、
`std_msgs`、`sensor_msgs`、`visualization_msgs`、`tc_route_msgs` である。

ロジック層と状態機械は標準ライブラリのみで動く。`asyncio` を使うため Python 3.10 以降を
前提とする。

## 9. 確認方法と未確認範囲

### 9.1 自動確認

本パッケージは自動試験を持たない。ロジック層と状態機械は ROS 非依存であり、
`RouteManagerCore` へ注入する 3 つの配信コールバックと 2 つのプランナ呼び出しを差し替えれば
単体試験できる構造だが、試験は未整備である。

### 9.2 手動で確認する範囲

`route_planner` を起動し、`/get_route` と `/update_route` を成立させて次を確認する。

- 初期経路の取得と `/active_route` の配信、`/mission_info` の内容
- プランナ未起動での接続打ち切り（状態機械が `IDLE` に留まること）
- 不正な経路（frame_id、版、waypoint なし、画像なし）の拒否
- 滞留理由ごとの判断（`front_blocked`、`road_blocked`、`no_hint`、`no_space`、
  `avoidance_failed`）
- 固定区間と可変区間の分岐
- shift の方向決定（車体位置側へずれること）と、同じ点での方向の再利用
- skip の回数制限（1 回の経路で 1 回、`not_skip` の点では飛ばさないこと）
- 停止属性を持つ点を skip した場合の追従側の挙動
- 版の照合（別世代の報告でログが出ること）
- 再計画の失敗後に `/report_stuck` が拒否されること（6.4 節）
- 経路・`projection`・LLH 付帯情報がローカル更新後も維持されること

### 9.3 未確認範囲

- **実機走行で再計画が有効に働くことを確認していない。** shift の横ずれ量、skip の
  可否、プランナ更新の成否はいずれも設計上の判断であり、実走行での結果ではない。
- 固定区間での `road_blocked` 再配信が、封鎖の解消にどう対応するかを確認していない。
- 再計画の失敗後に復帰できない点（6.4 節）の運用上の影響を確認していない。
- 状態機械のタイムアウトが、プランナの実際の応答時間に対して十分かを確認していない。
- `minor` が 100 回進む長時間走行を確認していない（5.1 節）。
- 単一スレッド executor での動作は確認していない。`MultiThreadedExecutor` 以外での
  使用を想定しない。

## 10. 影響範囲・未決事項

### 10.1 影響範囲

`tc_route_msgs` の `Route`、`Waypoint`、`RouteState`、`MissionInfo`、`ManagerStatus`、
`FollowerState`、`GetRoute`、`UpdateRoute`、`ReportStuck` に依存する。これらの変更は
本パッケージの変換処理（ROS ↔ 内部モデル）と `route_planner`、`route_follower` に同時に
影響する。

版の公開式（5.1 節）は `route_planner`、`route_follower`、`robot_console` の 3 者が前提に
する。式を変える場合は全体を同時に更新する。

`/route_state.status` の列挙値は `robot_console` の表示に対応する。公開状態文字列を
追加する場合は変換表と購読側を併せて更新する。

### 10.2 未決事項

| 件 | 選択肢 | blocker |
| --- | --- | --- |
| 6.4 節: 再計画の失敗から復帰できない | 失敗を `ERROR` ではなく `WAITING_REROUTE` の維持として扱う／公開状態を `error` に揃える | ではない。外部からエラーと分からない点が運用上の問題 |
| 4 章: 使われていないパラメータが 3 個ある | 機能を実装する／パラメータを削る | ではない |
| 5.1 節: `minor` の上限検査がない | 上限で `major` を進める／検査を入れて警告する | ではない |
| 9.1 節: 自動試験が無い | 版の計算、判断順序、skip と shift の回数制限を入出力照合で試験する | ではない。`route_follower` の境界試験と同じ方針で追加できる |

再計画が、渡されたデータと保持中の滞留報告のいずれも存在しない場合に未代入の変数を
参照する経路がある。状態機械が例外を捕捉して `ERROR` へ遷移するため処理は止まらない。
滞留報告のサービス経由では必ず保持されるため、現構成では到達しない。
