# ICP自己位置推定

固定ENU地図にFAST-LIOのIMU座標点群を点・平面ICPで照合する。LIO相対移動で次の姿勢を予測し、地図照合で補正する。`small_gicp` 1.0.1、NumPy、SciPyを使用する。

GNSS系と同じ`/localization/pose_enu`（`geometry_msgs/PoseWithCovarianceStamped`、map座標の車軸中心姿勢）を出力する。経路追従・停止線処理・速度制御のロジックは共通。GNSS版と同じ`route_directory`を指定し、ウェイポイントの座標・番号・停止属性・道幅をそのまま使う。地図manifestと経路projectionの原点・方位・座標系の一致を起動時に検査する。

## 入出力

|用途|トピック|
|---|---|
|IMU body点群|`/cloud_registered_body`|
|同時刻のLIO姿勢|`/lio/odometry_raw`|
|起動時のGNSS初期値|`/rtk_gps/fix`、`/rtk_gps/rtk_status`|
|利用者が設定する初期位置|`/initialpose`（map座標の車軸中心、Z・傾斜も含む）|
|共通自己位置|`/localization/pose_enu`、TF `map → base_link`|
|診断JSON|`/localization/icp_status`（`std_msgs/String`）|

速度指令・走行許可・経路操作トピックは配信しない。GNSS系とICP系は同時起動せず、起動設定でどちらか一方を選ぶ。共通launchのICPモードはnavigatorの自律指令を既存muxへ接続する。既存のdriver制限、障害物処理、手動切替、指令途絶監視はそのまま使用する。

## 初期位置と追跡

初期値は起動時に1回、同時刻のFIXと方位から設定する。水平標準偏差0.3 m以下、方位標準偏差3度以下、既知の共分散を要求する。主アンテナ位置のレバーアームを補正し、高さ・傾斜は地図の車体姿勢アンカーから設定する。地図ZにGNSS高度を直接代入しない。アンテナ間隔の設定値を実測値とみなした選別は行わない。

`initialize_from_gnss:=false`の場合、または利用者が位置を設定したい場合は`/initialpose`を与える。地図座標と取付位置を確認し、ICPで地図との一致を確認してからpose配信を始める。

追跡開始後はGNSSを自己位置補正にも再初期化にも使わない。ICP補正を採用できない点群ではLIOの相対移動を使って推定を続け、診断状態を`LIO_PREDICTION`とする。品質低下に連動した停止・FIX待ち・自動復帰は実装しない。LIOそのものが途絶した場合は新しいposeを配信しない。LIO座標系が切れた場合は推定を無効化し、利用者が`/initialpose`を設定するかノードを再起動する。

ICP採用条件は、地図まで0.5 m以内の一致率60%以上、距離中央値0.3 m以下、100対応以上、正規化情報行列の最小/最大固有値比0.0001以上、収束、補正量0.8 m以下・回転8度以下。初期照合の3次元補正量上限は2 m。0.5秒より古い処理結果は採用しない。未採用でも走行側の状態を変更しない。

これらは照合条件であり、絶対位置精度の保証ではない。pose共分散は固定の参考値に未補正時間に応じた増分を加えたもので、測量誤差を推定した共分散ではない。診断には状態、出力の有無、測定時刻、地図補正からの経過時間、照合指標を出す。

## 起動

通常ワークスペースの`install/setup.bash`を読み込んだGUIで「起動・設定」を開き、実行環境「実機（ICP）」・走行モード「自律走行」を選んでプリセットを適用する。「実機・ICP地図照合走行」の設定を確認して一斉起動する。GNSS系から切り替える際は現在の走行を停止し、起動中の構成を終了してから切り替える。

GUIと`icp_route.launch.py`の初期値は共通である。

|設定|初期値|
|---|---|
|記録ルート|`/media/nkb/TEST/autonomous_route_20261005/route`|
|地図manifest|`/media/nkb/TEST/icp_runtime_20261007/map_manifest.json`|
|small_gicpディレクトリ|`/home/nkb/colcon_ws_experiments/glim_runtime/python`|
|走行設定の保存先|`/media/nkb/TEST/icp_route_runs`|

全3,704点の記録ルートを使う。GNSS系でも同じ記録ルートを選ぶ。保存済みの利用者設定があればそちらを優先する。メディアが未接続、ファイルが不足、地図と経路の投影が不一致の場合は起動できない。媒体・設定を確認して再度起動する。通常のGUIから利用でき、一時領域へのoverlay配置や隔離版GUIの専用起動は不要。

```bash
ros2 launch icart_bringup icp_route.launch.py \
  output_root:=/media/nkb/TEST/icp_route_runs
```

共通launchは`localization_mode:=icp`またはsessionの同名設定でも選択できる。GNSS系は`gnss`を指定する。初期位置の配信を確認してから、既存の「自律走行開始」を操作する。地図読み込み・初期照合中はposeが出ない。

small_gicpを通常のPython環境に追加する必要はなく、隔離された既存のPython拡張を`icp_backend_python_path`で指定できる。拡張は実行するPythonのバージョン・CPUに一致する必要がある。

## 地図manifest

JSONの`schema`は1。`projection`に原点緯度・経度・高度、`map_yaw_offset_rad`、`map_frame_id`、`datum`を明示する。`points`と`base_anchors`はそれぞれ`path`・`sha256`を持つ。点群はN×3以上のNPY、アンカーはN×4×4の地図→車軸中心SE3配列。パスはmanifest基準または絶対パス。高さアンカーは初期Z/傾斜の参考であり、XY・yawを記録軌跡へ固定する拘束ではない。アンカーから5 m超の地点や、高さが曖昧な重複地点ではGNSS初期値を採用しない。

## ルート記録とGNSSとの比較

「実機／手動走行」のルート記録は、上記FIX拘束済み地図によるICPを既定とする。
地図の原点を採取sessionへ引き継ぎ、同じ車軸中心の位置をLLHのウェイポイントとして保存する。
「実機（融合）／手動走行」はGNSS融合を使う。どちらもGNSS生位置を比較用に別保存する。
記録・保存中の挙動は[経路採取](../route_survey/README.md)を参照する。

同じ走行で良好なFIXと正常なICP照合が続く場合、両方式のルートは近くなると期待できる。
FIX表示だけで位置・方位・取付寸法・時刻の誤差が消えるわけではない。
ICP追跡中は現在のRTKへ連続拘束せず、事前にFIX拘束した地図へ照合する。
同じ測位系を地図作成と比較に用いるため、近い結果だけで独立した絶対精度を保証しない。
移動距離に基づく採取時刻は方式ごとに異なり得るため、同番号の点同士だけで比較せず、
ルートの横方向差と同時刻に押した停止点の位置差を比較する。

GNSS時刻に位置と姿勢を補間し、追加の位置合わせは行っていない。
比較対象はアンテナ位置であり、今回の2種類の記録機能が生成したウェイポイントの直接比較ではない。
同日・同局・部分コースの結果で、別日・独立測量基準に対する絶対精度確認は未実施。
原本は `/media/nkb/TEST/localization_benchmark_20261004/rtk_constrained_map_20261005/summary.csv`。

Core Ultra 7 258Vで6本の実ログから各12秒、合計720枚のFAST-LIO body点群を照合した。
