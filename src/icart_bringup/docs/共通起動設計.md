# i-Cart mini 共通起動設計

## 目的・構成

実機とデジタルツインで、投影原点・経路・PyQt5操作UIを共有する。
自己位置推定はGNSS/LIO融合（`localization_mode=gnss`）または固定地図ICP（`icp`）を選択する。
このパッケージは設定生成・検査と起動管理を担う。
実機ドライバはhardware.launch、模擬センサはobstacle_route_simが提供する。
FAST-LIO、座標変換、経路管理・追従、障害物監視、navigator、muxは共通とする。
GNSS系は重力整列・融合を起動する。ICP系はraw LIOとbody点群を固定地図へ照合する。

| 入出力 | 用途 |
| --- | --- |
| `/lio/odometry_raw` → `/lio/odometry` | FAST-LIO出力をgravity_alignment_nodeで水平化し、融合・採取へ渡す |
| `/gnss/pose_enu` | GNSS単独の比較用位置。融合入力はNavSatFix/RtkStatusを直接使う |
| `/localization/pose_enu` | 選択した推定器の車軸中心姿勢。配信元を一つにする |
| `/localization/pose_llh` | route_geo_projectorによる表示用変換 |
| `/ypspur_ros/odom` | 実機車輪またはGazebo駆動odom |
| `/scan` | URGまたは模擬URGのLaserScan |
| `/cmd_vel/autonomous` → `/cmd_vel/fusion_limited` → `/cmd_vel` | GNSS系: navigator → 融合減速 → 手動／自律mux |
| `/cmd_vel/autonomous` → `/cmd_vel` | ICP系: navigator → 同じ手動／自律mux |
| `/manual_start` | 経路追従の開始・再開操作 |

真値はシミュレーションのセンサ生成・評価に使い、融合自己位置の代わりに配信しない。
LIO異常時の車輪退避や初期FIX条件は[融合設計](../../gnss_lio_fusion/docs/詳細設計書.md)を参照する。
ICP系は品質を診断として配信し、品質低下による走行状態変更・FIX再初期化は行わない。
地図と経路の同一投影を検査し、ウェイポイント・停止線・制御パラメータを変更せず利用する。
ICPの初期位置・入出力・照合条件は[ICP自己位置推定](../../icp_localization/README.md)を参照する。

## セッションと設定

パスはsession.yamlの所在から解決する。

| キー | 用途・既定 |
| --- | --- |
| projection_params | 共通ENU原点とmap yaw。必須 |
| route_config、csv_base_dir | route_planner設定とCSV所在。必須 |
| start_label、goal_label | 開始・終点label。生成時はCSV先頭・末尾を使う |
| trial_directory、trial_sdf | simulationの地形・IMU付きSDF |
| hardware_launch | realのドライバlaunch。空なら外部でドライバを起動する |
| hardware_config | 一括生成した実機接続設定。指定時は同期ゲート付き起動を使う |
| fusion_params、fastlio_config | 融合とFAST-LIOの設定 |
| localization_mode | gnssまたはicp。省略sessionはgnss、real_surveyが生成する実機採取sessionはicpが既定 |
| icp_map_manifest、icp_params | ICPの地図manifestと任意の起動時パラメータ |
| icp_backend_python_path | small_gicpの隔離Pythonディレクトリ（任意） |
| gnss_namespace | 実機・模擬の既定は `/rtk_gps` |
| simulation_domain_id、real_domain_id | 86、0。親プロセスのdomainと照合する |
| noise_profile、noise_seed | 模擬センサのconservative、1 |
| building_gnss | 建物近傍のFLOAT・biasを有効にする |

取付位置・角度・接続先は[実機ハードウェア統合](実機ハードウェア統合.md)に従う。
実機sessionのhardware.yaml等はコピーであり、リポジトリ側の設定変更を自動で追従しない。
生成済みsessionを上書きせず、新規出力先で準備する。

prepare_sessionはsession_world.sdfを生成する。物理刻みは1 ms、既知の車輪軸は等価な
局所Z表現とし、未指定の駆動上限を2 Nm・20 rad/s、旋回速度を±1.2 rad/s、
旋回加速度を±1 rad/s²にする。明示された既存上限は保持する。
これらは模擬計算の制約であり、実機モータの実測値ではない。

## 経路と座標

`routes/fixed/waypoints.csv` はLLHを正本とし、高度を空欄にする。
route_plannerがprojection設定からENUを生成する。順序・label・左右幅・停止・スキップ属性を保持する。
採取経路を使う場合は、そのprojection.yamlも引き継ぐ。
real_surveyのICP採取では地図manifestのprojectionをsessionと保存ルートの正本にし、
同梱初期経路もLLHから再投影する。地図欠損・ハッシュ不一致・選択場所との不整合は起動前に拒否する。

融合yawはmapの+xから反時計回り、GNSS headingは真北から時計回り。
前方ANT1・後方ANT2の配置ではGNSS方位へ180°の補正を適用する。
受信機側で補正する場合は二重適用しない。単体fusion.launchの補正既定値は0°である。

## 起動・操作・終了

同梱地図の起動は[README](../README.md)、実機準備は[実機ハードウェア統合](実機ハードウェア統合.md)を参照する。

```bash
ros2 run icart_bringup run_session --session <session.yaml> --environment simulation --start-ui
```

`run_session` は入力を検査してDDS domainを設定し、launchを実行する。
実機は `--environment real` とする。環境切替は全停止後に行う。
直接launchや単独UIを使う場合は、親シェルのROS_DOMAIN_IDも設定に合わせる。

CLI一括起動ではUIからスタックを重複起動せず、manual_startだけを操作する。
UIで起動・全停止を管理する場合は、UI単独起動後、対応プリセットと設定を選ぶ。
自律運用はmanual_start待ち、採取用survey.launchは初期manualかつ自律復帰無効である。
L1保持で手動操縦し、採取ボタンは0/1/2/3を使う。

主要子プロセスの終了で共通launchも終了する。
Joy・manual_teleop・mux・自己位置配信元を二重起動しない。

## 監視・停止条件

- GNSS融合の初期位置には良好FIXと方位、重力整列の準備完了が必要。ICPは良好FIX＋方位または手動初期位置で地図照合を成立させる。
- navigatorの位置・車輪odom期限は1秒。実機は単調時計、模擬はROS時計で監視する。
- 実機自律走行は障害物ヒント未受信・1秒途絶でも停止する。
- 車輪ドライバのMotionLimits監視は実機で有効にし、模擬構成では無効にする。
- 融合の全運動入力途絶時は自律指令をゼロにする。LIOから車輪へ退避してもURG停止を維持する。
- 手動指令はdeadmanを使うが、自律側の障害物監視・融合減速を通らない。

UIの表示値だけで入力が新鮮と判断せず、受信期限と診断を確認する。
融合位置の絶対精度や車輪スリップを、これらの監視だけで保証するものではない。

## 確認方法

`tests/` で設定生成・相対パス・未設定値・domain不一致・座標整合・起動構成を確認する。
`tools/evaluate_console_session.py` は模擬ROS入力とUIのSnapshot・開始操作を結合確認する。
実機では接続・取付・方位・時計・停止距離を確認する。
生成した地図やログはGitへ追加しない。

## 実機の時刻同期ゲート

通常構成は外部NTP→PC chrony→software PTP→MID360。
GNSSはGGAの測定時刻とRMCの日付から測定UTCを保持する（gnss_utc、transport_delay_ms=0）。
RMCのchrony SOCKはnoselectとし、USB到着時刻でPCを合わせない。

GUIの実機／実機（融合）の手動走行はreal_survey→survey→bringup、
自律走行はrecorded_route→bringupの共通経路を通る。
hardware_configを持つ共通実機起動はGNSS/MID360のみ先に起動し、clock_gateでNTP/PTP成立を待つ。
成立後に車輪ドライバ、FAST-LIO、融合、mux、navigatorを起動する。センサは重複起動しない。
同期ゲートはclock_source=ntp・同じboot ID・更新3秒以内の状態のみ受理し、180秒待って未成立なら起動中止。
運用中の条件喪失は共通スタックをshutdownする。復帰後の走行再開は利用者が再起動する。
シミュレーションおよび個別の診断用launchはこの共通ゲートの対象外。

サービスのNTP条件は選択サーバの直近応答成功、鮮度2ポーリング周期以内（最大256秒）、
正常Leap、残補正5 ms以下、推定誤差上限35 ms以下。
点群・IMUはtime_type=1、カーネル受信差-1〜10 ms、継続受信を確認する。
時刻逆行は過去最大値から0.1 msまで許容しminor_backwardsへ記録する。
それ以上の逆行は10秒の抑止。繰り返す微小逆行が累積した場合も検出する。
データの時刻そのものは補正・書換しない。readyは絶対精度の認定ではない。

初回はprepare_clock_hostでchronyを準備した後、管理者が
`sudo bash src/rtk_gps_um982/tools/install_clock_service.sh enp0s31f6 192.168.1.201`
を実行する。以後はOS起動時にサービスが立ち上がり、GUIでsudoや個別PTP起動は不要。
既存GNSSドライバは通常起動前に停止し、シリアルを二重に開かない。

GUIは実機モードの全タブ上部に同期警告を表示する。NTP未成立・PTP配信待ち・センサ同期待ち・
状態更新停止を区別し、正常復帰で消す。時計や指令の変更は警告表示では行わない。
PC起動後のNTP同期・PTP配信はGUI操作不要。ネット接続後に自動で進み、
GUIの一斉起動からセンサ取得と同期ゲート待ちへ進む。
[時刻同期の運用と確認](../../rtk_gps_um982/docs/PTP試験手順.md)を参照する。
