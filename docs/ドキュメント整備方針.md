# ドキュメント整備方針

## 1. 目的

本書は、このリポジトリで扱う文書の種別、種別ごとの配置・章立て・記載粒度・更新方針を定める。

文書が増えるほど「どこに書くか」「どこまで書くか」「いつ消すか」の判断がぶれ、同じ内容が
複数箇所に分散する。種別を先に決め、種別ごとに責務を固定することでこれを防ぐ。

本文に何を書き、何を書かないかは `CLAUDE.md` と `AGENTS.md` の「ドキュメント記述方針」を、
種別ごとの章立て雛形は `.claude/skills/documentation` を正とする。
本書はそれらの上位にある「文書の分類」と、種別ごとの粒度を定める。

---

## 2. 文書種別

このリポジトリで扱う文書は次の 5 種別に分類する。どの種別にも当てはまらない文書は作らない。

| 種別 | 役割 | 配置 | 寿命 |
| --- | --- | --- | --- |
| 規約 | 従うべき規則を定める | `docs/` | 恒久。改訂して使い続ける |
| アーキテクチャ設計 | 複数パッケージにまたがる構造と責務分担 | `docs/` | 恒久。現状に追従させる |
| 詳細設計書 | 1 パッケージの内部設計 | `src/<pkg>/docs/` | 恒久。現状に追従させる |
| 運用手順 | 導入・起動・操作の手順 | `README.md` / `src/<pkg>/README.md` | 恒久。現状に追従させる |
| 検討資料 | 正式文書になる前の分析・提案・レポート | `docs/notes/` | 決着したら削除する |

### 2.1 恒久文書と検討資料の区別

上表の上 4 種別は**現状を書く**恒久文書であり、実装が変われば書き換える。読み手はこれらを
現行仕様として扱ってよい。

検討資料だけは**ある時点の分析を書く**文書であり、現状追従の義務を負わない。読み手が現行仕様と
誤認しないよう、3.5 節の規則で隔離する。決着したら内容を恒久文書へ反映し、ファイルを削除する。

選択肢の比較と判断の記録を目的とした独立の文書は作らない。判断を支える制約・限界・適用条件は、
その判断が効いている恒久文書の本文へ書く。採用しなかった案は本文に含めない（ドキュメント記述方針）。

ある時点の観測を凍結して残す文書も作らない。確認した条件と結果のうち現在も有効なものは
恒久文書の確認方法として書き、過去の測定値は git 履歴が持つ。

---

## 3. 種別ごとの目的と粒度

各種別の**章立ての雛形**は `.claude/skills/documentation` の `assets/` に置く。
本章は雛形を再掲せず、雛形が満たすべき目的と、章立てだけでは表せない粒度の原則を定める。

| 種別 | 雛形 |
| --- | --- |
| 規約 | `assets/convention_template.md` |
| アーキテクチャ設計 | `assets/architecture_template.md` |
| 詳細設計書 | `assets/detailed_design_template.md` |
| 運用手順 | `assets/operation_readme_template.md` |
| 検討資料 | `assets/note_template.md` |

### 3.1 規約

**目的**: 個別の事例ではなく、判断の原理を与える。読み手が未知のケースに直面したときに
自力で判断できる状態にする。

**粒度の原則**: **個別対象の一覧表を作らない。** 一覧表は実装から必ず乖離する。個別の性質は
対象そのもの（`.msg` のコメント、設定ファイルのコメント）に宣言させ、規約は導出規則だけを
持つ。

例: `docs/トピック通信規約.md` は QoS を topic ごとに列挙せず、配信様式から QoS を導出する
規則だけを定め、個々の配信様式は `.msg` の先頭コメントに宣言させている。

### 3.2 アーキテクチャ設計

**目的**: パッケージ間の責務分担、データの流れ、境界の定義を示す。

**粒度の原則**: パッケージ内部の実装には踏み込まない。それは詳細設計書の役割である。
「どのパッケージが何を担い、何を約束するか」までを書く。

### 3.3 詳細設計書

**目的**: 1 パッケージの内部設計を、実装を読まずに把握できる状態にする。

**粒度の原則**: クラス名・関数名の列挙はしない。それはコードとドキュメントの二重管理になり、
必ず乖離する。書くべきは**コードを読んでも分からないこと**に限る。

- なぜその構造を選んだか
- どの制約があってその実装になっているか
- 外部との契約（topic / パラメータ / ファイル形式）
- 状態遷移と例外条件
- 確認方法と、確認していない範囲

最後の項目は独立した文書にしない。確認方法は設計と一体であり、分けると実装変更時に
片方だけが更新される。「何を確認していないか」を省かない。これが無いと読み手に過剰な
信頼を与える。

**同じ事実を複数の章へ書かない。** 片方だけが更新されて矛盾する。設定値の既定値と
選定理由、QoS の割り当てと選定理由、異常時の挙動、既知の欠陥の説明は特に割れやすい。
章立ての雛形が置き場所を 1 箇所に固定しているため、それに従う。一覧は README を正とし、
設計書では再掲しない。

### 3.4 運用手順

**目的**: 読み手が手順どおりに実行すれば動く状態にする。

**粒度の原則**: README に設計を書かない。設計は詳細設計書へ置き、README からリンクする。
README が 300 行を超えたら、設計が混入していないか点検する。

### 3.5 検討資料

**目的**: 恒久文書へ反映する前の分析・提案・レポートを共有する。反映が済むまでの一時的な
置き場であり、置き場が無いために恒久文書へ混入することを防ぐ。

**配置と命名**: `docs/notes/<YYYY-MM-DD>_<主題>.md`。**日付をファイル名の先頭に置く。**
一覧しただけで古さが分かる状態にするためである。「現状評価」のような、いつの現状か分からない
名前を使わない。

**冒頭に必須のヘッダ**: 状態・作成日・対象コミット・決着期限の 4 行を置き、直後に結論を
3 行以内で書く。読み手が全文を読まずに要否を判断できるようにする。以降の構成は主題に
応じて自由とする。

**規則**:

1. 恒久文書（規約・アーキテクチャ設計・詳細設計書・運用手順）から `docs/notes/` へリンクしない。
   参照は検討資料 → 恒久文書の一方向のみとする。恒久文書から参照すると、消すと壊れるため
   消せなくなる
2. 検討資料は現状追従の義務を負わない。トピック名・パラメータ名・リンクの整合性検査の
   対象外とする
3. 決着したら内容を恒久文書へ反映し、**ファイルを削除する**。「状態: 採用」と書いて残さない。
   判断の記録は git 履歴が持つ
4. 決着期限の超過は `tools/check_docs.py` が検出して報告する。期限を延ばす場合は期限行を
   書き換える。延長した事実が git diff に残る

**粒度の原則**: 検討の**時系列**ではなく**判断構造**を書く。「最初に A を試したが駄目だったので
B にした」は経緯であり、書くべきは「B を採る。A は〈理由〉により要件を満たさない」である。

恒久文書へ反映する際、採用しなかった案は持ち込まない。持ち込むのは、
現在の構成を支える制約・限界・適用条件だけである。

## 4. 書いてはならないこと

本文に何を書き、何を書かないかは `CLAUDE.md` と `AGENTS.md` の「ドキュメント記述方針」を
正とする。本節は再掲せず、経緯の記述を現在の仕様の記述へ変換する方法だけを示す。

```
削除前: 当初は JSON で配信していたが、スキーマが実装にしか存在しないという指摘を
        受けて型付きメッセージへ修正した。

書き換え後:
        融合状態は型付きメッセージで配信する。スキーマが送信側の実装にしか
        存在しない形式は、購読側が独自に検証を実装することになるため使わない。
```

変換の要点は、**主語を作業から仕様へ移すこと**である。「〜へ修正した」は作業の記述であり、
「〜で配信する」は仕様の記述である。削った経緯のうち、現在の仕様を支えている制約
（この例では「スキーマが送信側の実装にしか存在しない」）だけを仕様の理由として残す。

本書に固有の禁止事項は次のとおり。

- リポジトリ外の絶対パス
- コードから自明な内容の言い換え
- 他文書と重複する内容（リンクで参照する）
- リンクの一覧だけを持つ文書（6 章）

## 5. 命名と配置

### 5.1 ファイル名

- 日本語名を基本とする。内容を表す名詞句にする。
- **ファイル名と本文の見出しを一致させる。** 中身だけを書き換えて名前を据え置くと、
  読み手はファイル名から内容を判断できなくなる。
- 作業単位を名前に含めない。`_phase1` `_完全版` `_input` `_開発指示書` `_報告書` のような、
  実装完了後に意味を失う語を使わない。
- 同一対象の文書を複数作る場合は、扱う観点で分ける。
  `robot_console_アーキテクチャ設計.md` と `robot_console_画面機能設計.md` のように分け、
  phase や版で分けない。
- 検討資料は 3.5 節の命名に従い、日付を先頭に置く。

### 5.2 配置

`CLAUDE.md` の規約に従う。

- ワークスペース全体に関わる文書 → `docs/`
- 特定パッケージに閉じる文書 → `src/<pkg>/docs/`
- 検討資料 → `docs/notes/`
- メーカー資料・外部仕様 → `docs/references/`

判断に迷う場合は「この文書はパッケージを削除したら一緒に消えるか」で判断する。消えるなら
`src/<pkg>/docs/`、残るなら `docs/`。

### 5.3 パッケージごとの必須文書

| 文書 | 必須条件 |
| --- | --- |
| `README.md` | 全パッケージ。interface 定義のみのパッケージも含む |
| `docs/<名前>_詳細設計書.md` | ノードまたは非自明なロジックを持つパッケージ |

interface 定義のみのパッケージ（`tc_*_msgs`）は、README でメッセージ一覧と用途を示す。
各メッセージの配信様式・レートは `.msg` のコメントに書き、README では重複させない。

## 6. 作業単位の文書の扱い

実装の指示・入力として作られた文書（`_input`、`開発指示書` など）は、実装が完了した時点で
役目を終える。成果物である設計書が正になるため、次のいずれかを行う。

1. 設計書へ未反映の内容があれば、設計書へ移す
2. 現在の構成を支える制約が含まれていれば、その制約が効いている恒久文書へ移す
3. 上記を終えたら削除する

「後で参照するかもしれない」を理由に残さない。git 履歴から復元できる。

リンクの一覧だけを持つ文書も作らない。読み手を 1 段余計に経由させる割に、リンク先が
増減しても追従されず、どこが正かを曖昧にする。索引が必要な範囲は `docs/README.md` と
各パッケージの `README.md` に限る。
