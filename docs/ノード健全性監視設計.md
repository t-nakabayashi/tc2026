# ノード健全性監視設計

## 1. 目的と範囲

本書は、`robot_console` がシステム内の各ノードの稼働状況を把握する方式を定める。

対象は次の 2 系統である。

| 系統 | 手段 | 判定の性質 |
| --- | --- | --- |
| 外形監視 | `health_topics` の受信鮮度 | 他律的。配信側の協力を必要としない |
| 自己申告 | `/diagnostics`（`diagnostic_msgs/DiagnosticArray`） | 自律的。ノード自身が理由を申告する |

トピックの配信様式・QoS・命名の規約は [トピック通信規約.md](トピック通信規約.md) に従う。

---

## 2. 二層構成の理由

周期的な業務出力があるノードは外形監視を基礎に自己申告を重ねる。周期出力のないノードは、診断の受信鮮度で生存を判定する。

```
  自己申告 (/diagnostics)   … なぜ不調か。外形に出ない内部状態
──────────────────────────
  外形監視 (health_topics)  … 生きているか。全ノード共通の土台
```

### 2.1 外形監視を自己申告で置き換えられない理由

- **停止したノードは自分の停止を報告できない。** クラッシュ・ハングした瞬間に自己申告も止まる。
- **自己申告の周期配信は業務出力の停止を検出できない。** 診断タイマが回っていることが示すのは
  spin ループの生存だけである。センサ読み出しスレッドが停止して業務 topic が途絶えても、
  診断は正常を出し続ける。「publisher は存在するがデータが流れない」は実際に起きる故障であり、
  これを外形から捉えられるのは受信鮮度だけである。
- **外部パッケージは自己申告できない。** `FAST_LIO`、`livox_ros_driver2` は submodule の外部
  パッケージであり、診断配信を組み込むには fork 改変が必要になる。

### 2.2 自己申告が担う範囲

自己申告では以下を扱う。

- 不調の理由（シリアルポート未接続、NTRIP 認証失敗、パラメータ不正など）
- topic は正常に出ているが品質が劣化している状態
- 周期的な業務 topic を持たないノードの生存（診断受信の途絶も監視する）

### 2.3 実ノードとシミュレータを区別しない

外形監視は topic 名で判定するため、実ノードと、同じ topic を配信するシミュレータを区別
しない。シミュレーション構成では `ypspur_ros2` や `rtk_gps_um982` の profile が、実体が
`ros_gz_bridge` や `gnss_simulator` であっても `RUNNING` と表示される。

これは仕様として受け入れる。実機構成では当該 topic を配信するのは実ノードだけであり、
区別のために診断のノード名を判定条件へ加えると、profile ごとの対応表が増えて構成変更時の
保守点が増えるためである。

### 2.4 判定に使わない情報

受信したメッセージの**内容の妥当性は判定しない**。`/scan` の range が妥当か、odom が発散して
いないかといった判断は各ノード自身の責務であり、`robot_console` が各ノードのドメイン知識を
持つことになるため行わない。内容に基づく異常は、当該ノードが自己申告する。

## 3. 外形監視（health_topics）

### 3.1 定義

`health_topics` は `robot_console` の `config/node_launch_profiles.yaml` に profile 単位で
定義する、**その profile を起動したときに正常なら配信されているはずの既存 topic** の一覧である。
健全性のために新設する topic ではない。

### 3.2 スキーマ

```yaml
    health_topics:
      - topic: /route_state
        type: tc_route_msgs/msg/RouteState
        rate_hz: 1.0
      - topic: /manager_status
        type: tc_route_msgs/msg/ManagerStatus
        rate_hz: 5.0
```

| キー | 必須 | 内容 |
| --- | --- | --- |
| `topic` | 必須 | 解決済みの絶対トピック名 |
| `type` | 必須 | `<package>/msg/<Name>` 形式のメッセージ型名 |
| `rate_hz` | 必須 | 保証される最低レート [Hz]。正の有限値。鮮度しきい値の導出元 |

型名を併記する理由は、購読生成にメッセージ型が必要なためである。実行時に
`get_publishers_info_by_topic()` で型を解決する方式は、publisher が現れるまで購読を生成できず、
定期的な再解決処理が必要になるため採らない。

`rate_hz` を併記する理由は、しきい値の導出元を機械可読にするためである。`.msg` コメントの
公称レート宣言は人間向けであり、そのままでは実装が参照できない。

`rate_hz` には `.msg` の公称レートそのものではなく、**動作条件によらず保証される最低レート**を
書く。`/fusion/status` は通常 50 Hz で配信されるが、初期化待ちの間は 1 Hz へ落ちる。公称値の
50 を書くとしきい値が 0.5 秒となり、正常な初期化待ちを途絶と誤判定する。

### 3.3 登録できる topic の条件

**配信様式が `stream` の topic だけを登録する。** `latch` と `event` は登録しない。

- `latch`（`/active_route`, `/mission_info`）は、値が変化しない限り配信されないことが正常である。
  鮮度判定に入れると、正常動作中のノードが恒常的に異常と判定される。
- `event`（`/manual_start`, `/road_blocked`）も同様に、無音が正常である。

`/active_target` と `/route/active_target_llh` は目標がない間に配信されないため登録しない。
`route_follower` は周期的な `/follower_state`、地理座標変換は `/localization/pose_llh` を監視する。

`route_manager` のように `latch` と `stream` の両方を配信するノードは、`stream` 側
（`/route_state`, `/manager_status`）だけを登録すれば死活を判定できる。

### 3.4 購読方式

- **実受信を根拠とする。** publisher の存在確認（`count_publishers()`）は「publisher はあるが
  データが流れない」故障を検出できないため使わない。
- **`raw=True` の購読とする。** `rclpy` の raw subscription はメッセージを `bytes` のまま渡すため、
  デシリアライズを回避できる。健全性判定に必要なのはコールバックが呼ばれた事実だけであり、
  `/scan` のような高レート topic でも負荷を無視できる。
- QoS は `stream` の既定（`BEST_EFFORT` / `VOLATILE` / `KEEP_LAST(1)`）で統一する。
  `BEST_EFFORT` 購読は `RELIABLE` 配信元とも互換であるため、配信側の設定を調べる必要がない。
- 表示のために既に購読している topic にも、健全性用の購読を別に張る。表示側の購読は remap
  対象の相対名で、鮮度キーも表示都合の名前（`obstacle_hint`、`image.sensor_viewer` など）で
  あり、profile 定義の絶対 topic 名と一対一に対応しないためである。購読を共用するには表示側の
  全経路へ健全性キーの記録を追加する必要があり、記録漏れがそのまま誤った異常判定になる。
  重複する購読は raw・`BEST_EFFORT`・depth 1 であり、コストよりも判定の確実性を優先する。

### 3.5 鮮度しきい値

`health_topics` の `rate_hz` から、[トピック通信規約.md](トピック通信規約.md) 3 章の導出規則
（`stale_sec = max(3 / rate_hz, 0.5)`、`lost_sec = max(10 / rate_hz, 2.0)`）で算出し、
`FreshnessMonitor.set_threshold()` へ登録する。しきい値そのものを profile 定義に書くことはしない。

### 3.6 起動猶予

profile の起動直後は、まだ topic が流れていないことが正常である。起動を要求してから
`startup_grace_sec`（既定 10 秒）の間は、未受信（`UNKNOWN`）を異常と判定しない。

## 4. 健全性の合成規則

profile ごとの表示状態は、起動管理（`LaunchManager` が管理する子プロセスの状態）と
トピック鮮度の両方から決める。

### 4.1 トピック鮮度の集約

profile に属する `health_topics` 各々の `FreshnessLevel` を、次のとおり 1 つへ集約する。

| 条件 | 集約結果 |
| --- | --- |
| すべて `OK` | `OK` |
| すべて `OK` ではなく、1 つ以上が `OK` または `STALE` | `STALE` |
| すべて `LOST` または `UNKNOWN` | `LOST` |
| 起動猶予期間内で、すべて `LOST` または `UNKNOWN` | `UNKNOWN` |

部分的な途絶を `STALE` として残すのは、GNSS 不感帯で `/fusion/status` は出ているが
`/rtk_gps/fix` が途絶える、といった部分故障を潰さずに表示するためである。

### 4.2 起動状態との合成

| 子プロセス状態 | 集約鮮度 | status | health | 備考 |
| --- | --- | --- | --- | --- |
| `RUNNING` | `OK` | `RUNNING` | `OK` | 正常 |
| `RUNNING` | `STALE` | `RUNNING` | `STALE` | 部分途絶 |
| `RUNNING` | `LOST` | `ERROR` | `LOST` | プロセスは生存するが出力が無い |
| `RUNNING` | `UNKNOWN` | `STARTING` | `UNKNOWN` | 起動猶予期間内 |
| `STARTING` | 任意 | `STARTING` | `UNKNOWN` | |
| `STOPPED` | `OK` / `STALE` | `RUNNING` | 集約値 | GUI 外で起動された（4.3） |
| `STOPPED` | `LOST` / `UNKNOWN` | `STOPPED` | `UNKNOWN` | |
| `ERROR` | 任意 | `ERROR` | `LOST` | 起動失敗・異常終了 |

`health_topics` が空で `diagnostic_nodes` が設定されている profile は、各ノードの診断受信鮮度を
同じ規則で集約する。両方が未設定の場合のみ子プロセス状態だけで判定する。

### 4.3 GUI 外で起動されたノード

子プロセス状態が `STOPPED` でも `health_topics`（空の場合は指定ノードの診断）が受信できている場合、そのノードは
`robot_console` 以外の手段（端末からの `ros2 launch`、別ホスト）で起動されている。
この場合 `status` を `RUNNING` とし、`externally_started` フラグを立てる。

`externally_started` は表示色を変えず、チップの tooltip に表示する。停止操作は
`robot_console` が起動していない子プロセスに対しては行えないため、UI 上も停止要求は送らない。

## 5. 自己申告（/diagnostics）

### 5.1 配信仕様

| 項目 | 規定 |
| --- | --- |
| topic | `/diagnostics` |
| 型 | `diagnostic_msgs/msg/DiagnosticArray` |
| 配信様式 | `stream` |
| 公称レート | 1 Hz |
| QoS | `stream` の既定（`BEST_EFFORT` / `VOLATILE` / `KEEP_LAST(1)`） |
| 対象 | 自作パッケージのノード。外部パッケージは対象外 |

`DiagnosticArray.header.stamp` には配信時刻を入れる。
配信側はノードごとの全診断観点を1つの配列にまとめる。受信側は配列に登場したノードの
診断を丸ごと置き換え、含まれなくなった観点を取り下げとして削除する。他ノードの診断は保持する。
最後の観点を取り下げて配信がなくなった場合や空配列の場合は、受信期限で失効する。

受信時刻は `time.monotonic()` で記録する。1 Hz 配信に対して最終受信から3秒を超えると
`STALE`、10秒を超えると `LOST` とし、期限を超えた診断のレベルと文言は表示判定から外す。
ROS時刻やPCの壁時計の補正はこの期限に影響しない。

### 5.2 DiagnosticStatus のフィールド規約

| フィールド | 規約 |
| --- | --- |
| `name` | `<ノード名>/<観点>` 形式。ノード名は `Node.get_name()` の値とする |
| `level` | `OK` / `WARN` / `ERROR` / `STALE` |
| `message` | 日本語の 1 行。GUI の tooltip にそのまま表示する |
| `hardware_id` | 実デバイスを持つノードのみ設定する。ソフトウェアのみのノードは空文字 |
| `values` | 補助情報。**制御判断には使わない**（5.4） |

`name` の先頭を `profile_id` ではなくノード名とする理由は、ノードが自分の属する profile を
知り得ないためである。`icart_recorded_route` のような複合 profile は複数ノードをまとめて起動し、
同じノードが単独 profile としても起動される。

profile とノードの対応は、配信側ではなく `node_launch_profiles.yaml` の `diagnostic_nodes` に
持たせる。

```yaml
    diagnostic_nodes: [route_manager_node]
```

`diagnostic_nodes` が空の profile は診断による補正を受けない。

### 5.3 観点の名前

| 観点 | 内容 |
| --- | --- |
| `liveness` | ノードの生存と主処理の進行状況。全ノードが最低 1 つ持つ |
| `device` | シリアルポート、カメラ、LiDAR など外部デバイスの接続状態 |
| `quality` | 出力の品質劣化（融合モードの縮退、検出信頼度の低下など） |

### 5.4 values を制御に使わない理由

`diagnostic_msgs/KeyValue` は `string` / `string` の対であり、数値を載せても型は文字列である。
ここに制御依存を持たせると、値の意味・単位・妥当範囲が購読側の暗黙知になり、
`std_msgs/String` に JSON を載せるのと同じ問題が再発する。

制御判断に使う値は、[トピック通信規約.md](トピック通信規約.md) 8 章のとおり型付きメッセージで
配信する。`/diagnostics` は表示と事後解析の経路に限定する。

### 5.5 健全性への反映

`/diagnostics` は 4 章の合成結果を次のとおり補正する。

| `level` の最悪値 | 補正 |
| --- | --- |
| `OK` | 補正しない |
| `WARN` | `health` が `OK` の場合に `STALE` へ下げる |
| `ERROR` | `status` を `ERROR`、`health` を `LOST` にする |
| `STALE` | `health` が `OK` の場合に `STALE` へ下げる |

`message` は `HealthSummaryView.diagnostic_message` として保持し、チップの tooltip に表示する。

`health_topics` がある場合は外形監視を生存判定に使用し、診断の不在だけでは異常としない。
周期出力がなく `diagnostic_nodes` が設定された認識ノード等は診断の受信鮮度を使う。
GUIから起動した場合、10秒の起動猶予を過ぎて未受信または全ノードが期限切れなら `ERROR/LOST` とする。
外部起動の場合、受信中は `RUNNING`、3秒を超える遅延は `STALE`、全ノードが10秒を超えて
途絶すると `STOPPED/UNKNOWN` とする。配信再開時は自動的に現在の診断から再判定する。
診断タイマーだけが動く業務処理の停止は、業務出力監視またはノード固有の自己診断がなければ検出できない。

## 6. 実装配置

| 役割 | 配置 |
| --- | --- |
| 診断配信の共通ヘルパ | `src/tc_diagnostics/` |
| profile と `health_topics` の定義 | `src/robot_console/config/node_launch_profiles.yaml` |
| profile 定義のロードと検証 | `src/robot_console/robot_console/core/launch_profile.py` |
| 健全性用の購読生成 | `src/robot_console/robot_console/ros/console_node.py` |
| 鮮度の保持と判定 | `src/robot_console/robot_console/core/freshness.py` |
| 健全性の合成 | `src/robot_console/robot_console/core/node_health.py` |
| 表示 | `src/robot_console/robot_console/ui_qt/widgets/node_health_card.py` |

合成規則（4 章）は ROS 非依存の純関数として `core/node_health.py` に置き、`ConsoleCore` から
呼び出す。ROS なしで単体テストできる状態を保つ。

### 6.1 共通ヘルパの責務

`tc_diagnostics` は次だけを提供する。

- `/diagnostics` publisher と 1 Hz タイマの生成
- `DiagnosticStatus` の組み立てと `name` 規約の適用
- ノードが申告する `level` / `message` / `values` の受け取り

各ノードの判定ロジックは持たない。`diagnostic_updater` を使わないのは、依存とノードごとの
定型コードを増やさずに、本書の `name` 規約を 1 か所で強制するためである。
