# 実機走行用ルートと選択課題A

状態: 検討中
作成日: 2026-10-18
対象コミット: c89d563
決着期限: 2026-11-15

回避幅を与えた経路は `tsukuba2026` として選べる配置になったが、実機では走行していない。
選択課題Aのエリアは事前計測が禁止されているため、走行ログから固定経路を作る今の手法を
適用できない。駐車場内の通路網を可変ブロックとして与える方針としたが、通路網の作り方と
現地の情報が揃っていない。課題A対応・非対応の2つのルートは、経路CSVを
分割点で2ファイルへ分けて持つ。分割点とエリアの通路網は決まったが、分割の作業と、
エッジごとのwaypoint生成は済んでいない。これらが未決である。

## 背景

つくば2026コースの経路は `src/route_survey/results/tsukuba2026_waypoints.csv` にある。
3,704点すべてに左右の回避幅が入っており、求め方は
`src/route_survey/docs/waypointの回避幅を求める手順.md` にまとめてある。

この成果物を `src/route_planner/routes/tsukuba2026/` へ配置し、全域を固定ブロック1つと
する課題A非対応のルートとして登録した。内容と手順は
[本走行コース](../../src/route_planner/routes/tsukuba2026/README.md) にある。
2025年のコースは削除済みである。

## 未決1: 実機走行による確認

登録済みのものは次のとおりである。

- `src/route_planner/routes/tsukuba2026/fixed/waypoints.csv` と `route_config.yaml`
- `src/route_planner/params/tsukuba2026.yaml` と
  `src/route_manager/params/tsukuba2026.yaml` の同名の起動カード。`robot_console` は
  両方の `params/` を走査して起動カードを検出するため、片方だけでは選べない

現在の停止属性は、16点が `line_is_stop`、`signal_is_stop` は全点0である。信号交差点の

`route_follower` は `signal_stop` の waypoint を `manual_start` に加え `sig_recog==1`

経路そのものは `src/route_survey/tools/build_route.py` が作る。同じ入力での再実行が
登録済みの経路とバイト単位で一致することを確認してある。停止属性を変える場合は、
この生成側を直して再生成する。

## 未決2: 選択課題A（事前計測なしエリア通過）

公式の条件は次のとおりである。

- 市役所職員駐車場3の内部。本走行で**1回だけ**走行できる
- 事前にロボットを走らせること、カメラ・LiDAR・メジャー等で計測することはできない。
  チームメンバーの目視確認と既存の地図サービスの利用は認められる
- 手前の道路端から安全を確認し、ゲートから進入、チェックポイントを通過し、再びゲートから
  退出する。チェックポイントの通過方向は問わない
- 停車中の車両の0.5 m以内に近づいた場合は失敗とする
- 自律走行を継続できなくなった場合も失敗とする。ただし自律走行自体の失敗とはならず、
  非常停止後にゲート外へ戻してオペレータ操作で再開できる
- 駐車車両や緑ロードコーンにより通路が塞がれている可能性がある

**事前計測が禁止されているため、走行ログから地図と経路を作り、区間ごとに回避幅を与える
今の手法はこのエリアに適用できない。** 手順の入力である「同じ走行ログに由来する地図と
経路」をそもそも作れない。

回避幅は駐車場の通路として左右1.5 mを与える。車体幅0.6 mに対し、車体端で1 m強の
横移動を許す値である。通路幅は航空写真で3.7〜4.9 mであり、通路が狭いときは実測空き幅が
上限を縛る。停車車両からの離隔は回避幅ではなく、次の設定で決まる。

通路の封鎖は、看板ではなく物理的な通行可否で扱う。2026年は決まった様式の経路封鎖看板が
設置されないため、`road_blockage_detector`（看板のYOLO検出）は課題Aでは使わない。
滞留を `route_follower` が検知して `/report_stuck` を出し、`route_manager` が可変区間に
対して `/update_route` を呼び、`route_planner` が封鎖エッジを除いて再探索する経路が
既にある。

`build_route.py` の `optional_tasks.A` は `enabled=False` であり、理由として
「事前計測なし区域。固定計測ルートを作成しない。」を保持している。

**方針は、課題Aの区間を可変ブロックとし、駐車場内の全通路をノードとエッジで定義する形
とする。** 固定の1本道ではなく通路網を与えるため、塞がれた通路があれば `/update_route`
で別の通路を選び直せる。公式条件でも目視確認と既存の地図サービスの利用は認められている。

### 通路網をどこから作るか

`route_planner` の可変ブロックは `nodes.csv`（`id,lat,lon`）、`edges.csv`
（`source,target,waypoint_list,reversible,weight_factor`）、エッジごとの waypoint CSV を
必要とする。これらを地図サービスの座標から作れるかを確かめた。

- 対象エリアは、庁舎東通りの**北側**、つくば警察署研究学園交番（36.083776,
  140.079453）とつくば研究学園郵便局（36.083633, 140.079415）の**西隣**の駐車場である。
  公式の課題Aページが載せる航空写真の図と、地理院写真タイルの同じ範囲を並べて同定した。
  北東角が斜めに切り取られた形、西隣の植栽付き駐車場、南側の歩道と車道の並びが一致する
- 公式図のゲートは区画の**南西角**にあり、本走行コースの `E03`（庁舎東・車両出入口3、
  36.08339818, 140.07834776）と同じ位置である。往路は庁舎東通りの歩道を東へ進むため、
  ここで左折して進入する。公式図のチェックポイントは北東の斜め境界沿いにある
- OpenStreetMap にはこの区画の通路中心線が `service=parking_aisle` として登録されている
  （way 383552873、東西111 m・南北93 m）。分岐点と端点をノードに取ると**15ノード・
  19エッジ・通路総延長562 m**の連結グラフになる。道路への接続点は2か所あり、それぞれ
  `E03`（車両出入口3）と `E04`（車両出入口4）の位置に対応する
- OSMの線形は航空写真からのトレースであり、測量値ではない。通路中心線の位置誤差は
  数メートルの桁で入りうる。写真と比べると通路の登録にも粗さがあり、そのままでは
  駐車枡の列と列の間をすべて拾えていない。**ノードとエッジは通路網の接続関係と概略線形を
  与えるものとして扱い、停車車両からの離隔は走行時の観測で決める。**不足する通路は
  航空写真から足す
- Googleマップから座標を機械的に取り出すことはしない。Google Maps Platform の利用規約は
  コンテンツの抽出・保存・派生データの作成を禁じている。チームメンバーが画面で目視確認する
  用途に留める。機械処理の入力は、このリポジトリで既に出典とライセンスを記録している
  OpenStreetMap（ODbL）と航空写真タイルを使う

### OSMと航空写真から、どこまで寄せられたか

観測値を得る前に、OSMの通路網と航空写真から位置を推定した。観測値と突き合わせた
結果は次のとおりで、**OSMをそのまま使うと2〜3 mずれる**。

| 推定方法 | 観測値との差（中央値 / 最大） |
| --- | --- |
| OSMの原位置 | 2.43 m / 3.44 m |
| OSM全体を東+2.5 m・北+1.2 m並進 | **0.85 m / 1.83 m** |
| エッジごとに航空写真の通路中心へ吸着 | 1.45 m / 1.83 m |

OSMのずれは向きによらない一様な並進で説明でき、並進だけで1 m以下に入る。航空写真の
通路中心への吸着は、駐車車両の寄り方に引かれて過剰に動く箇所があり、並進を上回らない。
**別の区画で同じ作業をする場合は、OSMの一様並進を基本とし、航空写真は通路の有無と
幅の確認に使う。**

航空写真から読み取った通路幅は3.7〜4.9 mである。失敗条件が停車車両から0.5 mで
あることを踏まえると、**地図由来の中心線だけでは条件を満たせない。** 通路網の役割は
接続関係とどの通路を通るかの指定に留め、横位置は走行時の観測で決める。

### 停車車両からの離隔を決めているもの

**実機の自律走行では `lidar_layer_slicer` は起動しない。** `icart_bringup` の共通起動は
AI助言を使うときだけこのノードを起動し、実機では `use_ai_advice=true` を無視する。
したがって `/obstacle/layers` は配信されず、`route_follower` の実測空き幅による上限は
効かない。`lidar_layer_slicer` の `side_margin_m` は実機の離隔を決めていない。

実機で横移動量を決めているのは次の2つである。

- `obstacle_monitor` の回避量の提案。片側の点を内側から見て、`robot_width_m`（0.8 m）
  ＋その半分より広いギャップを探し、**ギャップの内側の縁から `robot_width_m` だけ寄せた
  位置**を提案する。下限は `avoid_offset_min_m`（0.75 m）
- `route_follower` のクランプ。提案値を waypoint の回避幅と `avoid_max_offset_m` で
  打ち切る。打ち切り後が `avoid_min_offset_m`（0.35 m）に満たない側は回避しない

提案の仕方は2通りある。車体全幅0.6 m、`robot_width_m`=0.8 mで計算した結果である。

- **車体が通れる幅のギャップを見つけて、その内側を通る場合**。ギャップの判定閾値は
  `robot_width_m` + その半分 = 1.2 mである。内側の縁から0.8 m寄せるので、内側の障害物
  からは 0.8 − 0.3 = **0.5 m** 残る。外側の障害物からは「ギャップ − 1.1 m」であり、
  ギャップ1.2 mで0.1 m、1.6 mで0.5 m、2.0 mで0.9 mとなる
- **外側に観測点が無い（開空間）場合**。端の障害物の脇を通る。障害物から
  `(robot_width_m×1.5)/2` − 車体半幅 = 0.6 − 0.3 = **0.3 m** 残る

課題Aの通路幅は航空写真で3.7〜4.9 mあり、両側に車列があっても2 m前後のギャップが残る
見込みで、この場合は内側0.5 m・外側0.9 m前後になる。**0.5 mを下回り得るのは、片側が
開いていて端の障害物の脇を通る場合（0.3 m）と、ギャップが1.6 m未満の場合である。**
`robot_width_m` を上げれば両方広がるが、ギャップの判定閾値も上がり、通れると判断する
隙間が減る。本走行まで日が無いため、既存の値のまま据え置く。

### 模擬環境で測れないこと

`obstacle_route_sim` の合成worldでは、この離隔を測れない。

- 合成worldの結合launchは `lidar_layer_slicer` を起動しないため、`side_margin_m` の
  影響をそもそも観測できない
- 模擬の車体は全幅0.4 mで、実機の0.6 mより狭い。離隔は片側0.1 m楽に出る
- 車体が障害物を押しのけて通ることがあり、通行可否の判定に使えない

### route_planner 側の成立性

次を確認した。

- 可変ブロックの `start` と `goal` に同じノード（ゲート）を指定し、チェックポイントを
  1つ与えると、進入と退出が同じノードになる経路を組み立てられる
- 固定ブロック（前半）→ 可変ブロック（往復）→ 固定ブロック（後半）の順で連結でき、
  ブロック境界で点が飛ばない。ゲートのノードは、前半・後半の分割点と同じ位置に置く
- 同じ通路を往復するため、経路の中にラベルが重複する waypoint が現れる。往路と復路で
  別の通路を通らせたい場合は、復路側にもチェックポイントを置いて経路順を縛る

不足しているのは、通路中心線から エッジごとの waypoint CSV（0.75 m間隔、接線方位、
回避幅、停止属性）を作る変換である。`route_planner/tools/segment_waypoints.py` は
採取した点列を分割するツールで、地図由来の線形からは作れない。追加する必要がある。

判断を要するのは次の点である。

- 走行時の離隔。`lidar_layer_slicer` は観測点ごとに横移動量の区間
  `[y-(robot_width_m/2+side_margin_m), y+(同)]` を塞がりとして除き、残りの上端を
  `available_*_offset_m` として出す。`route_follower` はこれを回避幅の上限に使う。
  上限まで寄せたとき、車体中心から障害物までは `robot_width_m/2+side_margin_m` に
  なる。実機の車体全幅は0.6 mであり、既定の `robot_width_m=0.6`・`side_margin_m=0.1`
  では 0.4 m となるため、**車体側面から障害物まで `side_margin_m` の0.1 mしか残らない。
  停車車両から0.5 mという条件を満たさない。** 0.5 mを残すには `side_margin_m` を
  0.5 mにする。この上限は全コースに効くため、使える回避量が一律0.4 m減り、
  `avoid_min_offset_m`（0.35 m）を割る場面では回避をやめて再経路へ移る。模擬環境で
  本線への影響を測ってから決める。`obstacle_monitor` の `robot_width_m` は0.8 mで、
  こちらは余裕を含んだ値として別に持っている
- 停車車両から0.5 mという条件を、どの観測で判定するか。URGは高さ0.49 mの1断面しか
  持たず、車両のバンパー下や張り出しを見分けられない
- 通路が塞がれていた場合に、失敗を確定させて退出する判断を誰が行うか。`/update_route` の
  再探索で回り込める場合と、チェックポイント自体へ到達できない場合を分ける必要がある

## 未決3: 実装済みの構成と、残っている確認

課題A対応と非対応の2つのルートは、同じ waypoint の行を複製せずに定義する。CSVを
複製すると、停止属性や回避幅の更新が片方にだけ入る。

現行 `route_planner` の制約は次のとおりである。

- 固定ブロックは `segment_id` が指すCSVを全行連結する。ブロック側でCSVの一部だけを
  切り出す指定は持たない
- `/get_route` の `start_label` / `goal_label` は、全ブロックを連結した後の経路に対する
  スライスである。経路の途中へ別ブロックを差し込む用途には使えない

**経路CSVをゲート地点で2ファイルへ分ける。** 課題A非対応のルートは2つの固定ブロックを
順に連結し、対応するルートは同じ2ファイルの間に課題Aの可変ブロックを挟む。どちらの
ルートでも各行は1回だけ現れ、`route_planner` のコード変更も要らない。

**分割点は `WP0738`（index 738、36.08336371645, 140.07864295169）とする。** 往路の
線分のうち、進入路の道路側の端と駐車場側の端を結ぶ線分と交わるものを探し、その手前の
waypointを採った。次を確認してある。

- 停止点ではない（`line_is_stop=0`、回避幅は左右とも3.0 m）。道路端停止 `E04` の3.3 m先
- ブロック末尾では姿勢が直前点からの方位で上書きされるが、ここは直線部であり、CSVの
  `heading_deg` との差は0.18度に収まる

分割と、課題A対応ルートの登録は済んでいる。内容は
[本走行コース](../../src/route_planner/routes/tsukuba2026/README.md) にある。同じ
`fixed/part1.csv`・`fixed/part2.csv` を2つの `route_config` が参照し、経路CSVは
複製していない。課題A対応のルートは3,997点、課題A区間は293点・215 mである。

残っているのは実機での確認と、走行時の離隔設定（未決2）である。
