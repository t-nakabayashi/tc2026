# 自律走行実現に向けた不足システムとタスクリスト

- 版: 0.2
- 作成日: 2026-07-26
- 対象: tc2026 ワークスペース全体 (`src/` 配下 20 パッケージ)

## 1. 文書目的・対象範囲

本文書は、現行システムを実機で自律走行させるために不足しているシステムを整理し、
着手順序を付けたタスクリストとして管理するものである。

- 調査方法は、`src/` 配下全パッケージの実装読解、各パッケージ `README.md` と `docs/`
  配下設計書の読解、`docs/次期システム_アーキテクチャ検討レポート.md` との突き合わせである。
- 実機・センサ・GUI を用いた動作確認は行っていない。記載はコードとドキュメントから
  確認できる事実に基づく。
- 各項目には根拠となるファイルと行番号を付す。行番号は本文書作成時点のものである。

## 3. タスクリスト

優先度の定義は以下とする。

- **P0**: これがないと実機自律走行が成立しない
- **P1**: 実機を動かす前に必要な安全項目
- **P2**: 走行品質に直結する項目
- **P3**: 運用・検証基盤

### 3.1 P0 — 実機自律走行の成立条件

- [x] **P0-1a. LiDAR ドライバの導入 (2026-07-26 完了)**
  - 使用センサは Livox Mid-360 と北陽電機 Top-URG (UTM-30LX)、および LiDAR-inertial
    odometry に FAST_LIO を用いる。
  - Mid-360: `src/livox_ros_driver2` を submodule で追加した。upstream は
    `package.xml` を持たず colcon で直接ビルドできないため、ROS 2 専用に整理された
    `atinfinity/livox_ros_driver2` の `jazzy` ブランチを追従先とする。
  - Livox-SDK2: `src/livox_sdk2_vendor` を新設し、submodule の SDK を colcon の
    install 空間へ配置する。GCC 13 の `<cstdint>` include 漏れは upstream PR #111
    相当のパッチを CMake が自動適用して解消する。`/usr/local` への sudo install は
    不要である。詳細は `src/livox_sdk2_vendor/README.md` を参照。
  - Top-URG: apt の `ros-jazzy-urg-node` を使う。ワークスペースには含めない。
  - FAST_LIO: `src/FAST_LIO` を submodule で追加した。upstream は C++14 を
    5 箇所で固定しており Jazzy の rclcpp (C++17 必須) と衝突するため、
    C++17 化のみを施した `t-nakabayashi/FAST_LIO` の `jazzy` を追従先とする。
    ビルド依存の `pcl_ros` は apt で導入する。
  - 確認: `build/` `install/` `log/` を削除したクリーン状態から
    `colcon build --symlink-install` と `colcon build` の両方が 20 パッケージ成功。

### 3.2 P1 — 実機を動かす前に必要な安全項目

- [ ] **P1-1. 非常停止 (E-stop) 系統の新設**
  - `estop` / `emergency` に相当する topic・ノードがワークスペースに存在しない。
  - 現行の安全機構は `drive_cmd_mux_node` の L1 デッドマンと cmd タイムアウトによる
    ゼロ出力、および `ypspur_node` の cmd_vel タイムアウト停止
    (`src/ypspur_ros2/src/ypspur_node.cpp:112-122`) のみである。
  - `robot_console` にも停止手段がなく、オペレータの手段はプロセスを SIGINT で
    停止して `ypspur_ros2` のタイムアウト停止に頼る形に限られる
    (`src/robot_console/robot_console/gui_core.py:236-248`)。

- [ ] **P1-2. 発進インターロックの整備**
  - `route_follower` の `start_immediately` の `declare_parameter` 既定値が `True`
    (`src/route_follower/route_follower/route_follower_node.py:92`)、
    mux の `initial_mode` が `autonomous` である。
  - このため既定パラメータのまま起動すると、route 配信の瞬間に
    `/cmd_vel/autonomous` から最終 `/cmd_vel` までが出力される。
  - manual から auto へ復帰する際の `auto_resume_delay_s` によるゼロ出力は
    初回発進には適用されない
    (`src/drive_mode_manager/drive_mode_manager/drive_mode_core.py:189-208`)。
  - 実機プロファイルで `start_immediately=false` を強制し、発進をオペレータの
    明示操作のみとする必要がある。
  - なお `params/default.yaml` は `false` であり、launch 引数既定も `false` である。
    `declare_parameter` 既定値のみが `True` で三者が不一致である。

- [ ] **P1-3. 自己位置異常時の停止ロジックの実装**
  - `robot_navigator` は `msg.pose.pose` のみを参照し共分散を見ていない
    (`src/robot_navigator/robot_navigator/robot_navigator_node.py:268-270`)。
  - RTK 劣化・自己位置ジャンプに対する制御側の安全処理がない。

- [ ] **P1-4. 入力鮮度 (age) 監視の追加**
  - `robot_navigator` は購読値を保存するのみで、`header.stamp` の鮮度検査を
    行っていない。自己位置系が停止しても最後の pose を使い続けて指令を出す。

- [ ] **P1-5. Joy 切断時の自律走行ポリシーの決定と実装**
  - `DriveModeCore._select_output` の autonomous 分岐は `joy_available` を
    参照しない
    (`src/drive_mode_manager/drive_mode_manager/drive_mode_core.py:189-208`)。
  - E-stop 不在と重なり、Joy の電池切れや Bluetooth 切断中は物理的な即時停止
    手段がなくなる。

- [ ] **P1-6. 速度上限の単一管理点の設定**
  - 手動ターボは 1.2 × 1.5 = 1.8 m/s を指令
    (`src/drive_mode_manager/params/default.yaml`)、`robot_navigator` の `max_vel`
    は 1.1、`ypspur_ros2` のクランプは 1.0
    (`src/ypspur_ros2/config/default.yaml`) と 3 層で食い違う。
  - 最終的に `ypspur_node` が 1.0 に丸めるため、GUI 表示速度と実速度が乖離する。
  - mux 出力段での最終速度リミッタと、層間の上限整合チェックが必要である。

- [ ] **P1-7. 終端状態からの復帰インタフェースの追加**
  - `route_manager` の `ERROR` / `HOLDING`、`route_follower` の `ERROR` / `FINISHED`
    から復帰する Service / Topic が実装されていない。
  - `route_manager` の外部インタフェースは `report_stuck` サービスと
    `follower_state` 購読のみで
    (`src/route_manager/route_manager/route_manager_node.py:316, 330`)、
    初期ルート要求は起動時 1 回のみである (`:690-710`)。
  - FSM は `ERROR` から `E_REQUEST_INITIAL_ROUTE` を許容するが
    (`src/route_manager/route_manager/manager_fsm.py:239`)、再発火させる経路がない。
  - `route_follower` は `ERROR` / `FINISHED` で早期 return し
    (`src/route_follower/route_follower/follower_core.py:398-399`)、
    新ルート適用でも status を変更しない。
  - 結果としてミッション再実行にノード再起動が必要である。

- [ ] **P1-8. driver 死活監視と `/diagnostics` の実装**
  - `ypspur_node` が `YPSpur_get_pos()` / `YPSpur_get_vel()` の戻り値を検査せず、
    coordinator 障害時に pose (0,0,0) の odometry を publish し続ける
    (`src/ypspur_ros2/src/ypspur_node.cpp:126-129`)。
  - `rtk_gps_um982` は設計書が規定する通信途絶 5 秒の ERROR 監視タイマーが未実装
    (`src/rtk_gps_um982/docs/design.md:197`)。
  - `/diagnostics` は全パッケージで未実装
    (`src/rtk_gps_um982/docs/design.md:201` で見送りと明記)。

- [ ] **P1-9. 信号横断の再判定と待機タイムアウトの追加**
  - `WAITING_STOP` の解除は `sig_recog == 1` の単発ラッチで一度きりであり
    (`src/route_follower/route_follower/follower_core.py:465-491`、
    ラッチは消費後クリア `:286-289`)、横断中に赤へ変わっても停止しない。
  - GO 判定は連続 `judge_count=3` フレームのみで確定する
    (`src/traffic_signal_recognizer/traffic_signal_recognizer/traffic_signal_recognizer_node.py:83`)。

### 3.3 P2 — 走行品質

- [ ] **P2-1. ゴールへの減速プロファイルの実装**
  - `pos_tol` 外では上昇側の加速度制限のみを適用し、許容内に入った瞬間に
    `v_ref = 0.0` とする
    (`src/robot_navigator/robot_navigator/robot_navigator_node.py:675-679`)。
  - 距離に応じた減速プロファイルと減速度制限が存在しない。
  - `max_acc_w` は宣言と取得のみで制御式に未使用である (`:73, :100`)。
  - PID ゲインはハードコードであり現場調整ができない (`:144-146`)。

- [ ] **P2-2. 経路追従則の導入**
  - 横偏差 (cross-track error) と曲率フィードフォワードがなく、単一 waypoint への
    heading 制御のみである。

- [ ] **P2-3. リアルタイム障害物回避の実装**
  - `robot_navigator` は `/obstacle_avoidance_hint` の `front_clearance_m` のみを
    使用し、`front_blocked` / `left_offset_m` / `right_offset_m` を参照しない
    (`src/robot_navigator/robot_navigator/robot_navigator_node.py:377-388`)。
    navigator 単体では停止のみが可能である。
  - 横方向回避は `route_follower` が `/active_target` をずらす形で実現するが、
    起動条件が重い。移動 < 0.10 m かつ速度 < 0.05 m/s が 15 秒継続する滞留検知
    (`src/route_follower/route_follower/follower_core.py:120-122`)、
    waypoint の `left_open` / `right_open` が非ゼロ (`:566-573`)、
    Hint 統計が十分かつ前方遮蔽多数決が真 (`:575-588`) の全成立が必要である。
  - 動的障害物・歩行者には構造的に対応できない。

- [ ] **P2-4. 前方検出レンジの拡大**
  - `front_clearance_m` は `x <= max_obstacle_distance_m` でフィルタした点群から
    算出するため、有限値なら必ず `max_obstacle_distance_m` 以下となる
    (`src/obstacle_monitor/obstacle_monitor/obstacle_monitor_node.py:201-209, 379-381`)。
  - `max_obstacle_distance_m` はコード既定・同梱 YAML とも 1.5 である。
  - `hint_range_m: 5.0` が設定されているが、点群が 1.5 m でカットされるため
    5 m までの距離ヒントは構造上出ない。パラメータが誤解を招く状態である。

- [ ] **P2-5. 滞留・回避パラメータの ROS パラメータ化**
  - `follower_core.py:112-137, 190-193` の 13 個のチューニング値が
    ハードコードであり、実走行での現場調整ができない。
  - `src/route_follower/README.md:91-93` も ROS パラメータ化を検討中と記載している。

- [ ] **P2-6. `obstacle_monitor` の判定形状と docstring の整合**
  - `front_cone_half_deg` は宣言のみで未使用である
    (`src/obstacle_monitor/obstacle_monitor/obstacle_monitor_node.py:51`)。
  - docstring とコメント (`:7, 181, 230`) は角度くさび判定と記載するが、
    実装は `|y| <= robot_width/2` の矩形帯である (`:374-375`)。
  - 旋回時の内輪側障害物が判定帯から外れる。

- [ ] **P2-7. GNSS アンテナから base_link へのレバーアーム補正**
  - ENU pose はアンテナ位置そのものであり
    (`child_frame_id: gps_link`、
    `src/geo_pose_converter/geo_pose_converter/geo_pose_converter_node.py:41`)、
    `robot_navigator` はこれを車体位置として扱う。
  - アンテナを車体中心からずらして搭載すると恒常的な経路ずれになる。

### 3.4 P3 — 運用・検証基盤

- [ ] **P3-1. 実機 TF ツリーの構築**
  - 実機構成で TF を publish するノードが存在しない。`TransformBroadcaster` の
    使用はシミュレーション用の 2 箇所のみである
    (`src/obstacle_route_sim/scripts/odom_tf_broadcaster.py:28`、

  - TF 責務分担は `docs/次期システム_アーキテクチャ検討レポート.md:897-922` に

- [ ] **P3-3. 実機相当の統合シミュレーションの構築**

- [ ] **P3-4. `robot_console` の状態表示の拡充**
  - `/drive_mode_status`、`/cmd_vel/autonomous`、`/rtk_gps/*` を購読していない

## 4. 着手順序の推奨

1. P0-2 (bringup と起動手順) — 現行ドキュメントどおりでは起動しないため、
   他すべての作業の前提となる。コストが小さい。
2. P1-1 (E-stop) と P1-2 (発進インターロック)、P1-3 (自己位置異常停止) —
   実機を動かす前に必要である。走らせてから作るものではない。
3. P0-4 (ENU 原点整合検証) と P0-5 の先行分 (fix 品質ゲート、BUG-3 の修正) —
   小さい修正で危険度が大きく下がる。
4. P0-1 (LiDAR 系) と P0-3 (カメラ) — センサ入力の実体を用意する。
5. P2-1 (減速プロファイル) と P2-4 (検出レンジ) — 走行品質の底上げ。
6. BUG-1〜BUG-5 の修正と P3-13 (テスト整備) — 上記作業中に踏む問題を先に除去する。
7. P3-1 (TF) / P3-3 (統合シム) / P2-2 (経路追従則) / P2-3 (リアルタイム回避) —
   中期。アーキテクチャ変更を伴う。
