# トピック通信規約

## 1. 目的

本書は、このワークスペースの自作パッケージが ROS 2 topic を配信・購読するときの共通規約を定める。

メッセージ型は用途ごとに異なってよい。統一するのは型ではなく、**配信様式・公称レート・QoS・
トピック名・Header の扱い**である。これらが宣言されていないと、購読側は配信側の実装を読むまで
QoS を決められず、受信が成立しない、または鮮度判定が誤るという不具合を繰り返す。

本書は原理のみを記述する。個々のトピックがどの様式・レートで配信されるかは、
対応する `.msg` ファイルの先頭コメントに宣言する（5章）。

---

## 2. 配信様式

すべての topic は、次の 3 様式のいずれかに分類する。

| 様式 | 定義 | 代表例 |
| --- | --- | --- |
| `stream` | 一定周期で配信し続ける。値が変化しなくても配信する。 | `/route_state`, `/follower_state`, `/drive_mode_status`, `/localization/pose_enu` |
| `latch` | 値が確定・変化したときだけ配信し、後発の購読者にも最新値を届ける。 | `/active_route`, `/mission_info` |
| `event` | 事象が発生したときだけ配信する。後発の購読者へ過去分は届けない。 | `/manual_start`, `/sig_recog`, `/road_blocked`, `/perception/*/overlay` |

様式は「値の性質」ではなく「配信タイミング」で決まる。状態量であっても周期配信するなら `stream`
である。

### 2.1 様式の選択基準

- 受信側が「いま現在の値」を常に必要とし、途絶を異常として検出したい場合は `stream` とする。
- 更新頻度が低く、後から起動した購読者（GUI、ログ収集）が最新値を必要とする場合は `latch` とする。
- 発生事実そのものが意味を持ち、再送すると二重処理になる場合は `event` とする。

### 2.2 様式の制約

- `latch` と `event` は**死活監視に使えない**。配信が無いことが正常な状態だからである（7章）。
- `stream` は、値が未確定の期間も「未確定である」ことを表す値で配信を継続する。配信を止めると、
  購読側からはノード停止と区別できない。

---

## 3. 公称レート

`stream` の topic は公称レートを宣言する。宣言値は次の 2 つに使う。

1. 購読側の鮮度判定しきい値（`stale` / `lost`）の導出
2. 帯域・処理負荷の見積り

レートがパラメータで可変な場合は、既定値を公称レートとし、パラメータ名を併記する。

鮮度しきい値は公称周期 `T = 1 / rate` から次のとおり導出する。

| しきい値 | 既定の導出 | 下限 |
| --- | --- | --- |
| `stale_sec` | `3 * T` | 0.5 秒 |
| `lost_sec` | `10 * T` | 2.0 秒 |

下限を設ける理由は、高レートな topic でしきい値が過度に短くなり、一時的なスケジューリング遅延で
誤検出することを避けるためである。導出値が実情に合わない topic は、理由を付して個別に指定してよい。

`latch` と `event` にはレートを宣言しない。

---

## 4. QoS

QoS は様式から機械的に導出する。個別トピックごとの QoS 表は作らない。

| 様式 | Reliability | Durability | History | Depth |
| --- | --- | --- | --- | --- |
| `stream` | `BEST_EFFORT` | `VOLATILE` | `KEEP_LAST` | 1 |
| `latch` | `RELIABLE` | `TRANSIENT_LOCAL` | `KEEP_LAST` | 1 |
| `event` | `RELIABLE` | `VOLATILE` | `KEEP_LAST` | 10 |

### 4.1 購読側の規則

- `stream` の購読は `BEST_EFFORT` とする。`BEST_EFFORT` 購読は `RELIABLE` 配信元とも互換であり、
  配信側の設定を調べずに接続が成立する。
- `latch` の購読は配信側と同じ `RELIABLE` / `TRANSIENT_LOCAL` とする。`VOLATILE` で購読すると、
  購読確立が配信より遅れた場合に最新値を二度と受け取れない。
- `event` の購読は `RELIABLE` とする。取りこぼしが処理の欠落に直結する。

### 4.2 例外

既定から外れる場合は、`.msg` のコメントに理由を書く。現時点の例外は次のとおり。

| topic | 例外 | 理由 |
| --- | --- | --- |
| `/localization/pose_enu` | `RELIABLE`, depth 10 | 自己位置は下流の制御入力であり、取りこぼしを避ける。 |
| `/rtk_gps/fix`, `/rtk_gps/heading`, `/rtk_gps/rtk_status` | `RELIABLE`, depth 10 | driver 実装の既定。後段はこれに合わせる。 |
| `/livox/lidar`, `/livox/imu`, `/scan` | センサ仕様に従う | 外部パッケージが配信元であり、こちらから規定しない。 |

### 4.3 外部パッケージ

`FAST_LIO`、`livox_ros_driver2` など submodule の外部パッケージは本規約の対象外とする。
これらを購読する場合は、配信側の QoS に購読側が合わせる。

---

## 5. 宣言の置き場所

配信様式・公称レート・QoS の例外は、**`.msg` ファイルの先頭コメントに書く**。別文書の一覧表は
実装から乖離するため作らない。

書式は次のとおり。

```
# <メッセージの用途を 1 行で>
#
# 配信様式: stream (20 Hz, route_follower の control_rate_hz)
# 配信元: route_follower
```

```
# 配信様式: latch
# 配信元: route_manager
```

`.msg` を持たない topic（`std_msgs` などの汎用型をそのまま使う topic）は、配信元ノードの
publisher 生成箇所の直上コメントに同じ書式で宣言する。

## 6. トピック名

### 6.1 名前空間

機能領域ごとに名前空間を割り当てる。

| 名前空間 | 領域 |
| --- | --- |
| `/localization/` | 自己位置推定の出力 |
| `/rtk_gps/` | GNSS 受信機 driver の出力 |
| `/fusion/` | GNSS・LIO 融合の状態 |
| `/lio/` | LIO の出力と前処理 |
| `/perception/<source>/` | 画像認識の出力。`<source>` は `traffic_signal` / `road_blockage` |
| `/route/` | 経路に関する派生情報 |
| `/cmd_vel/` | 速度指令の入力系統 |

経路・走行制御の中核 topic（`/active_route`, `/route_state`, `/manager_status`,
`/follower_state`, `/active_target`, `/drive_mode_status`, `/obstacle_avoidance_hint`）は、
既に広く参照されているため名前空間を付けず現行名を維持する。

### 6.2 相対名・絶対名・private 名

| 形式 | 使う条件 |
| --- | --- |
| 相対名（`route_state`） | launch からの remap を許す topic。原則こちらを使う。 |
| 絶対名（`/route_state`） | システム内で 1 本しか存在せず、remap を許さない topic。 |
| private 名（`~/ntrip_status`） | 同一ノードを複数起動する可能性があり、ノードごとに分離すべき topic。 |

publisher・subscription を相対名で書く場合、実際のトピック名を画面やログに出すときは
`Node.resolve_topic_name()` で解決した名前を使う。

### 6.3 表記

- lower_case とスラッシュ区切りを基本とする。
- 既存の公開トピック名は不用意に変更しない。

## 7. Header

`std_msgs/Header` を持たせる基準は次のとおり。

| 種別 | Header |
| --- | --- |
| 状態メッセージ（ノードの状態・観測結果を運ぶもの） | **必須** |
| 埋め込み用メッセージ（配列要素など、単独で配信しないもの） | 不要 |

Header を必須とする理由は、(1) 観測時刻と受信時刻を区別できること、(2) 複数 topic の結果を
同一フレームに対応付けられること、(3) bag 再生時に配信時刻と観測時刻を分離できることによる。

`frame_id` を持たない状態メッセージでも、`stamp` のために Header を置く。

---

## 8. 制御依存と診断の分離

診断・観測目的の topic に、制御判断を依存させてはならない。

診断 topic は「落ちても走行に影響しない」ことを前提に、レートを絞る、QoS を弱める、配信を
止めるといった変更が許される経路である。ここに制御依存を通すと、診断側の変更が走行挙動を壊す。

制御判断に使う値は、様式・レート・QoS を宣言した専用の型付きメッセージで配信する。
`std_msgs/String` に JSON を載せる形式は、スキーマが実装にしか存在せず、購読側が独自に
パースと検証を実装することになるため、制御経路には使わない。

ノードの健全性と診断情報の扱いは [ノード健全性監視設計.md](ノード健全性監視設計.md) に定める。

---

## 9. 新規トピック追加時の手順

1. 2 章の基準で配信様式を決める。
2. `stream` なら公称レートを決める。
3. 4 章の表から QoS を決める。例外にする場合は理由を用意する。
4. 6 章の規則でトピック名を決める。
5. `.msg` の先頭コメントに様式・レート・配信元を宣言する。`.msg` を持たない場合は
   publisher 生成箇所の直上に書く。
6. 状態メッセージなら `std_msgs/Header` を持たせる。
7. 死活監視に使える topic（`stream`）であれば、`robot_console` の
   `config/node_launch_profiles.yaml` の `health_topics` へ追加する。
